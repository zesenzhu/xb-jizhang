# 小宝记账文档规范

## 文档职责

- 需求文档回答“为什么做、给谁做、做什么”，不描述具体代码实现。
- 技术文档回答“系统如何实现”，记录边界、数据流、约束、风险和取舍。
- API 文档回答“前后端如何协作”，按业务领域维护；字段细节以 NestJS Swagger 和代码 DTO 为准。
- UI 文档回答“页面如何组织和反馈”，重点描述流程、状态、权限差异和移动端体验，不替代设计稿。
- ADR 记录重要技术决策的背景、选项、结论和后果，避免把关键决策只留在聊天记录中。

## 语言与命名

- `docs/` 文档正文、标题、表格、示例说明和文件名默认使用中文。
- 新增文档使用简洁明确的中文文件名，例如 `用户与角色需求.md`、`后端架构.md`、`接口约定.md`。
- 代码、命令、API 路径、配置键、枚举值和必要行业术语保留原始写法。
- 已存在的英文文件名作为历史兼容文件保留；需要迁移时必须同步更新所有链接，并单独检查 Git 历史和引用。

## 单一事实源

- 产品规则只在需求文档定义，前后端文档引用它，不重复发明另一套角色和流程。
- 接口字段以 DTO、Swagger 和 API 文档共同约束；代码契约变化时必须同步 API 文档。
- 数据归属、权限和金额规则必须同时能在需求、数据模型和测试中找到对应描述。
- 不把实现计划、临时讨论和已确认规范混在同一文档中。

## 文档元信息

正式文档开头使用 YAML frontmatter：

```yaml
---
title: 用户与角色需求
type: requirement
status: draft
version: 0.1
owner: 小宝
updatedAt: 2026-10-30
related:
  - ../requirements-baseline.md
---
```

`status` 使用 `draft`、`review`、`approved`、`implemented` 或 `deprecated`。文档进入 `approved` 前不能作为接口实现的唯一依据。

## 需求文档写法

需求至少包含：背景与问题、目标、非目标、用户角色、使用场景、功能范围、业务规则、权限规则、异常边界、验收标准、数据/API/UI 影响、测试要求和未决问题。

验收标准使用“给定 / 当 / 则”描述，使其可以直接转换为单元测试、接口测试或 E2E 测试。每条规则明确主语、前置条件和失败结果，禁止只写“支持”“完善”“正常处理”等不可验证表述。

## 技术与 API 文档写法

- 技术方案先写现状和问题，再写推荐方案、实施范围、取舍与风险。
- API 文档必须说明认证方式、角色要求、方法、路径、参数、成功响应、错误场景、幂等和并发约束。
- 数据模型文档必须说明归属边界、关系、删除策略、索引和迁移影响。
- 架构图使用 Mermaid 时，同时用文字解释关键数据流，避免图表成为唯一说明。

## UI 文档写法

页面说明至少包含页面目标、入口、核心操作、加载态、空状态、错误态、离线态、权限差异、移动端适配和可访问性要求。只有确实影响实现的视觉 token、组件约束或响应式规则才进入 UI 规范。

## 维护与审查

- 需求、权限、接口、部署或测试口径变化时，检查所有 `related` 文档和 `docs/README.md` 索引。
- 文档更新后检查链接、状态、版本、示例和术语是否一致；删除过期规则，不保留相互矛盾的旧说法。
- 不留下 `TODO`、`待确认` 伪装成已定方案。真实未决内容集中写入“未决问题”，并说明影响范围。
- 文档变更完成后按 `commit-after-change` 提交为可独立解释的原子 commit。
