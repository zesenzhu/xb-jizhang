# 小宝记账三期后端技术评估

## 1. 文档范围与结论

本文档评估三期范围（四项需求及图片附件范围收敛）对后端、数据库、部署和接口契约的影响，并给出可实施的技术方案。它不替代 DTO、Prisma Schema、实施计划或前端 UI 文档；接口路径和字段的最终契约以对应 API 文档、DTO 和 Swagger 为准。

本文以当前工作区 `3fa06ae` 的代码和三期需求 `v0.3` 为基线核对。四项需求及图片附件范围收敛的结论如下：

| 需求 | 后端影响 | 结论 |
| --- | --- | --- |
| 邀请流程修复 | 中 | 保留“邮箱目标 + 一次性 Token + 72 小时”模型，不改通用邀请码；新增公开预览、登录后 Token 详情和按邀请记录响应；登录回跳仍由前端负责 |
| 账单图片附件 | 无（本期不做） | 移出三期范围；后端不新增附件表、接口、对象存储和备份任务，专项设计保留为后续方案 |
| 历史备注快捷选择 | 小到中 | 不新增备注模板表；为 `Transaction` 增加 `noteUpdatedAt`，新增账本内备注候选查询；同时把后端备注上限从 2000 收敛到 200 |
| 原生键盘适配 | 无 | 纯前端视口和输入体验改造，后端不新增接口或字段 |
| 日期时间选择优化 | 小 | 不改变时间存储和统计口径；补强 `occurredAt` 校验，要求带时区的完整 ISO 8601 时间 |

本期明确不引入：邀请邮件/短信/推送、站内消息中心、按账号搜索用户、图片 OCR、图片内容审核、Redis 图片缓存、公开对象桶、预签名直传。Redis 适合缓存短期状态，不适合作为图片二进制的主存储。

## 2. 现状核对

### 2.1 邀请

当前 `invitation` 模块已实现创建、账本待处理邀请列表、我的邀请、按 Token 接受/拒绝和撤销。核对结果：

- `LedgerInvitation` 只保存 `targetEmail`、`tokenHash`、角色、状态、过期时间和 `acceptedAt`，符合邮箱目标和 Token 哈希模型。
- 同一账本、同一邮箱的 `PENDING` 唯一性由数据库部分唯一索引 `ledger_invitation_pending_ledger_email_key` 保证，Service 还会把唯一冲突转换为 `40901`。
- 创建邀请只在响应中返回一次性 `inviteToken`；后续列表和详情不返回 Token。
- `GET /api/invitations` 只返回与当前用户邮箱匹配、未过期的 `PENDING` 邀请，但不返回 `inviter`，也没有可响应邀请的标识或 Token。
- 接受/拒绝只接受 `token` 请求体。没有 Token 的“我的邀请”列表因此只能看、不能操作。
- 邀请目标邮箱与当前用户邮箱不一致时，Service 返回 `40401`，前端无法区分“链接无效”和“邮箱不匹配”，也不方便引导补全邮箱。
- 账号未填写邮箱时返回通用 `40001`，没有可执行的 `SET_EMAIL` 语义。
- 邀请登录回跳是前端路由守卫行为，不在 API 契约内；当前 API 没有 `redirect` 参数，也不应新增任意 URL 回跳。

### 2.2 备注

`Transaction.note` 已入库，创建和编辑 DTO 当前允许 1 到 2000 个字符；产品需求和前端抽屉都按 200 个字符处理。`docs/前端/记账抽屉.md` 已把“后端允许 2000、前端收紧 200”列为待收敛项，本期应关闭该差异。

当前没有备注候选接口，也没有按“备注最近使用时间”查询的索引或字段。直接用 `Transaction.updatedAt` 排序会被金额、分类等无关修改干扰，不能准确表达“最近使用过的备注”。

### 2.3 附件（本期不做）

当前没有附件模型、对象存储依赖或上传接口；前端“图片”是禁用占位。本期不处理附件，因此不引入 `ApiResponseInterceptor` 的二进制例外，也不新增 413/415/503 映射。相关约束保留在后续专项设计中。

### 2.4 时间

`occurredAt` 使用 `@IsISO8601()` 校验，接受日期或没有时区偏移的本地时间；Service 再用 `new Date()` 解析。对于日期时间选择器，这会产生两个风险：

- 前端如果发送 `2026-11-08T20:30` 这类无偏移时间，服务端会按运行环境本地时区解释，和账本时区不一致；
- `@IsISO8601()` 对 `2026-02-30` 等非法日历日期不一定严格拒绝，可能在解析时被归一化。

统计按账本时区分组，现有实现不需要改变；需要补强的是写入契约，而不是统计逻辑。

## 3. 邀请流程后端设计

### 3.1 方案选择

保留现有邀请模型，增加“按邀请记录响应”的第二种寻址方式，而不是把 Token 放进“我的邀请”列表。理由是：

- Token 只在创建时返回一次，是链接持有者的凭据；把它重新暴露给已登录用户会扩大泄露面。
- `invitationId` 是当前用户邮箱匹配后可读取的记录 ID，配合服务端邮箱校验即可安全用于就地接受/拒绝。
- 链接流程仍需要 Token 预览和登录后详情；Token 与 ID 最终调用同一状态迁移逻辑，避免两套规则。

不采用“输入对方账号直接加人”：账号搜索会带来用户枚举和隐私问题，且需求已经确认保留邮箱邀请。

### 3.2 接口面

| 方法 | 路径 | 认证 | 用途 | 状态 |
| --- | --- | --- | --- | --- |
| `GET` | `/api/invitations/preview?token=` | 公开 | 登录前查看邀请说明和终态 | 新增 |
| `GET` | `/api/invitations/token?token=` | 登录 | 登录后查看邀请详情、邮箱匹配状态 | 新增 |
| `GET` | `/api/invitations` | 登录 | 我的待处理邀请，可直接响应 | 扩展响应字段 |
| `POST` | `/api/invitations/:invitationId/accept` | 登录 | 按邀请记录接受 | 新增 |
| `POST` | `/api/invitations/:invitationId/decline` | 登录 | 按邀请记录拒绝 | 新增 |
| `POST` | `/api/invitations/accept` | 登录 | 按 Token 接受，兼容旧客户端 | 保留 |
| `POST` | `/api/invitations/decline` | 登录 | 按 Token 拒绝，兼容旧客户端 | 保留 |
| `POST` | `/api/ledgers/:ledgerId/invitations` | `OWNER` | 创建邀请，返回一次性 Token | 不变 |
| `GET` | `/api/ledgers/:ledgerId/invitations` | `OWNER` | 账本待处理邀请 | 不变 |
| `DELETE` | `/api/ledgers/:ledgerId/invitations/:invitationId` | `OWNER` | 撤销邀请 | 不变 |

建议新前端统一走“Token 详情 → 按 ID 响应”或“我的邀请 → 按 ID 响应”；旧 Token 接口只用于兼容，不再作为新页面的主路径。

### 3.3 状态机与幂等

| 当前状态 | 操作 | 条件 | 结果状态 | 响应 |
| --- | --- | --- | --- | --- |
| `PENDING` | 接受 | 邮箱匹配、非成员 | `ACCEPTED` | `200`，创建成员关系 |
| `PENDING` | 接受 | 邮箱匹配、已是 `ACTIVE` 成员 | `ACCEPTED` | `200`，`alreadyMember=true`，不新增成员 |
| `PENDING` | 接受 | 邮箱匹配、原成员为 `LEFT/REMOVED` | `ACCEPTED` | `200`，复用原成员关系并恢复 `ACTIVE` |
| `PENDING` | 拒绝 | 邮箱匹配 | `DECLINED` | `200`，`data: null` |
| `PENDING` | 接受/拒绝 | 已过期 | `EXPIRED` | `409`，返回终态 |
| `ACCEPTED` | 接受 | 当前用户仍是活跃成员 | `ACCEPTED` | `200`，`alreadyMember=true` |
| `ACCEPTED` | 接受 | 当前用户已不是活跃成员 | `ACCEPTED` | `409`，不能凭旧邀请重新加入 |
| `DECLINED` | 拒绝 | 邮箱匹配 | `DECLINED` | `200`，幂等 |
| `DECLINED/REVOKED/EXPIRED` | 接受 | 任意 | 不变 | `409`，返回终态 |
| `REVOKED/ACCEPTED` | 拒绝 | 任意 | 不变 | `409`，返回终态 |

“已是活跃成员”时消费邀请并返回 `alreadyMember=true`，是为了避免邀请永远停留在待处理列表；不新增第二条 `LedgerMember`。

### 3.4 事务与并发

接受邀请的推荐事务顺序：

```text
开始事务
  → 按 ID 或 Token 定位邀请
  → 对账本行加 FOR KEY SHARE（与账本删除互斥）
  → 对邀请行加 FOR UPDATE（串行化同一邀请的响应）
  → 重新读取当前用户邮箱并校验目标邮箱
  → 校验状态、有效期、账本是否存在
  → 查询成员关系
  → 创建、恢复或确认已有成员
  → 条件更新邀请 PENDING → ACCEPTED
  → 提交
```

拒绝邀请不需要成员关系，只需锁邀请行并条件更新 `PENDING → DECLINED`。撤销由 Owner 执行，同样使用条件更新，不覆盖已进入终态的邀请。

锁顺序统一为“账本 → 邀请 → 成员”，避免接受邀请、账本删除和撤销并发时出现反向锁序。条件更新影响行数为 0 时返回 `40931`，不能静默覆盖。

### 3.5 邮箱前提与错误语义

- 当前账号没有邮箱：返回 `40031`，`data.action = "SET_EMAIL"`，不消费邀请。
- 当前账号邮箱与目标邮箱不一致：返回 `40331`，`data.action = "CHANGE_EMAIL"`，可带脱敏目标邮箱，不消费邀请。
- 邀请不存在、Token 无效或不属于当前用户可见范围：返回 `40431`，不泄露邀请是否存在。
- 邀请已过期、撤销、拒绝或已接受且无法幂等：返回 `40931`，`data.status` 返回终态。
- 已是活跃成员：接受返回 `200`，`alreadyMember = true`，并在 `data.ledger` 中返回可进入的账本摘要。

Token 详情接口对“邮箱未填/不匹配”返回 `200` 和 `blockedReason`，让前端能直接渲染补全入口；真正执行接受/拒绝时才使用上述错误码。这样既保留可解释的 UI，又不把校验失败伪装成成功。

邮箱补全复用 `PATCH /api/users/me`，不新增接口。邮箱修改成功后，前端重新拉取 Token 详情或我的邀请，再继续响应。

### 3.6 安全与日志

- 邀请 Token 继续使用 32 字节随机值，数据库只存 SHA-256 哈希；Token 只在创建响应返回一次。
- 公开预览只返回账本名称、邀请人展示名、角色、状态和过期时间，不返回 `ledgerId`、成员、账单、金额或完整目标邮箱。
- 公开预览、Token 详情、我的邀请都使用 `Cache-Control: no-store`，避免共享设备或代理缓存泄露邀请信息。
- 邀请链接当前使用查询参数 `?token=`，Nginx 访问日志会记录完整 `$request`。上线前必须对邀请相关路径隐藏查询串，或在日志格式中对 `token` 做脱敏；同时在邀请页设置 `Referrer-Policy: no-referrer`，避免第三方资源拿到完整链接。
- 邀请相关接口需要限流：公开预览按 IP，Token 详情按用户，接受/拒绝按用户。具体窗口在实现计划中固定，至少返回 `42901`。
- 登录和注册 API 不接受 `redirect` 参数；回跳路径由前端生成并在站内校验，后端不能成为开放重定向的一环。

### 3.7 数据与索引

本期不新增邀请表字段，继续使用 `LedgerInvitation` 现有结构。需要补一个查询索引：

```prisma
@@index([targetEmail, status, expiresAt])
```

该索引服务“我的邀请”按当前邮箱查询待处理、未过期邀请。账本维度的待处理列表继续使用现有 `[ledgerId, targetEmail, status]` 和 `[ledgerId, status]`。

不把 `tokenHash` 或 Token 放进列表响应；不新增 `invitation_notification` 表。邀请提醒仍由“我的邀请”数量和页面状态表达。

## 4. 图片附件：本期不做

账单图片附件与对象存储已移出三期范围。本期不新增 `TransactionAttachment` 表、对象存储配置、上传/读取/删除接口、附件清理任务和附件备份演练；`ATTACHMENT_ENABLED` 等开关也不进入本期实施。

保留[账单图片附件与对象存储设计](./账单图片附件与对象存储设计.md)作为后续专项方案，用于记录 MinIO/OSS 选型、2C2G 服务器评估、上传接口、幂等、备份和预签名演进。该文档本期状态为后续设计，不能作为本期迁移或接口实现依据。

本期不做附件带来的直接结果：

- 账单接口不返回 `attachmentCount` 或 `attachments`；
- 不新增 `40041`、`40341`、`40441`、`40941`、`40942`、`41301`、`41501`、`50341` 等附件专用错误码；
- 记账快捷条“图片”入口继续保持禁用或隐藏；
- 数据库迁移只包含邀请索引、备注字段和备注索引，不包含附件表。

## 5. 历史备注快捷选择

### 5.1 数据与排序

不新增备注模板表。备注仍是 `Transaction.note`，新增一个可空字段：

```prisma
noteUpdatedAt DateTime? @map("note_updated_at")
```

语义：

- 创建账单时备注非空：`noteUpdatedAt = now`。
- 编辑时备注文本发生变化：`noteUpdatedAt = now`。
- 编辑时备注未变化：保持原值，避免修改金额导致备注跳到最前。
- 备注被清空：`noteUpdatedAt = null`。
- 账单软删除：不修改 `noteUpdatedAt`，候选查询通过 `deletedAt IS NULL` 排除。
- Migration 回填：现有非空备注使用 `updatedAt` 作为 `noteUpdatedAt`。

索引：

```prisma
@@index([ledgerId, createdById, noteUpdatedAt])
```

候选按 `noteUpdatedAt DESC, createdAt DESC` 排序，取当前用户在当前账本中最近的 10 条去重文本。只使用 `createdById = 当前用户`，不把其他成员创建的备注带入，避免共享账本中泄露他人的备注习惯。

### 5.2 查询口径

- 只查当前账本、未删除、非空备注。
- 去除首尾空白后去重；保留最近一次文本内容。
- 只返回长度不超过 200 的备注；历史超长备注仍在账单详情中可读，但不进入候选。
- 默认和最大 `limit` 都是 10。
- 不使用 `Transaction.updatedAt` 排序，避免无关字段编辑影响候选顺序。
- 数据量增大后可以使用 `SELECT DISTINCT ON (btrim(note))` 的原生 SQL；个人规模也可以先按 `noteUpdatedAt` 取有限窗口后在 Service 去重，但必须保证“最近 10 条唯一文本”不被同文本淹没。推荐前者，并通过集成测试锁定时区、排序和去重结果。

### 5.3 接口与缓存

- `GET /api/ledgers/:ledgerId/note-suggestions?limit=10`，`VIEWER` 及以上可读。
- 返回 `{ items: [{ text, lastUsedAt }] }`，固定上限、非分页。
- `Cache-Control: private, max-age=30`；账单创建、编辑、删除后前端主动失效候选缓存。
- 首期不引入 Redis 缓存。若后续需要，Key 使用 `jizhang:note-suggestions:{ledgerId}:{userId}`，TTL 30 秒，并在账单写操作后删除。

### 5.4 备注长度收敛

需求和前端都按 200 个字符处理，后端 DTO 当前是 2000。建议：

- 创建和编辑 DTO 改为 200；
- 现有超过 200 的备注不截断、不删除，仍可读取；
- 候选接口过滤超过 200 的历史备注；
- 上线前执行一次审计查询，确认是否存在超过 200 的备注；若存在，产品需确认“编辑时要求缩短”还是保留旧值只读。不能静默截断用户历史数据。

## 6. 键盘与时间选择的后端边界

### 6.1 键盘

键盘挤压、输入框自动放大、`visualViewport`、安全区和候选条位置都是前端职责。后端不新增接口、字段或配置，也不通过禁止缩放来规避问题。需要保证账单创建/编辑接口在键盘开合、重试和重复提交时仍然幂等，这部分沿用现有 `clientRequestId` 和版本控制。

### 6.2 时间

- `occurredAt` 必须是有日期、时间且带 `Z` 或 `±HH:mm` 偏移的 ISO 8601 字符串；日期-only 和无偏移本地时间拒绝，返回 `40021`。
- 使用 `@js-temporal/polyfill` 或等价严格解析校验日历合法性，拒绝 `2026-02-30` 这类会被 `Date` 归一化的值。
- 前端按账本时区选择时间，再转换为带偏移的 instant；后端按 instant 存储，统计继续按账本时区分组。
- 时间选择器取消不提交，确认后才进入 `PATCH`；这与现有版本控制兼容。
- 不新增时间字段，不修改统计口径；时间修改后仍递增 `version` 并写审计。

## 7. 横切契约

### 7.1 错误码

| HTTP | code | 场景 |
| --- | --- | --- |
| `400` | `40031` | 响应邀请前需要设置邮箱 |
| `403` | `40331` | 当前账号邮箱与邀请目标不一致 |
| `404` | `40431` | 邀请不存在、Token 无效或不可见 |
| `409` | `40931` | 邀请已过期、撤销、拒绝或状态不允许 |
| `429` | `42901` | 邀请预览或响应接口超过限流阈值 |

`ApiExceptionFilter` 本期不需要新增 413/415/503 映射；后续附件功能立项时再补。领域 Service 显式抛出带 `code` 的异常时，仍以显式 `code` 为准。

### 7.2 响应与日志

- 邀请预览和响应接口不得记录完整 Token、签名 URL 或存储密钥。
- 邀请 Token 在查询串中时，Nginx 访问日志必须脱敏；建议在站点配置中对 `/user/invitations` 和 `/api/invitations/preview|token` 使用不含 `$args` 的日志格式，或把 Token 迁移到 URL fragment。

### 7.3 限流

当前代码没有统一的应用层限流 Guard。建议本期至少对以下接口增加限流，并在实现计划中确定窗口：

| 接口 | 维度 | 建议 |
| --- | --- | --- |
| 邀请公开预览 | IP + token | 每分钟 30 次 |
| Token 详情 / 我的邀请 | 用户 | 每分钟 60 次 |
| 接受/拒绝邀请 | 用户 | 每分钟 10 次 |

单实例可以使用应用内限流；多实例或需要跨重启保持时使用 Redis。限流失败返回 `42901`，不泄露目标用户或账本是否存在。

## 8. 数据库与迁移

建议按以下顺序生成互不破坏的 Migration：

1. `ledger_invitation` 增加 `[targetEmail, status, expiresAt]` 索引。
2. `transaction` 增加 `note_updated_at`，回填非空备注，增加 `[ledgerId, createdById, noteUpdatedAt]` 索引。
3. 不删除 `Transaction.note`，不重命名现有列；不使用 `db push`。

迁移前检查：

- 是否存在超过 200 字符的备注；
- 现有 `LedgerInvitation.PENDING` 数据是否满足部分唯一索引；

## 9. 实施与发布顺序

1. **邀请后端**：新增索引和响应接口，保留旧 Token 接口；前端随后接入。先发后端是加法变更，不破坏旧页面。
2. **备注候选**：增加 `noteUpdatedAt` 和候选接口；先完成备注长度审计，再收敛 DTO 到 200。若存在历史超长备注，先与产品确认处理方式。
3. **时间校验**：先让前端发送带偏移的完整 ISO 时间，再开启后端严格校验，避免旧客户端被突然拒绝。

## 10. 测试要求

- 邀请 Service：按 ID/Token 接受、邮箱缺失、邮箱不匹配、已活跃成员、`LEFT/REMOVED` 恢复、过期/撤销/拒绝终态、重复接受幂等。
- 邀请 Controller：公开预览不需要认证，Token 详情和按 ID 响应需要认证，路径参数和 DTO 正确传递。
- 邀请集成：部分唯一索引、并发接受、账本删除与接受的锁互斥、我的邀请只返回匹配邮箱。
- 备注：`noteUpdatedAt` 创建/编辑/清空语义、账本隔离、去重、排序、10 条上限、超长备注排除。
- 时间：带偏移 ISO 通过，日期-only、无偏移、非法日历日期返回 `40021`。

## 11. 风险与未决问题

1. 现有数据是否存在超过 200 字符的备注尚未审计；在确认前不能静默截断历史备注。
2. 邀请 Token 目前在查询串中，Nginx 日志脱敏是上线前置条件；迁移到 URL fragment 会改变链接格式和回跳处理，本期不作为默认方案。
3. 公开邀请预览会向 Token 持有者展示账本名称和邀请人昵称，属于可接受的 bearer 信息，但需要限流和 `no-store`；是否进一步减少展示字段待评审。
4. 图片附件后续立项时，需要重新确认存储选型、2C2G 服务器容量、备份恢复和移动端上传体验。

## 12. 决策摘要

| 决策 | 结论 |
| --- | --- |
| 邀请模型 | 保留邮箱目标、一次性 Token、72 小时；新增按邀请记录响应，不改为通用邀请码 |
| 邀请列表 | 返回可响应记录和邀请人信息，不返回 Token |
| 登录回跳 | 前端保存 `pathname + search` 并校验站内路径；API 不接收任意 redirect |
| 备注候选 | 不建模板表；增加 `noteUpdatedAt` 和账本内候选查询；只取当前用户备注 |
| 备注长度 | 后端收敛到 200；历史超长备注先审计，不静默截断 |
| 键盘 | 纯前端，无后端/API 变更 |
| 时间 | 保持 ISO instant 和账本时区；补强带偏移与日历合法性校验 |
