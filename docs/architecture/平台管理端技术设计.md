# 小宝记账平台管理端技术设计

## 1. 设计范围

本文档定义 NestJS 后台对平台管理端的身份、会话、权限、数据模型、审计、接口和部署边界。前端管理页面暂不实现，但后台必须按本设计预留模块和数据库结构，避免后续把普通用户体系改造成混合管理员体系。

## 2. 现状与问题

当前后台的 `auth` 和 `user` 模块服务普通用户，`User` 通过 `LedgerMember` 访问账本。账本成员角色只适用于单个账本，不能承担平台管理员权限。如果将管理员直接实现为 `User.isAdmin`，会导致 Cookie、Guard、刷新会话、权限查询和审计主体混用。

## 3. 推荐架构

采用两个独立身份域：

```text
普通用户域
User ── RefreshSession
  └── LedgerMember ── Ledger ── Transaction

平台管理域
AdminUser ── AdminRefreshSession
    └── AdminUserRole ── AdminRole ── AdminRolePermission ── AdminPermission
                                      │
                                      └── AdminAuditLog
```

两套身份域共享同一个 NestJS 服务和 PostgreSQL 实例，但不共享登录 Cookie、Token audience、刷新会话表或 Guard。管理员如需记账，必须另外使用普通用户账号。

## 4. 后端模块边界

建议新增以下 NestJS 模块：

| 模块 | 职责 | 关键边界 |
| --- | --- | --- |
| `admin-auth` | 管理员登录、刷新、退出、当前管理员和会话撤销 | 只接受 `AdminUser`，不调用普通用户登录流程 |
| `admin-user` | 管理员账号、启停、角色绑定 | 仅 `admin:admin_user:manage` 可修改 |
| `admin-permission` | 内置角色、权限码和权限解析 | 普通用户账本角色不接入此模块 |
| `admin-user-management` | 用户查询、状态操作和资料脱敏 | 不返回密码、Token 或内部密钥 |
| `admin-ledger` | 账本查询、归档/恢复和运营摘要 | 默认不修改账单正文和成员 Owner |
| `admin-transaction` | 按独立高风险权限查看或修改账单 | 所有读取和写入都需要理由与审计 |
| `admin-config` | 受控系统配置读写 | 秘密配置不通过普通 API 返回 |
| `admin-audit` | 审计日志写入和查询 | 日志追加写，查询也受权限控制 |
| `admin-common` | 管理员上下文、权限装饰器、请求元数据 | 不复用普通用户身份上下文 |

普通用户的 `auth`、`user`、`ledger` 和 `ledger-member` 模块继续只服务普通用户域。公共响应、异常和请求 ID 可以复用 `common`，但认证上下文和权限判断必须保持身份域隔离。

## 5. 认证和会话设计

### 5.1 登录链路

```text
POST /api/admin/auth/login
  ↓
AdminAuthGuard / 管理员凭证校验
  ↓
AdminUser 状态校验
  ↓
AdminRefreshSession 持久化 Token 哈希
  ↓
签发 aud=admin 的 access/refresh Token
  ↓
写入 admin_access_token / admin_refresh_token Cookie
```

管理员访问后台接口时必须依次完成：Cookie 读取、JWT 签名校验、`type=admin_access` 校验、`aud=admin` 校验、管理员状态校验和权限码校验。不能只验证 JWT 有效就放行。

### 5.2 Cookie 与 JWT

| 项目 | 普通用户 | 平台管理员 |
| --- | --- | --- |
| Access Cookie | `access_token` | `admin_access_token` |
| Refresh Cookie | `refresh_token` | `admin_refresh_token` |
| Access audience | `app` | `admin` |
| Access 类型 | `access` | `admin_access` |
| Refresh 存储 | `RefreshSession` | `AdminRefreshSession` |
| Guard | `AuthGuard` | `AdminAuthGuard` |

管理员 Cookie 使用 HttpOnly、Secure（生产）、明确 Path 和 `SameSite`。后台前端未来与 API 同源时，管理员刷新 Cookie 的 Path 可以限制到 `/api/admin/auth`，降低发送范围。

### 5.3 刷新和撤销

- Refresh Token 只保存 SHA-256 哈希，不保存原文。
- 每次刷新都创建新的 `AdminRefreshSession`，旧会话记录 `revokedAt` 和 `replacedBySessionId`。
- 检测到旧 Token 重放时，撤销该管理员的全部活跃管理会话，并返回专用认证错误。
- 管理员停用、修改密码或权限发生重大变化时，可以撤销全部管理会话。
- Redis 只用于限流、短期锁或缓存，不作为管理员刷新会话的唯一来源。

## 6. 权限模型

### 6.1 数据关系

推荐使用可扩展的 RBAC 模型：

```text
AdminUser ──< AdminUserRole >── AdminRole
AdminRole ──< AdminRolePermission >── AdminPermission
```

角色和权限使用稳定的英文 `code` 唯一约束。内置角色由迁移或初始化脚本创建，不能通过普通运营接口删除。管理员请求上下文包含 `adminUserId` 和解析后的权限集合，最终授权仍由服务端数据库状态决定。

### 6.2 权限检查

建议提供以下通用能力：

```text
getAdminContext(request)
requireAdminPermission(context, 'admin:user:status')
requireAuditReason(input.reason)
recordAdminAudit(context, operation)
```

Controller 可以使用权限装饰器表达接口要求，但 Service 必须在关键写操作前再次检查资源归属、目标状态和权限，不能只依赖路由层装饰器。

权限不足返回管理端专用错误码，但不暴露其他管理员、权限配置或资源存在性信息。普通用户 Token 命中管理端路由时按认证失败处理。

## 7. 数据模型方向

### 7.1 `AdminUser`

至少包含：

- `id`、`username`、`passwordHash`、`displayName`；
- `isActive`、`lastLoginAt`、`createdAt`、`updatedAt`；
- 可选的 `mfaEnabled` 和 MFA 配置引用，不在普通查询中返回。

`username` 全局唯一。管理员账号不保存普通用户 `User` 的外键。

### 7.2 权限模型表

- `AdminRole`：角色编码、名称、描述、内置标识和时间字段；
- `AdminPermission`：权限编码、名称、描述和时间字段；
- `AdminUserRole`：管理员与角色的唯一关系；
- `AdminRolePermission`：角色与权限的唯一关系。

所有关系表使用复合唯一约束，外键删除策略默认禁止误删或使用明确的级联策略。角色和权限变更必须记录审计。

### 7.3 `AdminRefreshSession`

至少包含 `adminUserId`、`tokenHash`、`deviceName`、`userAgent`、`lastUsedAt`、`expiresAt`、`revokedAt`、`replacedBySessionId`、`createdAt`。`tokenHash` 建立唯一索引，`adminUserId + revokedAt` 和 `expiresAt` 建立查询索引。

### 7.4 `AdminAuditLog`

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 审计 ID |
| `adminUserId` | 操作管理员 |
| `requestId` | 请求关联 ID |
| `action` | 稳定操作编码 |
| `targetType` / `targetId` | 目标资源类型和 ID |
| `reason` | 操作原因 |
| `beforeData` / `afterData` | 脱敏前后摘要 JSON |
| `result` | `SUCCESS` 或 `FAILURE` |
| `errorCode` | 失败时的分类错误码 |
| `ip` / `userAgent` | 请求来源信息 |
| `createdAt` | 发生时间 |

审计日志只追加写，不允许物理修改。`beforeData`、`afterData` 必须过滤密码、Cookie、Token、密钥和完整个人敏感信息；大字段或附件不直接写入日志。

## 8. 后台业务数据操作边界

### 8.1 用户和账本

后台查询可以跨账本，但必须根据权限返回脱敏结果。禁用用户、归档账本等状态操作使用事务，并在更新条件中检查当前状态，避免并发覆盖。

### 8.2 账单

后台默认只读取汇总或脱敏信息。敏感账单读取和账单修改单独拆成权限，并要求操作原因。管理员修改账单时：

1. 校验管理员权限、目标账单存在性和当前版本；
2. 校验修改字段和金额规则，复用普通账单领域规则；
3. 在同一事务中更新账单并写入审计；
4. 返回脱敏后的服务端最新数据。

管理员操作不能通过伪造普通用户 `createdById`、`updatedById` 或 `payerId` 隐藏操作来源。

### 8.3 配置

可管理配置与部署秘密分离。数据库连接串、JWT Secret、Redis 密码等只通过部署环境注入，不能进入 `AdminConfig` 或管理端响应。

## 9. 部署和前端边界

- 后端继续与普通 API 共用 NestJS 服务、容器和数据库，但路径以 `/api/admin/**` 隔离。
- 未来前端使用 `/admin/login` 和 `/admin/**`，普通用户继续使用 `/login` 和账本路由。
- Nginx 可以按 `/api/admin` 做限流、访问日志和额外安全策略；不要求拆成独立服务。
- 管理端暂不实现 Next.js 页面，但后端 CORS、Cookie Path、审计请求 ID 和错误码必须为独立前端预留。
- 生产环境必须使用 HTTPS；管理端入口可以额外限制 IP、VPN 或内网访问，作为部署策略而不是业务权限替代品。

## 10. 测试设计

- `AdminAuthService`：登录、停用账号、刷新轮换、重放检测、全部会话撤销。
- `AdminAuthGuard`：普通用户 Token、错误 audience、过期 Token、停用管理员和有效管理员。
- 权限 Service：三个内置角色的允许/拒绝矩阵、单权限授权和角色变更即时生效。
- 用户/账本管理 Service：分页契约、状态变更、并发冲突、脱敏字段和审计写入。
- 账单高风险操作：无权限、无理由、版本冲突、事务回滚、成功和失败审计。
- Repository/Controller：方法、URL、payload、认证上下文、错误码和不返回秘密字段。
- 数据库集成：管理员角色关系唯一约束、刷新会话链、审计追加写和权限变更后的即时读取。

## 11. 实施顺序

1. Prisma 增加 `AdminUser`、角色权限关系、`AdminRefreshSession` 和 `AdminAuditLog` 模型与迁移。
2. 实现 `admin-common`、`admin-auth` 和独立 Cookie/Token 验证。
3. 实现内置角色、权限码初始化和权限查询。
4. 实现用户、账本和审计查询接口，先提供脱敏只读能力。
5. 实现用户/账本状态操作和配置管理，接入操作原因与审计。
6. 最后评审敏感账单读取和修改能力，单独开通高风险权限和测试。

## 12. 取舍、风险与未决问题

- 独立账号体系增加管理端账号维护成本，但能避免管理员身份进入普通业务边界，推荐保留。
- RBAC 表结构比 `isAdmin` 复杂，但支持审计、最小权限和后续扩展，推荐一次性建立。
- 管理端与普通 API 共用服务降低部署成本，但必须严格隔离 Guard、Cookie、audience 和模块依赖。
- MFA、审计保留周期、敏感账单字段脱敏规则、后台入口是否限制内网，需要生产上线前形成独立安全评审结论。
