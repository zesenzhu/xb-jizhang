# 第四期账单图片附件与对象存储设计

> **第四期方案评审稿。** 三期仍不实施图片附件；本文记录第四期接入对象存储的目标架构、接口和运维约束。本文获批后再拆分 Prisma、后台接口、前端上传和部署实施任务。
>
> 本文正文中的“本期”均指第四期附件实施期，不代表当前三期范围。

## 1. 结论先行

第四期采用“对象存储保存文件 + PostgreSQL 保存元数据 + 预签名直传/直读”的方案：

| 决策 | 结论 |
| --- | --- |
| 存储 | 本地开发使用私有 MinIO；线上使用阿里云 OSS 标准本地冗余私有 Bucket |
| 桶 | 私有，不开放匿名读，不直接暴露公网 |
| 上传 | 先保存账单，再由 NestJS 签发短期上传地址，前端直传对象存储并调用完成确认 |
| 上传方式 | 预签名 `PUT`：前端 → MinIO/OSS；后台通过 `HEAD` 校验大小、类型和对象存在性 |
| 读取 | NestJS 鉴权后签发 5 分钟短期下载地址，前端直读对象存储 |
| 幂等 | 每张图片一个 `clientRequestId`，在同一账单内唯一 |
| 数量 | 单笔账单最多 5 张；单张不超过 10 MB；JPEG/PNG/WebP |
| 删除 | 数据库先标记 `DELETED`，对象异步清理，失败可重试 |
| 备份 | PostgreSQL 与对象存储必须同一套备份、恢复和演练 |
| 演进 | 后续再评估图片压缩、缩略图、分片上传和 CDN，不改变附件领域模型 |

### 1.1 阿里云 OSS 试用套餐边界

当前线上计划使用阿里云“对象存储 OSS 标准 - 本地冗余存储 20GB 3 个月”套餐，已知额度如下：

| 资源 | 当前额度 | 方案处理 |
| --- | --- | --- |
| 标准本地冗余存储 | 20 GB | 只存账单图片及附件对象，不存数据库备份 |
| 下行流量包 | 2 GB | 统计图片访问和下载；达到 80% 时告警 |
| 请求包 | 20 万次 | 统计 PUT、GET、HEAD、DELETE 等对象请求；达到 80% 时告警 |
| 有效期 | 3 个月 | 到期前确认续费、转按量付费或升级，不默认假设数据会被删除 |

本地冗余表示同一可用区内多设备冗余，适合第四期初期的个人和小型共享账本；它不等于跨可用区或跨地域容灾。重要附件仍需纳入独立备份和恢复演练。

按图片大小粗略估算，20 GB 约可保存 2 万张 1 MB 图片或 6,600 张 3 MB 图片；实际容量还要扣除缩略图、重试产生的临时对象和历史版本。2 GB 下行流量约对应 2,000 次 1 MB 原图下载，不能按“存储 20 GB”理解为可以无限读取。

### 1.2 当前服务器评估

当前生产服务器为阿里云 `ecs.e-c1m1.large`：2 vCPU、2 GiB 内存、Alibaba Cloud Linux 3、20 GB 系统盘。这个配置对“记账 API + PostgreSQL + Redis + Nginx + Next.js”已经偏紧，再在同一台机器上跑 MinIO 会明显增加 OOM 和磁盘不足风险。

按 Docker 单机部署估算：

| 组件 | 常驻内存估算 |
| --- | --- |
| 操作系统、Docker、日志与监控代理 | 300–500 MB |
| Nginx | 30–60 MB |
| Next.js 运行时 | 200–350 MB |
| NestJS 运行时 | 150–300 MB |
| PostgreSQL（`shared_buffers` 128 MB 左右） | 150–300 MB |
| Redis | 30–60 MB |
| MinIO（空闲到小文件读写） | 100–250 MB |
| 预留余量 | 200–400 MB |

不含 MinIO 时约 0.9–1.6 GB；加上 MinIO 约 1.0–1.8 GB。2 GiB 在正常低峰可能勉强运行，但以下场景很容易触发 OOM 或明显变慢：

- 同时上传多张 10 MB 图片，NestJS 内存缓冲叠加；
- `docker load` 新镜像、应用启动和 PostgreSQL 检查点同时发生；
- MinIO 与 PostgreSQL 争抢页缓存；
- 备份、日志轮转或系统更新占用内存和磁盘。

CPU 方面，2 vCPU 对低频记账和少量图片上传足够；SHA-256、文件转发和小文件读写不会持续打满 CPU。真正不适合的是图片压缩、缩略图、EXIF 重编码等 CPU/内存密集型处理，本期不做。

磁盘方面，20 GB 系统盘需要同时容纳系统、Docker 镜像、PostgreSQL 数据、日志和备份。图片长期写入会很快占满，且 MinIO 数据卷与数据库、备份争抢同一块盘会影响恢复能力。至少应增加独立数据盘（建议 100 GB ESSD）承载 PostgreSQL、备份和日志；对象存储使用 OSS 时不占 ECS 数据盘。

带宽方面，10 MB 图片在 5 Mbps 上理论上传约 16 秒，在 1 Mbps 上约 80 秒。第四期使用预签名直传，图片上传和读取不经过 ECS；ECS 只处理签名、完成确认和元数据请求。

**结论：**

1. **不建议在当前 2C2G 机器上再自建 MinIO 作为生产对象存储。** 若坚持自建，至少升级到 4 vCPU/4 GiB（更稳妥是 4C8G），并增加独立数据盘；仍需把备份放到另一块盘或 OSS。
2. **推荐使用阿里云 OSS 私有 Bucket。** ECS 不再运行对象存储进程，内存和磁盘压力显著下降；按量付费的存储和流量成本对个人账本通常较低。
3. 第四期直接使用浏览器预签名直传 OSS；NestJS 只负责签发地址、完成确认和权限校验，不中转图片二进制。上传队列限制为 2 个并发，并设置 Node 堆上限。
4. 无论选 OSS 还是 MinIO，都应增加至少 2 GB swap 作为 OOM 兜底；swap 只能降低崩溃概率，不能替代内存和容量规划。

对“实时数据”的含义需要明确：账单和附件元数据是实时业务数据，用户在账单详情中应立刻看到刚上传成功的图片；图片二进制本身不进入实时消息通道，也不参与账单金额、余额和统计计算。共享账本其他成员在看到新图片前最多需要一次刷新，不要求逐字节实时同步。

选择预签名直传是因为当前服务器资源有限：

- 文件不经过 NestJS，避免上传时叠加 Node 内存和 ECS 带宽；
- 后台仍负责账本权限、上传会话、完成确认和真实对象校验；
- MinIO/OSS 维持私有 Bucket，签名地址只在短时间内有效；
- 上传会话和 `PENDING` 状态增加了实现复杂度，但能把本地开发和线上部署保持为同一套业务流程。

使用 OSS 时，领域层通过 `ObjectStoragePort` 适配，生产使用 OSS 适配器，本地开发使用 MinIO 适配器；业务代码不直接依赖某一家厂商。

## 2. 业务约束与规模假设

### 2.1 业务约束

- 图片是账单的可选凭证，不是账单成立的必要条件；没有图片的账单仍然完整可用。
- 收入、支出账单支持图片；本期不做转账、预算、报销审批和 OCR。
- 图片只对有权查看该账单的账本成员可见；私人账户账单继续受账户可见性约束。
- 账单软删除后，其附件必须立即不可读；对象是否已物理删除不影响业务结果。
- 附件上传、读取和删除都必须经过账本成员、角色和资源归属校验，不能只靠对象地址难猜。
- 附件不能改变账单金额、账户余额、统计口径和并发版本规则。

### 2.2 规模假设

| 维度 | 本期假设 |
| --- | --- |
| 用户 | 个人、家庭、小型共同生活群体；单账本通常 1–10 人 |
| 图片量 | 单笔账单 0–5 张，单张不超过 10 MB |
| 用户配额 | 默认 2 GB，可配置；按上传者统计未删除附件 |
| 写频率 | 低频人工记账，不追求高并发上传 |
| 读频率 | 账单详情按需加载，列表只显示附件数量 |
| 部署 | 单台服务器、Docker Compose、单实例 NestJS；生产 OSS，本地 MinIO |
| 网络 | 移动端 4G/5G/Wi-Fi，存在弱网、切后台、锁屏和重复提交 |

如果未来出现大量用户、批量导入票据、多人同时上传或需要跨区域访问，再按第 12 节升级；不要在当前规模提前引入分片上传、CDN、图片处理集群或独立媒体服务。

## 3. 业内方案对比

### 3.1 常见方案

| 方案 | 典型做法 | 优点 | 主要问题 | 适用判断 |
| --- | --- | --- | --- | --- |
| 数据库二进制 | `bytea`/BLOB 存图片 | 事务简单、备份统一 | 主库和备份迅速膨胀；连接和内存压力大；恢复慢 | 不采用 |
| 应用本地磁盘 | 容器卷或服务器目录 | 实现快、无额外服务 | 容器重建/扩容/迁移丢文件；多实例不共享；备份容易漏 | 不采用 |
| 服务端代理到对象存储 | 客户端 → API → OSS/MinIO | 统一鉴权、服务端校验 | 带宽和内存经过 API；当前服务器资源紧张 | 不采用 |
| 预签名直传 | API 签发 URL → 客户端直传 OSS/MinIO | 不占 API 带宽；易扩展；支持本地和线上统一流程 | 需要 CORS、`PENDING/complete` 状态和完成校验 | **第四期采用** |
| 托管图片服务 | Cloudinary、Supabase Storage、UploadThing 等 | 上传、转码、CDN 一体化 | 费用、供应商锁定、数据出域 | 备选 |
| 云对象存储 | 阿里云 OSS、S3、R2、COS | 免运维、可扩展、生态成熟 | 费用、网络、合规和迁移 | **当前服务器推荐 OSS** |

### 3.2 预签名直传的关键细节

业内常说的“预签名直传”有两个容易混淆的变体：

1. **预签名 PUT**：API 返回一个 `PUT` URL，客户端直接上传。实现简单，但 URL 本身通常不能强制最大文件大小；服务端只能在上传后通过 `HEAD` 检查大小，恶意客户端仍可先上传超大文件。需要配合桶策略、配额和事后清理。
2. **预签名 POST Policy**：API 返回 URL 和表单字段，策略中声明 `content-length-range`、`Content-Type`、对象键前缀和过期时间。约束更强，但客户端实现和错误处理更复杂，OSS/MinIO/S3 的兼容细节需要验证。

此外还有 S3 Multipart Upload（分片上传）和 tus/tus-js-client（可恢复上传）。它们适合大文件、长视频或极弱网络，不适合 10 MB 以内的票据图片；本期不引入。

### 3.3 第四期为什么采用预签名直传

- 当前生产服务器只有 2 vCPU/约 2 GiB 内存，图片经过 NestJS 会额外占用应用内存和 ECS 带宽；直传可以把文件传输压力放到 OSS/MinIO。
- 预签名地址只在短时间内有效，Bucket 仍保持私有；客户端无法列举 Bucket，也不能自定义对象键。
- 上传完成后仍由后台校验对象存在、大小、元数据和文件头，预签名只负责授予一次短期写权限，不能绕过业务鉴权。
- 直传会增加上传会话、`PENDING` 状态和 CORS 配置，但这是第四期需要明确承担的复杂度，换来更低的服务器资源压力。
- 单张文件限制为 10 MB，第四期不引入分片上传；超过该规模后再独立评估 Multipart Upload。

结论：**第四期采用预签名直传和短期签名读取；本地使用 MinIO，线上使用阿里云 OSS。**生产与本地通过 `ObjectStoragePort` 隔离，账单业务不直接依赖具体存储 SDK。

## 4. 推荐架构

### 4.1 拓扑

```text
浏览器 / PWA
  │ 同源 HTTPS /api
  ▼
Nginx
  │
  ▼
NestJS API ────────────── PostgreSQL
  │  账单、附件元数据、审计、清理状态
  │
  └── OSS SDK / S3 接口 ── 阿里云 OSS（生产）或 MinIO（本地）
       私有 Bucket + 服务端加密/访问控制
```

文字说明：

- 浏览器通过同源 `/api` 请求签名地址，再直接访问 MinIO/OSS；对象存储管理接口不对浏览器开放。
- NestJS 负责认证、账本成员校验、账单归属校验、文件校验、对象读写和元数据事务。
- PostgreSQL 保存附件元数据和业务状态，是“这张图片是否属于这笔账单”的唯一事实源。
- OSS/MinIO 保存二进制对象，使用私有 Bucket 和随机对象键；Bucket 策略不允许匿名读。
- Nginx 只反代前端和 `/api`，不反代 OSS 或 MinIO 控制台/数据端口。

### 4.2 一次上传的时序

```text
1. 客户端创建/编辑账单，先拿到 transactionId
2. 客户端为每张图片生成 clientRequestId
3. POST /api/ledgers/:ledgerId/transactions/:transactionId/attachment-uploads
   body: clientRequestId + declaredMimeType + declaredSizeBytes
4. NestJS 校验登录、账本成员、角色、账单存在且未删除
5. 按 [transactionId, clientRequestId] 查询；命中 PENDING/ATTACHED 时返回已有上传会话或附件
6. 检查单笔数量、用户配额和声明的大小/类型，创建 PENDING 附件和短期上传策略
7. 前端直接 PUT 文件到 MinIO/OSS，不经过 NestJS
8. POST /api/ledgers/:ledgerId/attachments/:attachmentId/complete
9. NestJS 对对象执行 HEAD，并读取文件头确认大小、类型和对象存在
10. 校验通过后将 PENDING 更新为 ATTACHED 并写审计；失败保持不可读，允许重试，过期后由清理任务改为 DELETED
11. 返回附件摘要和短期读取地址
```

关键顺序是“先创建 PENDING 元数据、再直传、最后完成确认”：只有完成接口校验通过后，数据库才出现可读附件。客户端中断上传时保留短期 PENDING 记录，由过期清理任务删除对象并改为 `DELETED`，不影响账单本身。

### 4.3 一次读取的时序

```text
1. GET /api/ledgers/:ledgerId/attachments/:attachmentId/access-url
2. NestJS 校验登录、账本成员、账单未删除、附件未删除
3. 如账单关联私人账户，校验当前用户是账户所有者
4. 返回 5 分钟有效的签名 GET URL，不返回 objectKey
5. 浏览器按签名地址从 MinIO/OSS 读取图片
6. URL 过期、权限变化或对象不存在时，前端重新申请或显示失败状态
```

读取不返回永久公开地址，也不把对象存储的内部对象键暴露给客户端。签名 URL 过期后必须重新经过 NestJS 鉴权，成员被移除后不再签发新的读取地址；已经签发的地址最多在有效期内可用。

## 5. 数据模型

### 5.1 Prisma 模型

```prisma
enum TransactionAttachmentStatus {
  PENDING
  ATTACHED
  DELETED
}

model TransactionAttachment {
  id              String                     @id @default(uuid())
  ledgerId        String                     @map("ledger_id")
  transactionId   String                     @map("transaction_id")
  uploadedById    String                     @map("uploaded_by_id")
  clientRequestId String                     @map("client_request_id")
  objectKey       String                     @unique @map("object_key")
  originalName    String?                    @map("original_name")
  declaredMimeType String?                  @map("declared_mime_type")
  declaredSizeBytes Int?                    @map("declared_size_bytes")
  mimeType        String?                    @map("mime_type")
  sizeBytes       Int?                       @map("size_bytes")
  checksumSha256  String?                    @map("checksum_sha256")
  width           Int?
  height          Int?
  status          TransactionAttachmentStatus @default(PENDING)
  uploadExpiresAt DateTime?                  @map("upload_expires_at")
  uploadedAt      DateTime?                  @map("uploaded_at")
  deletedAt       DateTime?                  @map("deleted_at")
  purgedAt        DateTime?                  @map("purged_at")
  purgeAttempts   Int                        @default(0) @map("purge_attempts")
  lastPurgeError  String?                    @map("last_purge_error")
  lastUploadError String?                    @map("last_upload_error")
  ledger          Ledger                     @relation(fields: [ledgerId], references: [id], onDelete: Cascade)
  transaction     Transaction                @relation(fields: [transactionId], references: [id], onDelete: Cascade)
  uploadedBy      User                       @relation(fields: [uploadedById], references: [id], onDelete: Restrict)
  createdAt       DateTime                   @default(now()) @map("created_at")
  updatedAt       DateTime                   @updatedAt @map("updated_at")

  @@unique([transactionId, clientRequestId])
  @@index([ledgerId, transactionId, status])
  @@index([status, createdAt])
  @@index([deletedAt, purgedAt])
  @@index([uploadedById, createdAt])
  @@map("transaction_attachment")
}
```

### 5.2 字段与约束说明

| 字段 | 说明 |
| --- | --- |
| `transactionId` | 必填。附件必须属于已保存账单，不引入草稿账单或独立草稿附件 |
| `clientRequestId` | 单张图片的幂等键，由客户端生成 UUID；同一账单内唯一 |
| `objectKey` | 服务端生成，格式 `ledgers/{ledgerId}/attachments/{attachmentId}.{ext}`；客户端不可指定 |
| `declaredMimeType`/`declaredSizeBytes` | 客户端申请上传时的声明，只用于生成策略和初步校验，不能作为最终事实 |
| `mimeType` | 完成确认时服务端检测出的真实类型，不是客户端声明的 `Content-Type` |
| `sizeBytes` | 完成确认时从对象存储 `HEAD` 读取的实际字节数 |
| `checksumSha256` | 可选的服务端完整性校验值，不返回给普通客户端 |
| `width`/`height` | 可选；能读取图片尺寸时保存，不能读取时为 `null` |
| `status` | `PENDING` 等待直传确认；`ATTACHED` 可读；`DELETED` 业务上不可读，等待对象清理 |
| `uploadExpiresAt` | 上传策略失效时间；过期的 `PENDING` 记录不能完成确认 |
| `uploadedAt` | 对象直传成功并完成后台确认的时间 |
| `deletedAt` | 业务删除时间；读取地址接口和详情查询立即过滤 |
| `purgedAt` | 对象实际删除成功时间；为空表示仍在清理队列 |
| `purgeAttempts`/`lastPurgeError` | 清理重试次数和最近错误，便于排障 |
| `lastUploadError` | 最近一次完成确认失败原因，仅供后台排障，不返回给客户端 |

### 5.3 索引设计

- `[transactionId, clientRequestId]` 唯一：保证同一张图片重试不会产生重复附件。
- `[ledgerId, transactionId, status]`：账单详情、附件列表和数量统计。
- `[status, createdAt]`：过期 PENDING 和已删除附件清理任务按状态和时间扫描。
- `[deletedAt, purgedAt]`：查找待清理的已删除附件。
- `[uploadedById, createdAt]`：用户配额汇总和审计查询。

### 5.4 与账单的关系

- `Transaction` 增加 `attachments TransactionAttachment[]`；账单软删除不物理删除附件行。
- 账单详情返回 `attachments` 数组；账单列表返回 `attachmentCount`，不返回每张图片内容。
- `PENDING` 附件不计入 `attachmentCount`，不出现在账单详情的可读附件数组中。
- 账单软删除时，在同一数据库事务中把该账单所有 `PENDING`/`ATTACHED` 附件改为 `DELETED` 并写 `deletedAt`。
- 账本永久删除只允许空账本，因此正常不会出现“有附件的账本被硬删除”；数据库仍使用级联外键兜底。

## 6. 接口设计

### 6.1 接口总览

| 方法 | 路径 | 权限 | 用途 |
| --- | --- | --- | --- |
| `POST` | `/api/ledgers/:ledgerId/transactions/:transactionId/attachment-uploads` | `OWNER/EDITOR` | 创建附件上传会话并返回短期上传地址 |
| `POST` | `/api/ledgers/:ledgerId/attachments/:attachmentId/complete` | `OWNER/EDITOR` | 校验对象并完成附件绑定 |
| `GET` | `/api/ledgers/:ledgerId/attachments/:attachmentId/access-url` | 可查看账单的活跃成员 | 返回短期读取地址 |
| `DELETE` | `/api/ledgers/:ledgerId/transactions/:transactionId/attachments/:attachmentId` | `OWNER/EDITOR` | 移除附件 |
| `GET` | `/api/ledgers/:ledgerId/transactions/:transactionId` | `VIEWER+` | 详情包含附件摘要 |
| `GET` | `/api/ledgers/:ledgerId/transactions` | `VIEWER+` | 列表包含 `attachmentCount` |

前端不能直接调用对象存储管理 API，必须先通过 NestJS 创建上传会话；上传地址、读取地址均为短期凭证。

### 6.2 创建上传会话

#### 请求

```http
POST /api/ledgers/ledger-uuid/transactions/transaction-uuid/attachment-uploads
Content-Type: application/json

{
  "clientRequestId": "7b0d3c2e-...",
  "fileName": "receipt.jpg",
  "mimeType": "image/jpeg",
  "sizeBytes": 248321
}
```

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `clientRequestId` | string | 是 | UUID；同一账单内唯一 |
| `fileName` | string | 是 | 仅用于展示和扩展名推断；服务端清洗 |
| `mimeType` | string | 是 | 仅为客户端声明；JPEG/PNG/WebP；服务端完成时复核 |
| `sizeBytes` | integer | 是 | 大于 0 且不超过 10 MB；服务端完成时复核 |

#### 成功响应 `201`

```json
{
  "attachmentId": "attachment-uuid",
  "status": "PENDING",
  "uploadMethod": "PUT",
  "uploadUrl": "https://storage.example.com/signed-upload-url",
  "requiredHeaders": {
    "Content-Type": "image/jpeg"
  },
  "expiresAt": "2026-11-09T12:41:00.000Z"
}
```

`uploadUrl` 仅用于当前对象和短时间内的一次上传；前端不能修改对象键、Bucket、签名参数或使用该地址读取其他对象。

### 6.3 完成上传

前端对象上传成功后调用：

```http
POST /api/ledgers/ledger-uuid/attachments/attachment-uuid/complete
```

后台必须执行：

1. 重新校验当前用户对账单的写权限和附件归属。
2. 校验 `PENDING` 状态未过期；已 `ATTACHED` 时返回原附件，保证完成接口幂等。
3. 对对象执行 `HEAD`，确认对象存在、实际大小不超过 10 MB。
4. 读取对象头魔数，确认真实类型为 JPEG、PNG 或 WebP；不能只相信 `Content-Type`。
5. 将实际 `mimeType`、`sizeBytes`、校验值和 `uploadedAt` 写入数据库，状态更新为 `ATTACHED`。
6. 返回附件摘要和短期读取地址。

完成确认失败时，附件不能进入可读状态；前端显示失败并允许重试或重新创建上传会话。过期 PENDING 记录由清理任务删除并改为 `DELETED`。

#### 完成响应 `200`

```json
{
  "id": "attachment-uuid",
  "status": "ATTACHED",
  "transactionId": "transaction-uuid",
  "mimeType": "image/jpeg",
  "sizeBytes": 248321,
  "originalName": "receipt.jpg",
  "accessUrl": "https://storage.example.com/signed-read-url",
  "accessUrlExpiresAt": "2026-11-09T12:36:00.000Z",
  "createdAt": "2026-11-08T12:31:00.000Z",
  "attachmentCount": 2
}
```

#### 幂等与并发

- 同一 `clientRequestId` 的重复请求返回第一次创建的附件，不重复计数、不重复写审计。
- 两个并发请求使用同一 `clientRequestId` 时，数据库唯一约束是最终保护；后到者返回已有 PENDING/ATTACHED 记录，不重复创建。
- 两个并发请求使用不同 `clientRequestId` 且账单已有 4 张时，创建上传会话必须锁定账单行并统计 `PENDING + ATTACHED`，最多创建一个新的会话。
- 未完成上传的 PENDING 记录不进入账单详情；完成确认成功后，账单详情下一次查询包含该附件。
- 已过期或已删除的 PENDING 会话不能再次完成确认；客户端重试时必须生成新的 `clientRequestId`。
- 共享账本其他成员在下一次刷新后可见，不做实时推送。

#### 错误码

| HTTP | code | 场景 |
| --- | --- | --- |
| `400` | `40041` | 文件、类型、大小、文件名或 `clientRequestId` 非法 |
| `403` | `40341` | `VIEWER`、非成员或无权编辑该账单 |
| `404` | `40441` | 账单、账本或附件不可见 |
| `409` | `40941` | 附件数量超限或状态冲突 |
| `409` | `40942` | 用户附件配额不足 |
| `413` | `41301` | 文件超过大小限制 |
| `415` | `41501` | 不支持的图片类型 |
| `429` | `42901` | 上传频率超过限制 |
| `503` | `50341` | 对象存储不可用或附件功能关闭 |

### 6.4 读取附件地址

```http
GET /api/ledgers/ledger-uuid/attachments/attachment-uuid/access-url
```

- 需要登录；只有能查看该账单的活跃成员可以读取。
- 账单已软删除、附件不是 `ATTACHED`、成员失效、跨账本、私人账户不可见时返回 `40441`。
- 返回 5 分钟有效的签名 GET URL，不返回永久公开 URL、Bucket 名称或 `objectKey`。
- 浏览器使用 `accessUrl` 直接从 MinIO/OSS 读取图片；地址过期后重新调用本接口。
- 对象不存在或对象存储不可用返回 `40441`/`50341`，不能返回空 `200` 或损坏占位图冒充成功。

### 6.5 删除附件

```http
DELETE /api/ledgers/ledger-uuid/transactions/transaction-uuid/attachments/attachment-uuid
```

- 成功返回 `data: null`。
- 当前用户必须是账本 `OWNER` 或 `EDITOR`，账单未删除。
- 附件必须属于该账单和账本；重复删除同一附件返回 `200` 幂等结果。
- 在同一事务中把附件改为 `DELETED`、写 `deletedAt`、写审计；提交后异步删除对象。
- 附件删除不要求 `Transaction.version`，也不递增账单版本；账单字段编辑仍使用原版本控制。
- 账单软删除时，同一事务中把其所有有效附件标记为 `DELETED`，读取地址接口立即停止签发。

### 6.6 账单详情和列表

详情响应中的附件摘要：

```json
{
  "attachments": [
    {
      "id": "attachment-uuid",
      "mimeType": "image/jpeg",
      "sizeBytes": 248321,
      "originalName": "receipt.jpg",
      "accessUrl": "https://storage.example.com/signed-read-url",
      "accessUrlExpiresAt": "2026-11-09T12:36:00.000Z",
      "createdAt": "2026-11-08T12:31:00.000Z"
    }
  ]
}
```

列表项只返回 `attachmentCount`，避免一次加载全部附件元数据。附件按 `createdAt` 升序，首张可作为列表缩略图；不返回 `objectKey`、桶名、校验值或上传者敏感信息。

## 7. 一致性、幂等与故障处理

### 7.1 没有分布式事务

对象存储和 PostgreSQL 不能共享事务。设计原则：

- 数据库先创建 `PENDING` 上传会话，再由客户端直传对象；后台完成确认成功后才允许读取。
- `PENDING` 不是可读附件；对象上传成功但没有完成确认时，由过期清理任务删除并改为 `DELETED`。
- 完成确认时如果数据库更新失败，对象仍保持不可读，后续对账任务和 PENDING 清理任务负责处理。
- 数据库写入成功后对象读取失败属于存储故障，返回明确错误；不能把账单或附件记录删除来“掩盖”故障。
- 对象删除失败不影响业务删除；数据库状态 `DELETED` 是权威，对象由清理任务重试。
- 备份恢复后运行对账脚本，检查 `ATTACHED` 附件是否存在对象；只报告差异，不自动改业务数据。

### 7.2 幂等表

| 场景 | 幂等键 | 结果 |
| --- | --- | --- |
| 同一张图片重试 | `[transactionId, clientRequestId]` | 返回已有上传会话或已完成附件 |
| 重复删除附件 | `attachmentId` + 状态 | 返回 `200`，不重复清理 |
| 账单重复创建 | `[ledgerId, clientRequestId]` | 返回已存在账单，不重复绑定附件 |
| 清理任务重跑 | `purgedAt IS NULL` + 状态 | 已清理的记录不会再次删除 |

### 7.3 并发场景

| 场景 | 处理 |
| --- | --- |
| 同一账单并发上传第 5、6 张 | 锁定账单行，统计数量；只有一个成功，另一个 `40941` |
| 同一 `clientRequestId` 并发创建会话 | 唯一约束兜底；后到者返回已有上传会话 |
| 上传与账单软删除并发 | 上传事务锁定账单并检查 `deletedAt`；账单先删除则上传失败 |
| 删除与签名读取并发 | 签名接口先校验数据库状态；删除提交后不再签发新地址，已签发地址最多存活至过期 |
| 配额并发 | 默认软限制；严格配额需用户级锁或计数表 |
| 清理与恢复 | 清理处理过期 `PENDING` 和 `DELETED` 记录；恢复后的对账不自动删除对象 |

### 7.4 对象存储故障

- 创建上传会话时对象存储不可用：返回 `50341`，不创建会话；客户端保留本地文件并重试。
- 完成确认或读取签名地址时对象存储不可用：返回 `50341`，前端显示失败和重试，不把失败当成功。
- 删除时对象存储不可用：业务删除成功，对象进入清理队列；前端不再显示附件。
- 清理任务失败：记录 `purgeAttempts` 和 `lastPurgeError`，下一轮重试；超过阈值告警，不阻塞业务。

## 8. 安全与隐私

### 8.1 存储安全

- 桶私有，禁止匿名读和 public-read ACL。
- MinIO 本地部署时不暴露公网端口；生产 OSS 使用私有 Bucket 和最小权限 RAM 用户。
- 应用使用最小权限账号，只允许目标桶的 `GetObject`、`PutObject`、`DeleteObject` 和必要的 `HeadObject`；根账号只用于初始化和管理。
- 上传和读取地址由后台签发，上传地址默认 10 分钟有效，读取地址默认 5 分钟有效；地址中不包含可复用的长期凭据。
- 对象键由服务端生成，包含账本 ID 和随机附件 ID；客户端不能指定路径、覆盖已有对象或列举桶。
- 对象存储的访问密钥只通过环境变量注入，不写入代码、镜像、日志或文档。

### 8.2 内容安全

- 不信任客户端 `Content-Type` 和扩展名；读取文件头魔数确认 JPEG/PNG/WebP。
- 拒绝 SVG、HTML、脚本、压缩包和可执行文件；SVG 即使声明为图片也不接受。
- 文件名只用于展示和下载，去除路径分隔符、控制字符和过长名称。
- 设置 `X-Content-Type-Options: nosniff`，避免浏览器把图片当其他类型执行。
- 本期不做病毒扫描；只接受图片类型、限制大小、私有访问，风险由个人部署场景接受。若开放给不可信用户，需增加恶意文件扫描和图片解码沙箱。
- 图片可能在客户端被压缩或转码；服务端仍以实际收到的字节为准。

### 8.3 隐私

- 票据可能包含姓名、卡号后四位、地址、位置等敏感信息；默认私有，不生成公开链接。
- 本期保存原图字节，不主动移除 EXIF；手机照片可能包含 GPS 和设备信息。若隐私要求提高，增加服务端 `sharp` 处理：自动旋转、移除 EXIF、限制长边、重新编码；这会改变原图，需要单独评审。
- 日志不记录图片内容、对象键、签名 URL、存储密钥；错误日志只记录附件 ID、账本 ID、错误码和请求 ID。
- 审计记录附件 ID、媒体类型、大小和操作人，不记录图片内容。
- 备份文件和对象存储数据同样受访问控制，不能放在公开目录。

### 8.4 访问控制

- 上传：账本活跃成员 + `OWNER/EDITOR` + 账单未删除。
- 读取地址：账本活跃成员 + 账单可见（含私人账户规则）+ 附件状态为 `ATTACHED`。
- 删除：账本活跃成员 + `OWNER/EDITOR` + 附件属于该账单。
- 不把 `attachmentId` 当作授权凭据；每次请求都重新校验账本、账单和附件归属。
- 共享账本成员被移除或退出后，后台不再签发新的 `accessUrl`；已签发地址最多存活至过期。

### 8.5 限流与配额

| 接口 | 建议限制 |
| --- | --- |
| 上传 | 每用户每分钟 20 次、每小时 100 次 |
| 读取 | 每用户每分钟 300 次 |
| 删除 | 每用户每分钟 60 次 |
| 单用户总量 | 默认 2 GB，可配置 |
| 单笔数量 | 最多 5 张 |
| 单张大小 | 最多 10 MB |

超过限制返回 `42901` 或 `40942`；不能通过并发请求绕过单笔 5 张限制。

## 9. 性能与容量

### 9.1 上传路径

- NestJS 只接收上传会话和完成确认请求，不接收图片二进制；不需要为附件增加 `client_max_body_size`。
- 前端直传 MinIO/OSS，单张上限 10 MB；后台在创建会话时检查声明大小，在完成确认时通过 `HEAD` 再次检查实际大小。
- 上传队列最多 2 张并发，避免移动端同时创建过多会话和请求。
- 上传接口不经过图片压缩；客户端可选压缩，但票据可读性优先。
- 完成确认阶段读取对象头和必要元数据，不能把对象完整下载到 NestJS 内存。

### 9.2 读取路径

- 图片读取使用短期签名地址直达 MinIO/OSS，不经过 NestJS 流式转发。
- 签名地址默认 5 分钟有效，减少重复鉴权请求；删除或权限变更后不再签发新地址。
- 列表不加载图片内容，只返回 `attachmentCount`；详情按需加载。
- 未来读流量增大时可加 CDN 或更细粒度的短时签名策略，但必须保证删除和权限撤销语义。

### 9.3 容量估算

| 项目 | 估算 |
| --- | --- |
| 单张平均 | 2–5 MB（手机原图），上限 10 MB |
| 单账单 | 0–5 张，平均 1–2 张 |
| 1000 笔带图账单 | 约 2–10 GB |
| 单用户 2 GB 配额 | 约 400–1000 张平均大小图片 |
| 备份 | 至少与主存储同等容量，保留周期另计 |

上线前确认服务器磁盘、备份盘和监控阈值；磁盘使用率达到 80% 时告警，不能等写满后才发现。

## 10. PWA、移动端与弱网

### 10.1 上传顺序

采用“先建账单、后传附件”：

1. 用户填写账单并保存，先获得 `transactionId`。
2. 账单保存成功后，按队列上传图片，最多 2 张并发。
3. 每张图片有独立 `clientRequestId`，失败只重试该张。
4. 全部成功或部分失败都要明确展示；账单本身已经保存，不能因为图片失败而回滚账单。
5. 用户关闭抽屉后，队列可在详情页继续重试；失败图片不得显示为已保存。

这与前端设计一致，也避免附件草稿和账单草稿的双重生命周期。

### 10.2 离线与后台

- 离线时账单可以进入现有离线同步队列；图片文件保存在 IndexedDB 的待上传队列，联网后上传。
- iOS PWA 不保证 Background Sync；不能承诺关闭应用后仍自动上传。应用回到前台、恢复网络或用户手动重试时继续。
- 本地预览使用 `URL.createObjectURL`，移除或上传成功后 `revokeObjectURL`。
- 清理浏览器数据、卸载 PWA 或更换设备会丢失未上传图片；界面必须提示，不把本地队列当永久存储。
- 账单在服务端已被删除时，待上传图片按 `40441` 处理并清理本地队列。

### 10.3 图片格式与 HEIC

- 服务端只接受 JPEG、PNG、WebP。
- iOS 相册可能提供 HEIC/HEIF；如果浏览器上传的是 HEIC，服务端返回 `41501`，前端提示“请选择 JPEG/PNG/WebP 或先在系统相册转换”。
- 不在本期引入 HEIC 解码依赖；若后续大量用户受影响，再评估服务端 `sharp`/`libheif` 转码。
- 相机拍摄建议使用 `accept="image/*"`，并在客户端展示格式和大小提示。

## 11. 部署与运维

### 11.1 生产：阿里云 OSS

当前 2C2G ECS 不建议再运行 MinIO。生产使用阿里云 OSS：

- 创建私有 Bucket，开启服务端加密；Bucket 不开放匿名读，不使用 public-read ACL。
- 后端通过 RAM 角色（推荐）或最小权限 RAM 用户的 AccessKey 访问；不要把长期 AccessKey 写入前端、镜像或仓库。
- 后台签名使用与 Bucket 匹配的 OSS Endpoint；前端直传使用公网可达的 OSS Endpoint，不能使用仅 ECS 可访问的内网地址。
- OSS 负责持久化、冗余和文件传输；ECS 不再为对象存储保留数据盘，也不承担图片上传和下载带宽。
- OSS Bucket 必须配置 CORS，只允许生产前端域名和本地开发域名，允许 `PUT`、`GET`、`HEAD`，暴露 `ETag`、`Content-Length` 等完成确认所需响应头；不允许 `*` 来源。
- 生产 Nginx 只反代前端和 `/api`，不反代 OSS。
- 本地开发和测试使用 MinIO，通过 `ObjectStoragePort` 的 MinIO 适配器；生产使用 OSS 适配器，业务代码不直接依赖 SDK。

#### 11.1.1 控制台准备步骤

按顺序做完，缺一项上传都会失败：

1. **建 Bucket**：地域与 ECS 同地域（当前示例为 `oss-cn-shenzhen`）；读写权限设为**私有**；开启服务端加密；不开静态网站托管。
2. **建 RAM 用户**（不要用主账号 AK）：只授予该 Bucket 的对象读写删权限，策略如下，把 `<bucket>` 换成实际名称：

   ```json
   {
     "Version": "1",
     "Statement": [
       {
         "Effect": "Allow",
         "Action": ["oss:PutObject", "oss:GetObject", "oss:HeadObject", "oss:DeleteObject"],
         "Resource": ["acs:oss:*:*:<bucket>/*"]
       }
     ]
   }
   ```

   不需要 `oss:ListBuckets`、`oss:PutBucketCors` 之外的桶级权限；能用 RAM 角色（ECS 实例角色）时优先用角色，避免把长期 AK 写进 `production.env`。
3. **确认两个 Endpoint**：签名给浏览器用公网地址（`https://oss-cn-shenzhen.aliyuncs.com`），服务端操作走内网地址（`https://oss-cn-shenzhen-internal.aliyuncs.com`）以省流量费；内网 Endpoint 浏览器不可达，不能填到 `OSS_ENDPOINT`。
4. **配置 CORS（必须手动做）**：`backend/src/modules/attachment/object-storage/aliyun-oss-object-storage.ts` 里虽然有 `ensureCors()`，但**当前生产代码没有任何地方调用它**，因此必须去 OSS 控制台 → 该 Bucket → 数据安全 → 跨域设置，新增规则：

   | 项 | 值 |
   | --- | --- |
   | 来源 | `https://jizhang.xiaobao.work`（本地联调再加 `http://localhost:8090`），不要填 `*` |
   | 方法 | `GET`、`PUT`、`HEAD` |
   | 允许 Headers | `*`（浏览器直传会带 `Content-Type`） |
   | 暴露 Headers | `ETag`、`Content-Length`、`Content-Type` |
   | 缓存时间 | `3000` 秒 |

   `ETag` 必须暴露，否则 `complete` 阶段拿不到对象校验值；缺 CORS 时浏览器直传会在预检阶段失败，前端看到的是网络错误而不是 `40401`。
5. **生命周期（可选）**：给 `attachments/` 前缀配置「碎片过期 7 天」，避免中断的分片上传长期占空间；**不要**对 `attachments/` 配自动删除，删除由后端清理任务负责。

本地 MinIO 仅用于开发和集成测试，不部署到生产服务器：

```text
services:
  minio:
    image: minio/minio:<pinned-version>
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: ...
      MINIO_ROOT_PASSWORD: ...
    volumes:
      - minio_data:/data
    networks:
      - internal
    ports:
      - "127.0.0.1:9000:9000"
```

### 11.2 2C2G 资源限制

如果继续使用当前 2 vCPU/2 GiB 机器，至少做以下限制，否则 OOM 风险很高：

| 项 | 建议 |
| --- | --- |
| Node 堆上限 | Next.js、NestJS 分别设置 `--max-old-space-size=384` |
| PostgreSQL | `shared_buffers=128MB`、`max_connections` 控制在 50 以内、`work_mem=4MB` |
| Redis | `maxmemory 64mb`，使用 `allkeys-lru` 或明确淘汰策略 |
| 上传并发 | `ATTACHMENT_MAX_CONCURRENT_UPLOADS=2`，避免多个 10 MB 缓冲叠加 |
| Swap | 增加 2 GB swap 作为兜底，监控 swap in/out；不能替代扩容 |
| Docker | 给 backend/frontend/db/redis 设置内存上限，避免单容器拖垮整机 |
| 日志 | 限制 Docker 日志大小和保留数量，避免 20 GB 系统盘被日志占满 |
| 数据盘 | 建议增加 100 GB ESSD 承载 PostgreSQL、备份和日志；OSS 承载图片 |

如果出现持续 swap、OOM kill、上传超时或构建/部署期间服务不可用，应优先升级到 4 GiB 内存，而不是继续调小缓存。

### 11.4 备份与恢复

- PostgreSQL 和对象存储必须一起备份；只备份数据库会留下不可读附件。
- OSS 生产环境推荐开启 Bucket 版本控制或使用独立备份 Bucket + `ossutil sync`；明确“删除是否传播到备份”和保留周期。需要保留已删除图片时，备份 Bucket 单独设置生命周期，不能把备份 Bucket 设为公开。
- 本地 MinIO 使用 `mc mirror` 到独立备份盘或远端；不要只依赖开发机单节点磁盘。
- 推荐每日数据库 dump + 对象存储同步；保留 14 个日备份、4 个周备份。
- 备份前记录时间点；恢复时使用同一时间点的数据库和对象备份。
- 恢复顺序：PostgreSQL → 对象存储 → 对账脚本 → 应用健康检查。
- 对账脚本检查每个 `ATTACHED` 附件的对象是否存在，输出缺失清单；不自动删除数据库记录，也不自动删除对象。
- 开放上传前必须完成一次恢复演练，记录 RPO/RTO、缺失对象数和恢复步骤。
- 备份文件加密或放在受控目录，不提交 Git，不放入公开静态目录。

### 11.5 监控

至少监控：

- 上传成功/失败数、平均耗时、413/415/503/429 数量；
- OSS 存储量、请求错误率、下行流量、请求包消耗和费用；本地 MinIO 时监控磁盘和对象数；
- 清理队列长度、`purgeAttempts` 异常增长；
- 数据库附件表大小和慢查询；
- 备份最近成功时间和恢复演练记录。

## 12. 演进路线

### 12.1 阶段一：预签名直传（本期）

- 单张 ≤10 MB、低并发、私有 OSS 或本地 MinIO、后台签发上传和读取地址。
- 适合当前 2C2G 服务器，避免 NestJS 中转图片二进制。

### 12.2 阶段二：图片处理与缩略图

- 引入 `sharp` 做自动旋转、EXIF 清理、长边限制和缩略图。
- 详情页加载缩略图，点击查看原图；减少移动端流量。
- 需要评估 CPU、内存和原图保留策略，不阻塞本期上线。

### 12.3 阶段三：可恢复上传

触发条件（满足其一即可评估）：

- 单日上传图片超过 1000 张，或峰值并发上传超过 10；
- 单张上限提高到 20 MB 以上；
- API 带宽或内存成为瓶颈；
- 多实例部署，需要统一上传会话和对象存储签名配置。

演进接口（不改变现有附件领域模型）：

```http
POST /api/ledgers/:ledgerId/transactions/:transactionId/attachment-uploads
→ {
  "attachmentId": "...",
  "mode": "PRESIGNED_POST",
  "uploadUrl": "...",
  "fields": { "key": "...", "Content-Type": "...", "x-amz-..." },
  "expiresAt": "..."
}

POST /api/ledgers/:ledgerId/attachments/:attachmentId/complete
→ 校验对象存在、大小和类型，状态 PENDING → ATTACHED
```

届时增加分片/断点续传、上传会话续期和更细粒度的清理策略；前端通过 `AttachmentTransport` 适配层演进，不改账单页面。

### 12.4 阶段四：读取加速

- 读流量大时使用短时签名 URL + CDN；
- 仍需保证删除、权限撤销和私有性；
- 不在本期引入公开 CDN 或永久 URL。

## 13. 测试与验收

### 13.1 单元与接口测试

- 上传会话：类型、大小、文件名清洗、`clientRequestId` 格式、签名过期。
- 完成确认：对象不存在、大小不符、魔数不符、PENDING 过期、重复完成。
- 幂等：同一 `clientRequestId` 重复创建返回同一会话或附件；并发重复只创建一个。
- 数量：第 5 张成功、第 6 张 `40941`；并发第 5/6 张只创建一个会话。
- 权限：`VIEWER`、非成员、跨账本、已删除账单、私人账户不可见。
- 删除：重复删除幂等、账单软删除级联标记、权限失效后不再签发读取地址。
- 读取地址：成员权限、短期有效期、对象不存在/存储不可用错误。
- 清理：`purgedAt`、`purgeAttempts`、失败重试、已清理记录不重复删除。
- 配额：超配额 `40942`；并发配额为软限制的行为。
- 时间与账单：附件上传不改变账单 `version`、余额和统计。

- 验证桶私有策略：匿名 GET 被拒绝，越权对象键不可列举。
- 验证数据库与对象存储联合恢复：恢复后有效附件可读，缺失对象被对账报告。

## 14. 风险与未决问题

1. 单用户 2 GB 配额、单笔 5 张、单张 10 MB 是建议值，需结合实际磁盘和备份成本确认。
2. 备份位置、保留周期、RPO/RTO 尚未最终确定；未完成恢复演练前附件功能保持关闭。
3. 本期存储原图，不清理 EXIF；票据可能包含位置等隐私信息。是否启用 `sharp` 自动旋转/去元数据/缩略图待评审。
4. HEIC 不在支持范围；iOS 相册若上传 HEIC 会返回 `41501`，是否需要服务端转码待评估。
5. 预签名直传的 CORS、签名过期、完成确认和 PENDING 清理需要在实现前完成集成验证。
6. MinIO 与 OSS 的签名参数、ETag 和 HEAD 元数据存在兼容差异，适配器测试必须分别覆盖。
7. 本期不做病毒扫描和图片内容审核；只面向可信的家庭/个人用户。若开放注册或公开分享，需要重新评估。
8. 读取地址默认有效 5 分钟，已签发地址在过期前可能继续可用；隐私要求更高时缩短有效期。
9. 本地 MinIO 仅用于开发和集成测试；其版本、许可和升级策略需要固定在开发环境，生产不在当前 ECS 上运行 MinIO。
10. 图片宽度/高度为可选元数据；本期不引入图片解码库，读取不到时为 `null`。

## 15. 决策摘要

| 决策 | 结论 |
| --- | --- |
| 存储介质 | 生产阿里云 OSS 标准本地冗余私有 Bucket；本地开发和集成测试用 MinIO |
| 元数据 | PostgreSQL `TransactionAttachment`，不存二进制 |
| 上传方式 | 先建账单，再创建 `PENDING` 会话；前端预签名直传，后台完成确认 |
| 幂等 | 每张图片 `clientRequestId`，同一账单唯一 |
| 读取 | 鉴权后签发 5 分钟短期 `accessUrl`，私有桶 |
| 删除 | 数据库软删除 + 对象异步清理 + 重试 |
| 数量/大小 | 5 张/账单，10 MB/张，2 GB/用户（建议值） |
| 备份 | 数据库与 OSS 联合备份、恢复演练 |
| 预签名 | 第四期采用；上传地址 10 分钟，读取地址 5 分钟 |
| 图片处理 | 本期不压缩、不转码、不清理 EXIF；后续评估 |
