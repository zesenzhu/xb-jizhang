# 账单图片附件与对象存储设计

> **本期不实施。** 本文是图片附件与对象存储的后续专项设计，已移出三期范围；当前不新增附件表、上传接口、对象存储部署和备份任务。重新立项时需按最新服务器容量、存储选型和需求重新评审，不能直接作为本期实现依据。
>
> 本文正文中的“本期”指该专项重新立项后的实施期，不代表当前三期范围。

## 1. 结论先行

本期采用“对象存储保存文件 + PostgreSQL 保存元数据 + NestJS 代理上传/读取”的方案：

| 决策 | 结论 |
| --- | --- |
| 存储 | 生产优先阿里云 OSS 私有 Bucket；本地开发和自托管备选 MinIO |
| 桶 | 私有，不开放匿名读，不直接暴露公网 |
| 上传 | 先保存账单，再通过 `POST /api/ledgers/:ledgerId/transactions/:transactionId/attachments` 上传单张图片 |
| 上传方式 | NestJS 代理上传：`multipart/form-data` → 服务端校验 → 对象存储 |
| 读取 | NestJS 鉴权后代读：`GET /api/ledgers/:ledgerId/attachments/:attachmentId/content` |
| 幂等 | 每张图片一个 `clientRequestId`，在同一账单内唯一 |
| 数量 | 单笔账单最多 5 张；单张不超过 10 MB；JPEG/PNG/WebP |
| 删除 | 数据库先标记 `DELETED`，对象异步清理，失败可重试 |
| 备份 | PostgreSQL 与对象存储必须同一套备份、恢复和演练 |
| 演进 | 保留上传会话抽象，图片量或带宽达到阈值后再切换预签名直传/直读 |

### 1.1 当前服务器评估

当前生产服务器为阿里云 `ecs.e-c1m1.large`：2 vCPU、2 GiB 内存、Alibaba Cloud Linux 3、20 GB 系统盘。这个配置对“记账 API + PostgreSQL + Redis + Nginx + Next.js”已经偏紧，再在同一台机器上跑 MinIO 会明显增加 OOM 和磁盘不足风险。

按 Docker 单机部署估算：

| 组件 | 常驻内存估算 |
| --- | --- |
| 操作系统、Docker、日志与监控代理 | 300–500 MB |
| Nginx | 30–60 MB |
| Next.js 运行时 | 200–350 MB |
| NestJS 运行时 | 150–300 MB |
| PostgreSQL（`shared_buffers` 128 MB 左右） | 150–300 MB |
| Redis | 30–60 MB |
| MinIO（空闲到小文件读写） | 100–250 MB |
| 预留余量 | 200–400 MB |

不含 MinIO 时约 0.9–1.6 GB；加上 MinIO 约 1.0–1.8 GB。2 GiB 在正常低峰可能勉强运行，但以下场景很容易触发 OOM 或明显变慢：

- 同时上传多张 10 MB 图片，NestJS 内存缓冲叠加；
- `docker load` 新镜像、应用启动和 PostgreSQL 检查点同时发生；
- MinIO 与 PostgreSQL 争抢页缓存；
- 备份、日志轮转或系统更新占用内存和磁盘。

CPU 方面，2 vCPU 对低频记账和少量图片上传足够；SHA-256、文件转发和小文件读写不会持续打满 CPU。真正不适合的是图片压缩、缩略图、EXIF 重编码等 CPU/内存密集型处理，本期不做。

磁盘方面，20 GB 系统盘需要同时容纳系统、Docker 镜像、PostgreSQL 数据、日志和备份。图片长期写入会很快占满，且 MinIO 数据卷与数据库、备份争抢同一块盘会影响恢复能力。至少应增加独立数据盘（建议 100 GB ESSD）承载 PostgreSQL、备份和日志；对象存储使用 OSS 时不占 ECS 数据盘。

带宽方面，10 MB 图片在 5 Mbps 上理论上传约 16 秒，在 1 Mbps 上约 80 秒。代理上传会占用 ECS 公网带宽；如果图片上传频繁，预签名直传 OSS 可以绕开 ECS 带宽和内存缓冲。

**结论：**

1. **不建议在当前 2C2G 机器上再自建 MinIO 作为生产对象存储。** 若坚持自建，至少升级到 4 vCPU/4 GiB（更稳妥是 4C8G），并增加独立数据盘；仍需把备份放到另一块盘或 OSS。
2. **推荐使用阿里云 OSS 私有 Bucket。** ECS 不再运行对象存储进程，内存和磁盘压力显著下降；按量付费的存储和流量成本对个人账本通常较低。
3. 初期可以继续用 NestJS 代理上传到 OSS，接口和代码不变；把单实例并发上传限制在 2–3 个，并设置 Node 堆上限。若上传频率或图片体积上升，再切换为浏览器直传 OSS 的预签名模式。
4. 无论选 OSS 还是 MinIO，都应增加至少 2 GB swap 作为 OOM 兜底；swap 只能降低崩溃概率，不能替代内存和容量规划。

对“实时数据”的含义需要明确：账单和附件元数据是实时业务数据，用户在账单详情中应立刻看到刚上传成功的图片；图片二进制本身不进入实时消息通道，也不参与账单金额、余额和统计计算。共享账本其他成员在看到新图片前最多需要一次刷新，不要求逐字节实时同步。

选择代理上传而不是预签名直传，不是因为它“更先进”，而是因为当前规模下它更合适：

- 文件在服务端完成真实类型、大小和内容校验，不依赖客户端自律；
- OSS/MinIO 可以完全私有，不需要公网 Bucket、CORS 和额外的 URL 过期策略；
- 账单创建成功即拥有账单 ID，上传接口语义简单，不需要“待上传附件/确认完成”的中间态；
- 个人和家庭账本的图片量、并发和带宽都很低，预签名直传带来的扩展收益不足以抵消复杂度和攻击面。

预签名直传仍然是业内的主流扩展方案，本文在第 12 节给出不改变账单领域 API 的演进路径。使用 OSS 时，领域层通过 `ObjectStoragePort` 适配，生产用 OSS SDK，本地开发用 MinIO 的 S3 接口；业务代码不直接依赖某一家厂商。

## 2. 业务约束与规模假设

### 2.1 业务约束

- 图片是账单的可选凭证，不是账单成立的必要条件；没有图片的账单仍然完整可用。
- 收入、支出账单支持图片；本期不做转账、预算、报销审批和 OCR。
- 图片只对有权查看该账单的账本成员可见；私人账户账单继续受账户可见性约束。
- 账单软删除后，其附件必须立即不可读；对象是否已物理删除不影响业务结果。
- 附件上传、读取和删除都必须经过账本成员、角色和资源归属校验，不能只靠对象地址难猜。
- 附件不能改变账单金额、账户余额、统计口径和并发版本规则。

### 2.2 规模假设

| 维度 | 本期假设 |
| --- | --- |
| 用户 | 个人、家庭、小型共同生活群体；单账本通常 1–10 人 |
| 图片量 | 单笔账单 0–5 张，单张不超过 10 MB |
| 用户配额 | 默认 2 GB，可配置；按上传者统计未删除附件 |
| 写频率 | 低频人工记账，不追求高并发上传 |
| 读频率 | 账单详情按需加载，列表只显示附件数量 |
| 部署 | 单台服务器、Docker Compose、单实例 NestJS；生产 OSS，本地 MinIO |
| 网络 | 移动端 4G/5G/Wi-Fi，存在弱网、切后台、锁屏和重复提交 |

如果未来出现大量用户、批量导入票据、多人同时上传或需要跨区域访问，再按第 12 节升级；不要在当前规模提前引入分片上传、CDN、图片处理集群或独立媒体服务。

## 3. 业内方案对比

### 3.1 常见方案

| 方案 | 典型做法 | 优点 | 主要问题 | 适用判断 |
| --- | --- | --- | --- | --- |
| 数据库二进制 | `bytea`/BLOB 存图片 | 事务简单、备份统一 | 主库和备份迅速膨胀；连接和内存压力大；恢复慢 | 不采用 |
| 应用本地磁盘 | 容器卷或服务器目录 | 实现快、无额外服务 | 容器重建/扩容/迁移丢文件；多实例不共享；备份容易漏 | 不采用 |
| 服务端代理到对象存储 | 客户端 → API → OSS/MinIO | 统一鉴权、服务端校验、桶可私有、无 CORS | 带宽和内存经过 API；大文件/高并发成本高 | 本期采用 |
| 预签名直传 | API 签发 URL → 客户端直传 OSS/MinIO | 不占 API 带宽；易扩展；支持大文件 | 需要公网桶/CORS；大小和类型约束较弱；需要 pending/complete 状态 | 后续演进 |
| 托管图片服务 | Cloudinary、Supabase Storage、UploadThing 等 | 上传、转码、CDN 一体化 | 费用、供应商锁定、数据出域 | 备选 |
| 云对象存储 | 阿里云 OSS、S3、R2、COS | 免运维、可扩展、生态成熟 | 费用、网络、合规和迁移 | **当前服务器推荐 OSS** |

### 3.2 预签名直传的关键细节

业内常说的“预签名直传”有两个容易混淆的变体：

1. **预签名 PUT**：API 返回一个 `PUT` URL，客户端直接上传。实现简单，但 URL 本身通常不能强制最大文件大小；服务端只能在上传后通过 `HEAD` 检查大小，恶意客户端仍可先上传超大文件。需要配合桶策略、配额和事后清理。
2. **预签名 POST Policy**：API 返回 URL 和表单字段，策略中声明 `content-length-range`、`Content-Type`、对象键前缀和过期时间。约束更强，但客户端实现和错误处理更复杂，OSS/MinIO/S3 的兼容细节需要验证。

此外还有 S3 Multipart Upload（分片上传）和 tus/tus-js-client（可恢复上传）。它们适合大文件、长视频或极弱网络，不适合 10 MB 以内的票据图片；本期不引入。

### 3.3 为什么本期不直接上预签名

- 预签名要求对象存储对浏览器可达，需要额外的域名、TLS、CORS、Bucket 策略和签名地址泄露面。
- 预签名直传后仍需 `complete` 回调或 `HEAD` 校验，才能把附件从“待确认”变成“可读”；这引入了新的状态机、超时清理和重复确认问题。
- 预签名 PUT 不能可靠限制 10 MB，必须在服务端二次校验；预签名 POST Policy 能限制，但实现和兼容性成本更高。
- 当前图片量低，代理上传的带宽和内存成本可接受；服务端校验带来的安全收益更直接。
- 预签名并不能消除数据库与对象存储之间的一致性问题，只是把“上传”和“确认”拆开；本期不需要为此增加复杂度。

结论：**本期代理上传，保留演进接口；当上传并发、带宽或图片体积成为真实瓶颈时，再切换预签名，不改变账单附件领域模型和前端业务组件。**

## 4. 推荐架构

### 4.1 拓扑

```text
浏览器 / PWA
  │ 同源 HTTPS /api
  ▼
Nginx
  │
  ▼
NestJS API ────────────── PostgreSQL
  │  账单、附件元数据、审计、清理状态
  │
  └── OSS SDK / S3 接口 ── 阿里云 OSS（生产）或 MinIO（本地）
       私有 Bucket + 服务端加密/访问控制
```

文字说明：

- 浏览器只访问同源 `/api`，生产不直接访问 OSS 或 MinIO。
- NestJS 负责认证、账本成员校验、账单归属校验、文件校验、对象读写和元数据事务。
- PostgreSQL 保存附件元数据和业务状态，是“这张图片是否属于这笔账单”的唯一事实源。
- OSS/MinIO 保存二进制对象，使用私有 Bucket 和随机对象键；Bucket 策略不允许匿名读。
- Nginx 只反代前端和 `/api`，不反代 OSS 或 MinIO 控制台/数据端口。

### 4.2 一次上传的时序

```text
1. 客户端创建/编辑账单，先拿到 transactionId
2. 客户端为每张图片生成 clientRequestId
3. POST /api/ledgers/:ledgerId/transactions/:transactionId/attachments
   multipart/form-data: file + clientRequestId
4. NestJS 校验登录、账本成员、角色、账单存在且未删除
5. 按 [transactionId, clientRequestId] 查询是否已上传；命中则直接返回
6. 校验文件大小、魔数、真实类型和文件名
7. 统计当前有效附件数，检查是否已达到 5 张
8. 生成 attachmentId 和 objectKey，PutObject 到对象存储
9. 写入 TransactionAttachment（ATTACHED）和审计
10. 返回附件摘要；失败时尽力删除已上传对象
```

关键顺序是“先对象、后数据库”：只有在对象写入成功后，数据库才出现可读附件，避免详情接口返回一个不存在的对象。数据库写入失败时，对象成为孤儿；由尽力删除和后续对账处理，不影响业务正确性。

### 4.3 一次读取的时序

```text
1. GET /api/ledgers/:ledgerId/attachments/:attachmentId/content
2. NestJS 校验登录、账本成员、账单未删除、附件未删除
3. 如账单关联私人账户，校验当前用户是账户所有者
4. 从对象存储 GetObject 读取对象流
5. 设置 Content-Type/Length/Disposition/Cache-Control/nosniff
6. 流式返回；对象不存在或存储不可用返回明确错误
```

读取不返回永久公开地址，也不把对象存储的内部对象键暴露给客户端。浏览器通过同源 Cookie 鉴权，`<img>` 标签可以直接使用 `contentPath`。

## 5. 数据模型

### 5.1 Prisma 模型

```prisma
enum TransactionAttachmentStatus {
  ATTACHED
  DELETED
}

model TransactionAttachment {
  id              String                     @id @default(uuid())
  ledgerId        String                     @map("ledger_id")
  transactionId   String                     @map("transaction_id")
  uploadedById    String                     @map("uploaded_by_id")
  clientRequestId String                     @map("client_request_id")
  objectKey       String                     @unique @map("object_key")
  originalName    String?                    @map("original_name")
  mimeType        String                     @map("mime_type")
  sizeBytes       Int                        @map("size_bytes")
  checksumSha256  String                     @map("checksum_sha256")
  width           Int?
  height          Int?
  status          TransactionAttachmentStatus @default(ATTACHED)
  deletedAt       DateTime?                  @map("deleted_at")
  purgedAt        DateTime?                  @map("purged_at")
  purgeAttempts   Int                        @default(0) @map("purge_attempts")
  lastPurgeError  String?                    @map("last_purge_error")
  ledger          Ledger                     @relation(fields: [ledgerId], references: [id], onDelete: Cascade)
  transaction     Transaction                @relation(fields: [transactionId], references: [id], onDelete: Cascade)
  uploadedBy      User                       @relation(fields: [uploadedById], references: [id], onDelete: Restrict)
  createdAt       DateTime                   @default(now()) @map("created_at")
  updatedAt       DateTime                   @updatedAt @map("updated_at")

  @@unique([transactionId, clientRequestId])
  @@index([ledgerId, transactionId, status])
  @@index([status, createdAt])
  @@index([deletedAt, purgedAt])
  @@index([uploadedById, createdAt])
  @@map("transaction_attachment")
}
```

### 5.2 字段与约束说明

| 字段 | 说明 |
| --- | --- |
| `transactionId` | 必填。附件必须属于已保存账单，不引入草稿账单或独立草稿附件 |
| `clientRequestId` | 单张图片的幂等键，由客户端生成 UUID；同一账单内唯一 |
| `objectKey` | 服务端生成，格式 `ledgers/{ledgerId}/attachments/{attachmentId}.{ext}`；客户端不可指定 |
| `mimeType` | 服务端检测出的真实类型，不是客户端声明的 `Content-Type` |
| `sizeBytes` | 服务端读取到的实际字节数 |
| `checksumSha256` | 服务端计算的 SHA-256，用于完整性校验和对账，不返回给普通客户端 |
| `width`/`height` | 可选；能读取图片尺寸时保存，不能读取时为 `null` |
| `status` | `ATTACHED` 可读；`DELETED` 业务上不可读，等待对象清理 |
| `deletedAt` | 业务删除时间；内容接口和详情查询立即过滤 |
| `purgedAt` | 对象实际删除成功时间；为空表示仍在清理队列 |
| `purgeAttempts`/`lastPurgeError` | 清理重试次数和最近错误，便于排障 |

### 5.3 索引设计

- `[transactionId, clientRequestId]` 唯一：保证同一张图片重试不会产生重复附件。
- `[ledgerId, transactionId, status]`：账单详情、附件列表和数量统计。
- `[status, createdAt]`：清理任务按状态和时间扫描。
- `[deletedAt, purgedAt]`：查找待清理的已删除附件。
- `[uploadedById, createdAt]`：用户配额汇总和审计查询。

### 5.4 与账单的关系

- `Transaction` 增加 `attachments TransactionAttachment[]`；账单软删除不物理删除附件行。
- 账单详情返回 `attachments` 数组；账单列表返回 `attachmentCount`，不返回每张图片内容。
- 账单软删除时，在同一数据库事务中把该账单所有 `ATTACHED` 附件改为 `DELETED` 并写 `deletedAt`。
- 账本永久删除只允许空账本，因此正常不会出现“有附件的账本被硬删除”；数据库仍使用级联外键兜底。

## 6. 接口设计

### 6.1 接口总览

| 方法 | 路径 | 权限 | 用途 |
| --- | --- | --- | --- |
| `POST` | `/api/ledgers/:ledgerId/transactions/:transactionId/attachments` | `OWNER/EDITOR` | 上传并绑定一张图片 |
| `GET` | `/api/ledgers/:ledgerId/attachments/:attachmentId/content` | 可查看账单的活跃成员 | 读取图片内容 |
| `DELETE` | `/api/ledgers/:ledgerId/transactions/:transactionId/attachments/:attachmentId` | `OWNER/EDITOR` | 移除附件 |
| `GET` | `/api/ledgers/:ledgerId/transactions/:transactionId` | `VIEWER+` | 详情包含附件摘要 |
| `GET` | `/api/ledgers/:ledgerId/transactions` | `VIEWER+` | 列表包含 `attachmentCount` |

本期不提供“创建上传会话/确认上传”接口；预签名演进时再增加，见第 12 节。

### 6.2 上传附件

#### 请求

```http
POST /api/ledgers/ledger-uuid/transactions/transaction-uuid/attachments
Content-Type: multipart/form-data; boundary=...

file=@receipt.jpg
clientRequestId=7b0d3c2e-...
```

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `file` | 文件 | 是 | 单文件；JPEG/PNG/WebP；≤10 MB |
| `clientRequestId` | string | 是 | UUID；同一账单内唯一 |

#### 成功响应 `201`

```json
{
  "id": "attachment-uuid",
  "transactionId": "transaction-uuid",
  "mimeType": "image/jpeg",
  "sizeBytes": 248321,
  "originalName": "receipt.jpg",
  "contentPath": "/api/ledgers/ledger-uuid/attachments/attachment-uuid/content",
  "createdAt": "2026-11-08T12:31:00.000Z",
  "attachmentCount": 2
}
```

#### 服务端校验顺序

1. 登录会话有效。
2. 当前用户在目标账本中是 `ACTIVE` 成员，角色为 `OWNER` 或 `EDITOR`。
3. 账单属于该账本且 `deletedAt IS NULL`。
4. 按 `[transactionId, clientRequestId]` 查询幂等记录；命中则直接返回原附件，不重复上传。
5. 文件存在、字段完整、大小不超过 10 MB。
6. 文件头魔数、真实类型和文件名合法；拒绝 SVG、HTML、脚本和伪装类型。
7. 锁定账单行并统计 `ATTACHED` 附件数量；已达到 5 张返回 `40941`。
8. 检查用户配额；超过返回 `40942`。
9. 生成对象键并写入对象存储；写入失败返回 `50341`。
10. 写入附件元数据和审计；数据库失败时尽力删除对象。

#### 幂等与并发

- 同一 `clientRequestId` 的重复请求返回第一次创建的附件，不重复计数、不重复写审计。
- 两个并发请求使用同一 `clientRequestId` 时，数据库唯一约束是最终保护；后到者捕获唯一冲突，删除自己刚上传的对象，返回已存在附件。
- 两个并发请求使用不同 `clientRequestId` 且账单已有 4 张时，必须通过账单行锁串行化数量检查，最多一个成功。
- 上传成功后客户端立即拿到附件摘要；账单详情下一次查询包含该附件。共享账本其他成员在下一次刷新后可见，不做实时推送。

#### 错误码

| HTTP | code | 场景 |
| --- | --- | --- |
| `400` | `40041` | 文件、类型、大小、文件名或 `clientRequestId` 非法 |
| `403` | `40341` | `VIEWER`、非成员或无权编辑该账单 |
| `404` | `40441` | 账单、账本或附件不可见 |
| `409` | `40941` | 附件数量超限或状态冲突 |
| `409` | `40942` | 用户附件配额不足 |
| `413` | `41301` | 文件超过大小限制 |
| `415` | `41501` | 不支持的图片类型 |
| `429` | `42901` | 上传频率超过限制 |
| `503` | `50341` | 对象存储不可用或附件功能关闭 |

### 6.3 读取附件内容

```http
GET /api/ledgers/ledger-uuid/attachments/attachment-uuid/content
```

- 需要登录；只有能查看该账单的活跃成员可以读取。
- 账单已软删除、附件已删除、成员失效、跨账本、私人账户不可见时返回 `40441`。
- 返回二进制，不使用统一 JSON 成功包装；错误仍返回统一 JSON 错误体。
- 响应头：

```http
Content-Type: image/jpeg
Content-Length: 248321
Content-Disposition: inline; filename="receipt.jpg"
Cache-Control: private, max-age=300
X-Content-Type-Options: nosniff
```

- 不返回永久公开 URL；浏览器通过同源 Cookie 访问。
- 本期不承诺 `Range` 分段请求；图片按完整文件返回。后续如需大图渐进加载，可增加 Range 透传。
- 对象不存在或对象存储不可用返回 `40441`/`50341`，不能返回空 `200` 或损坏占位图冒充成功。

### 6.4 删除附件

```http
DELETE /api/ledgers/ledger-uuid/transactions/transaction-uuid/attachments/attachment-uuid
```

- 成功返回 `data: null`。
- 当前用户必须是账本 `OWNER` 或 `EDITOR`，账单未删除。
- 附件必须属于该账单和账本；重复删除同一附件返回 `200` 幂等结果。
- 在同一事务中把附件改为 `DELETED`、写 `deletedAt`、写审计；提交后异步删除对象。
- 附件删除不要求 `Transaction.version`，也不递增账单版本；账单字段编辑仍使用原版本控制。
- 账单软删除时，同一事务中把其所有有效附件标记为 `DELETED`，内容接口立即不可读。

### 6.5 账单详情和列表

详情响应中的附件摘要：

```json
{
  "attachments": [
    {
      "id": "attachment-uuid",
      "mimeType": "image/jpeg",
      "sizeBytes": 248321,
      "originalName": "receipt.jpg",
      "contentPath": "/api/ledgers/ledger-uuid/attachments/attachment-uuid/content",
      "createdAt": "2026-11-08T12:31:00.000Z"
    }
  ]
}
```

列表项只返回 `attachmentCount`，避免一次加载全部附件元数据。附件按 `createdAt` 升序，首张可作为列表缩略图；不返回 `objectKey`、桶名、校验值或上传者敏感信息。

## 7. 一致性、幂等与故障处理

### 7.1 没有分布式事务

对象存储和 PostgreSQL 不能共享事务。设计原则：

- 对象先写入，数据库后写入；数据库成功即代表附件可读。
- 数据库写入失败时，尽力删除刚写入的对象；删除失败只会留下孤儿对象，不影响业务。
- 数据库写入成功后对象读取失败属于存储故障，返回明确错误；不能把账单或附件记录删除来“掩盖”故障。
- 对象删除失败不影响业务删除；数据库状态 `DELETED` 是权威，对象由清理任务重试。
- 备份恢复后运行对账脚本，检查 `ATTACHED` 附件是否存在对象；只报告差异，不自动改业务数据。

### 7.2 幂等表

| 场景 | 幂等键 | 结果 |
| --- | --- | --- |
| 同一张图片重试 | `[transactionId, clientRequestId]` | 返回已存在附件 |
| 重复删除附件 | `attachmentId` + 状态 | 返回 `200`，不重复清理 |
| 账单重复创建 | `[ledgerId, clientRequestId]` | 返回已存在账单，不重复绑定附件 |
| 清理任务重跑 | `purgedAt IS NULL` + 状态 | 已清理的记录不会再次删除 |

### 7.3 并发场景

| 场景 | 处理 |
| --- | --- |
| 同一账单并发上传第 5、6 张 | 锁定账单行，统计数量；只有一个成功，另一个 `40941` |
| 同一 `clientRequestId` 并发上传 | 唯一约束兜底；后到者删除自己刚上传的对象，返回已存在附件 |
| 上传与账单软删除并发 | 上传事务锁定账单并检查 `deletedAt`；账单先删除则上传失败 |
| 删除与读取并发 | 读取先校验数据库状态；删除提交后新请求返回 `40441`，已开始的流可完成 |
| 配额并发 | 默认软限制；严格配额需用户级锁或计数表 |
| 清理与恢复 | 清理只处理 `DELETED` 记录；恢复后的对账不自动删除对象 |

### 7.4 对象存储故障

- 上传时对象存储不可用：返回 `50341`，不写数据库；客户端保留本地文件并重试。
- 读取时对象存储不可用：返回 `50341`，前端显示占位和重试，不把失败当成功。
- 删除时对象存储不可用：业务删除成功，对象进入清理队列；前端不再显示附件。
- 清理任务失败：记录 `purgeAttempts` 和 `lastPurgeError`，下一轮重试；超过阈值告警，不阻塞业务。

## 8. 安全与隐私

### 8.1 存储安全

- 桶私有，禁止匿名读和 public-read ACL。
- MinIO 本地部署时不暴露公网端口；生产 OSS 使用私有 Bucket 和最小权限 RAM 用户。
- 应用使用最小权限账号，只允许目标桶的 `GetObject`、`PutObject`、`DeleteObject` 和必要的 `HeadObject`；根账号只用于初始化和管理。
- 对象键由服务端生成，包含账本 ID 和随机附件 ID；客户端不能指定路径、覆盖已有对象或列举桶。
- 对象存储的访问密钥只通过环境变量注入，不写入代码、镜像、日志或文档。

### 8.2 内容安全

- 不信任客户端 `Content-Type` 和扩展名；读取文件头魔数确认 JPEG/PNG/WebP。
- 拒绝 SVG、HTML、脚本、压缩包和可执行文件；SVG 即使声明为图片也不接受。
- 文件名只用于展示和下载，去除路径分隔符、控制字符和过长名称。
- 设置 `X-Content-Type-Options: nosniff`，避免浏览器把图片当其他类型执行。
- 本期不做病毒扫描；只接受图片类型、限制大小、私有访问，风险由个人部署场景接受。若开放给不可信用户，需增加恶意文件扫描和图片解码沙箱。
- 图片可能在客户端被压缩或转码；服务端仍以实际收到的字节为准。

### 8.3 隐私

- 票据可能包含姓名、卡号后四位、地址、位置等敏感信息；默认私有，不生成公开链接。
- 本期保存原图字节，不主动移除 EXIF；手机照片可能包含 GPS 和设备信息。若隐私要求提高，增加服务端 `sharp` 处理：自动旋转、移除 EXIF、限制长边、重新编码；这会改变原图，需要单独评审。
- 日志不记录图片内容、对象键、签名 URL、存储密钥；错误日志只记录附件 ID、账本 ID、错误码和请求 ID。
- 审计记录附件 ID、媒体类型、大小和操作人，不记录图片内容。
- 备份文件和对象存储数据同样受访问控制，不能放在公开目录。

### 8.4 访问控制

- 上传：账本活跃成员 + `OWNER/EDITOR` + 账单未删除。
- 读取：账本活跃成员 + 账单可见（含私人账户规则）+ 附件未删除。
- 删除：账本活跃成员 + `OWNER/EDITOR` + 附件属于该账单。
- 不把 `attachmentId` 当作授权凭据；每次请求都重新校验账本、账单和附件归属。
- 共享账本成员被移除或退出后，旧 `contentPath` 立即失效。

### 8.5 限流与配额

| 接口 | 建议限制 |
| --- | --- |
| 上传 | 每用户每分钟 20 次、每小时 100 次 |
| 读取 | 每用户每分钟 300 次 |
| 删除 | 每用户每分钟 60 次 |
| 单用户总量 | 默认 2 GB，可配置 |
| 单笔数量 | 最多 5 张 |
| 单张大小 | 最多 10 MB |

超过限制返回 `42901` 或 `40942`；不能通过并发请求绕过单笔 5 张限制。

## 9. 性能与容量

### 9.1 上传路径

- Nginx `client_max_body_size` 至少 12 MB，避免默认 1 MB 在应用校验前返回 413。
- 本期 `FileInterceptor` 在内存中接收单文件，单张上限 10 MB；需要限制全局和单用户并发上传数，避免多个 10 MB 请求同时占用内存。
- 如果并发上传或文件上限提高，改为磁盘临时文件 + 流式 `PutObject`，或直接切换预签名。
- 上传接口不经过图片压缩；客户端可选压缩，但票据可读性优先。
- 计算 SHA-256 和读取魔数只遍历一次缓冲区，避免重复拷贝。

### 9.2 读取路径

- 图片读取经过 NestJS 流式转发，不把整个对象读入内存。
- 设置 `Cache-Control: private, max-age=300`，减少重复读取，同时让删除后的旧图在短时间内仍可能被浏览器缓存；隐私要求更高时缩短到 60 秒。
- 列表不加载图片内容，只返回 `attachmentCount`；详情按需加载。
- 未来读流量增大时可加 CDN 或短时签名 URL，但必须保证删除和权限撤销语义。

### 9.3 容量估算

| 项目 | 估算 |
| --- | --- |
| 单张平均 | 2–5 MB（手机原图），上限 10 MB |
| 单账单 | 0–5 张，平均 1–2 张 |
| 1000 笔带图账单 | 约 2–10 GB |
| 单用户 2 GB 配额 | 约 400–1000 张平均大小图片 |
| 备份 | 至少与主存储同等容量，保留周期另计 |

上线前确认服务器磁盘、备份盘和监控阈值；磁盘使用率达到 80% 时告警，不能等写满后才发现。

## 10. PWA、移动端与弱网

### 10.1 上传顺序

采用“先建账单、后传附件”：

1. 用户填写账单并保存，先获得 `transactionId`。
2. 账单保存成功后，按队列上传图片，最多 2 张并发。
3. 每张图片有独立 `clientRequestId`，失败只重试该张。
4. 全部成功或部分失败都要明确展示；账单本身已经保存，不能因为图片失败而回滚账单。
5. 用户关闭抽屉后，队列可在详情页继续重试；失败图片不得显示为已保存。

这与前端设计一致，也避免附件草稿和账单草稿的双重生命周期。

### 10.2 离线与后台

- 离线时账单可以进入现有离线同步队列；图片文件保存在 IndexedDB 的待上传队列，联网后上传。
- iOS PWA 不保证 Background Sync；不能承诺关闭应用后仍自动上传。应用回到前台、恢复网络或用户手动重试时继续。
- 本地预览使用 `URL.createObjectURL`，移除或上传成功后 `revokeObjectURL`。
- 清理浏览器数据、卸载 PWA 或更换设备会丢失未上传图片；界面必须提示，不把本地队列当永久存储。
- 账单在服务端已被删除时，待上传图片按 `40441` 处理并清理本地队列。

### 10.3 图片格式与 HEIC

- 服务端只接受 JPEG、PNG、WebP。
- iOS 相册可能提供 HEIC/HEIF；如果浏览器上传的是 HEIC，服务端返回 `41501`，前端提示“请选择 JPEG/PNG/WebP 或先在系统相册转换”。
- 不在本期引入 HEIC 解码依赖；若后续大量用户受影响，再评估服务端 `sharp`/`libheif` 转码。
- 相机拍摄建议使用 `accept="image/*"`，并在客户端展示格式和大小提示。

## 11. 部署与运维

### 11.1 生产：阿里云 OSS

当前 2C2G ECS 不建议再运行 MinIO。生产使用阿里云 OSS：

- 创建私有 Bucket，开启服务端加密；Bucket 不开放匿名读，不使用 public-read ACL。
- 后端通过 RAM 角色（推荐）或最小权限 RAM 用户的 AccessKey 访问；不要把长期 AccessKey 写入前端、镜像或仓库。
- ECS 与 OSS 同地域时使用内网 Endpoint（例如 `oss-cn-<region>-internal.aliyuncs.com`），避免服务器到 OSS 的公网流量和跨地域延迟；只有浏览器直传预签名时才需要公网 Endpoint 和 CORS。
- 代理上传时，ECS 只负责校验和转发；OSS 负责持久化、冗余和容量。ECS 不再为对象存储保留数据盘。
- 本期不需要给 OSS 配置浏览器 CORS；如果后续切换预签名直传，再按前端域名配置 CORS、暴露必要响应头并限制来源。
- 生产 Nginx 只反代前端和 `/api`，不反代 OSS。
- 本地开发和测试使用 MinIO，通过 `ObjectStoragePort` 的 S3 适配器；生产使用 OSS 适配器，业务代码不直接依赖 SDK。

本地 MinIO 仅用于开发：

```text
services:
  minio:
    image: minio/minio:<pinned-version>
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: ...
      MINIO_ROOT_PASSWORD: ...
    volumes:
      - minio_data:/data
    networks:
      - internal
    ports:
      - "127.0.0.1:9000:9000"
```

### 11.2 2C2G 资源限制

如果继续使用当前 2 vCPU/2 GiB 机器，至少做以下限制，否则 OOM 风险很高：

| 项 | 建议 |
| --- | --- |
| Node 堆上限 | Next.js、NestJS 分别设置 `--max-old-space-size=384` |
| PostgreSQL | `shared_buffers=128MB`、`max_connections` 控制在 50 以内、`work_mem=4MB` |
| Redis | `maxmemory 64mb`，使用 `allkeys-lru` 或明确淘汰策略 |
| 上传并发 | `ATTACHMENT_MAX_CONCURRENT_UPLOADS=2`，避免多个 10 MB 缓冲叠加 |
| Swap | 增加 2 GB swap 作为兜底，监控 swap in/out；不能替代扩容 |
| Docker | 给 backend/frontend/db/redis 设置内存上限，避免单容器拖垮整机 |
| 日志 | 限制 Docker 日志大小和保留数量，避免 20 GB 系统盘被日志占满 |
| 数据盘 | 建议增加 100 GB ESSD 承载 PostgreSQL、备份和日志；OSS 承载图片 |

如果出现持续 swap、OOM kill、上传超时或构建/部署期间服务不可用，应优先升级到 4 GiB 内存，而不是继续调小缓存。

### 11.4 备份与恢复

- PostgreSQL 和对象存储必须一起备份；只备份数据库会留下不可读附件。
- OSS 生产环境推荐开启 Bucket 版本控制或使用独立备份 Bucket + `ossutil sync`；明确“删除是否传播到备份”和保留周期。需要保留已删除图片时，备份 Bucket 单独设置生命周期，不能把备份 Bucket 设为公开。
- 本地 MinIO 使用 `mc mirror` 到独立备份盘或远端；不要只依赖单节点磁盘。
- 推荐每日数据库 dump + 对象存储同步；保留 14 个日备份、4 个周备份。
- 备份前记录时间点；恢复时使用同一时间点的数据库和对象备份。
- 恢复顺序：PostgreSQL → 对象存储 → 对账脚本 → 应用健康检查。
- 对账脚本检查每个 `ATTACHED` 附件的对象是否存在，输出缺失清单；不自动删除数据库记录，也不自动删除对象。
- 开放上传前必须完成一次恢复演练，记录 RPO/RTO、缺失对象数和恢复步骤。
- 备份文件加密或放在受控目录，不提交 Git，不放入公开静态目录。

### 11.4 监控

至少监控：

- 上传成功/失败数、平均耗时、413/415/503/429 数量；
- OSS 存储量、请求错误率、流量费用；自建 MinIO 时监控磁盘和对象数；
- 清理队列长度、`purgeAttempts` 异常增长；
- 数据库附件表大小和慢查询；
- 备份最近成功时间和恢复演练记录。

## 12. 演进路线

### 12.1 阶段一：代理上传（本期）

- 单张 ≤10 MB、低并发、私有 OSS 或本地 MinIO、后端代理。
- 适合个人和家庭账本，部署简单，校验集中。

### 12.2 阶段二：图片处理与缩略图

- 引入 `sharp` 做自动旋转、EXIF 清理、长边限制和缩略图。
- 详情页加载缩略图，点击查看原图；减少移动端流量。
- 需要评估 CPU、内存和原图保留策略，不阻塞本期上线。

### 12.3 阶段三：预签名直传

触发条件（满足其一即可评估）：

- 单日上传图片超过 1000 张，或峰值并发上传超过 10；
- 单张上限提高到 20 MB 以上；
- API 带宽或内存成为瓶颈；
- 多实例部署，代理上传难以水平扩展。

演进接口（不改变现有附件领域模型）：

```http
POST /api/ledgers/:ledgerId/transactions/:transactionId/attachment-uploads
→ {
  "attachmentId": "...",
  "mode": "PRESIGNED_POST",
  "uploadUrl": "...",
  "fields": { "key": "...", "Content-Type": "...", "x-amz-..." },
  "expiresAt": "..."
}

POST /api/ledgers/:ledgerId/attachments/:attachmentId/complete
→ 校验对象存在、大小和类型，状态 PENDING → ATTACHED
```

届时增加 `PENDING` 状态、上传会话过期清理和 confirm 幂等；前端通过 `AttachmentTransport` 适配层切换，不改账单页面。

### 12.4 阶段四：读取加速

- 读流量大时使用短时签名 URL + CDN；
- 仍需保证删除、权限撤销和私有性；
- 不在本期引入公开 CDN 或永久 URL。

## 13. 测试与验收

### 13.1 单元与接口测试

- 上传：类型、大小、魔数、空文件、文件名清洗、`clientRequestId` 格式。
- 幂等：同一 `clientRequestId` 重复上传返回同一附件；并发重复只创建一个。
- 数量：第 5 张成功、第 6 张 `40941`；并发第 5/6 张只成功一个。
- 权限：`VIEWER`、非成员、跨账本、已删除账单、私人账户不可见。
- 删除：重复删除幂等、账单软删除级联标记、内容接口立即 `40441`。
- 读取：响应头、二进制不被 JSON 包装、对象不存在/存储不可用错误。
- 清理：`purgedAt`、`purgeAttempts`、失败重试、已清理记录不重复删除。
- 配额：超配额 `40942`；并发配额为软限制的行为。
- 时间与账单：附件上传不改变账单 `version`、余额和统计。

### 13.2 集成与部署测试

- 使用隔离 PostgreSQL 和测试 MinIO/替代存储，不使用生产桶。
- 验证 Nginx `client_max_body_size` 和 12 MB 请求。
- 验证桶私有策略：匿名 GET 被拒绝，越权对象键不可列举。
- 验证数据库与对象存储联合恢复：恢复后有效附件可读，缺失对象被对账报告。
- 验证附件开关关闭时上传/读取返回 `50341`，账单创建和编辑不受影响。

### 13.3 移动端手工验收

- iOS Safari、iOS PWA、Android Chrome、Android PWA。
- 相机拍摄、相册选择、HEIC 拒绝提示、10 MB 超限、弱网重试、切后台、锁屏后恢复。
- 上传中关闭抽屉、重新进入详情、部分失败重试。
- 图片预览比例、加载失败占位、无权访问提示。

### 13.4 性能基线

- 单实例 5 个并发 10 MB 上传不 OOM，错误可控。
- 20 张连续上传的队列进度和重试正确。
- 读取 5 MB 图片时内存不随文件大小线性增长（流式）。
- 清理 100 条待删对象的耗时和失败重试。

## 14. 风险与未决问题

1. 单用户 2 GB 配额、单笔 5 张、单张 10 MB 是建议值，需结合实际磁盘和备份成本确认。
2. 备份位置、保留周期、RPO/RTO 尚未最终确定；未完成恢复演练前附件功能保持关闭。
3. 本期存储原图，不清理 EXIF；票据可能包含位置等隐私信息。是否启用 `sharp` 自动旋转/去元数据/缩略图待评审。
4. HEIC 不在支持范围；iOS 相册若上传 HEIC 会返回 `41501`，是否需要服务端转码待评估。
5. 代理上传的并发上限和内存占用需要压测确认；超过阈值时切换预签名。
6. 预签名直传需要 OSS/MinIO 对浏览器可达、CORS 和上传会话状态机，本期不实现。
7. 本期不做病毒扫描和图片内容审核；只面向可信的家庭/个人用户。若开放注册或公开分享，需要重新评估。
8. 附件内容缓存 5 分钟，删除后浏览器可能短暂显示缓存图片；隐私要求更高时缩短或禁用缓存。
9. 若自建 MinIO，其版本、AGPLv3 许可和升级策略需要在部署前确认；当前服务器优先 OSS，云 S3/R2 作为备选。
10. 图片宽度/高度为可选元数据；本期不引入图片解码库，读取不到时为 `null`。

## 15. 决策摘要

| 决策 | 结论 |
| --- | --- |
| 存储介质 | 生产阿里云 OSS 私有 Bucket；本地开发用 MinIO |
| 元数据 | PostgreSQL `TransactionAttachment`，不存二进制 |
| 上传方式 | 先建账单，再代理上传；`multipart/form-data` |
| 幂等 | 每张图片 `clientRequestId`，同一账单唯一 |
| 读取 | 鉴权代理读取，`contentPath`，私有桶 |
| 删除 | 数据库软删除 + 对象异步清理 + 重试 |
| 数量/大小 | 5 张/账单，10 MB/张，2 GB/用户（建议值） |
| 备份 | 数据库与 OSS 联合备份、恢复演练 |
| 预签名 | 本期不做，保留上传会话演进接口 |
| 图片处理 | 本期不压缩、不转码、不清理 EXIF；后续评估 |
