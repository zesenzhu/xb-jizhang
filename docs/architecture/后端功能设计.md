# 小宝记账后端功能设计

## 1. 文档范围

本文档定义第一期 NestJS 后台的模块边界、请求处理流程、权限校验、数据一致性和测试边界。它回答“后台应该有哪些能力，以及这些能力如何协作”，不替代具体 DTO 和接口字段文档。

## 2. 设计目标

- 所有账本数据以 `LedgerMember` 作为访问边界。
- 认证、角色和资源权限由服务端统一判断，前端不参与最终授权。
- 注册、角色变更、Owner 转移和账单写入等关键操作具备明确的事务边界。
- 金额、幂等、并发和软删除规则在 Service 层集中实现。
- Controller 保持轻量，业务规则集中在可单元测试的 Service 和领域辅助函数中。
- 后续可以在不改变用户权限语义的情况下增加账户、分类、账单和统计能力。

## 3. 后端模块边界

### 3.1 第一期模块

| 模块 | 职责 | 不负责的内容 |
| --- | --- | --- |
| `common` | 全局异常、响应、认证上下文、权限辅助、分页和日志 | 具体业务规则 |
| `auth` | 注册、登录、退出、刷新会话、修改密码 | 账本成员管理 |
| `user` | 当前用户资料、用户状态和敏感字段过滤 | 账本资源访问授权 |
| `ledger` | 个人/共享账本创建、查询、编辑、归档 | 复杂账单统计 |
| `ledger-member` | 成员列表、邀请接入、角色变更、移除、退出、Owner 转移 | 账户和账单内容 |
| `account` | 账本账户的新增、编辑、停用和可见性 | 成员邀请 |
| `category` | 收入/支出分类的新增、编辑、停用和排序 | 账单金额计算 |
| `transaction` | 收入、支出、查询、编辑、软删除和审计 | 页面汇总展示 |
| `statistics` | 月度收入、支出、结余和基础排行 | 修改账单 |
| `admin-auth` | 平台管理员登录、刷新、退出和管理会话 | 普通用户登录和账本成员角色 |
| `admin-permission` | 管理员角色、权限码和权限解析 | `LedgerMember` 固定角色 |
| `admin-user-management` | 普通用户查询、状态管理和脱敏资料 | 密码、Token 和普通用户登录 |
| `admin-ledger` | 账本查询、归档/恢复和运营摘要 | 默认修改账单正文和 Owner |
| `admin-transaction` | 高风险权限下的敏感账单查询和修改 | 无理由或无权限的后台操作 |
| `admin-config` | 受控系统配置读写 | 数据库、JWT、Redis 等部署秘密 |
| `admin-audit` | 管理员操作审计追加和查询 | 普通业务日志替代审计 |

### 3.2 后续模块

- `budget`：分类预算和周期预算；
- `backup`：导入、导出和备份恢复；
- `sync`：离线队列同步和冲突处理；
- `notification`：邀请和同步结果通知。

后续模块只有在一期需求进入开发时才创建，不提前建立空模块。

## 4. 请求处理流程

所有需要登录的账本接口遵循以下顺序：

```text
HTTP 请求
  ↓
全局 ValidationPipe
  ↓
JWT 鉴权 Guard
  ↓
提取当前用户上下文
  ↓
LedgerMember 权限校验
  ↓
Controller 调用 Service
  ↓
Service 执行业务规则和 Prisma 查询/事务
  ↓
统一响应或异常过滤
```

Controller 不从请求体接收可信的操作者 ID。操作者身份只能来自认证上下文；请求体中的 `ledgerId`、`userId` 或 `memberId` 只能作为资源定位信息，必须再次校验归属关系。

平台管理接口遵循另一条处理流程：

```text
HTTP 请求 /api/admin/**
  ↓
ValidationPipe
  ↓
AdminAuthGuard（Cookie、JWT type、audience、账号状态）
  ↓
AdminPermissionGuard / Service 权限校验
  ↓
高风险操作原因和并发版本校验
  ↓
Service 事务更新业务数据与 AdminAuditLog
  ↓
统一响应或异常过滤
```

普通用户 `AuthGuard` 不能用于管理端接口，管理端 `AdminAuthGuard` 也不能被普通账本模块复用。两类上下文都必须从服务端认证信息取得操作者 ID，不信任请求体中的 `adminUserId` 或 `userId`。

## 5. 认证与用户流程

### 5.1 注册

注册 Service 在一个 Prisma transaction 中完成：

1. 校验用户名、密码和可选邮箱；
2. 检查用户名和邮箱唯一性；
3. 创建用户并保存密码哈希；
4. 创建默认个人账本；
5. 创建该用户的 `OWNER` 成员关系；
6. 签发访问凭证和刷新凭证。

任一步失败都回滚全部写入，不能留下无账本用户或无 Owner 账本。

### 5.2 登录和会话

- 登录成功后通过 HttpOnly Cookie 保存访问凭证和刷新凭证。
- Refresh Token 不从 localStorage 或普通业务请求体中读取。
- PostgreSQL 保存刷新会话记录和 Token 哈希，Redis 只用于限流、缓存和短期锁。
- 每次刷新都轮换刷新凭证；检测到旧 Token 重放时，撤销对应的会话链。
- 退出时清理两类 Cookie，并撤销当前设备会话；修改密码时撤销该用户全部刷新会话。
- 访问凭证过期时，客户端通过独立刷新请求续期；刷新失败返回统一认证错误。
- 登录失败、账号停用和刷新失败不能泄露不必要的账号存在性信息。

平台管理员使用独立的 `admin_access_token`、`admin_refresh_token`、`AdminRefreshSession` 和 `aud=admin` Token。管理员认证规则、权限模型、审计和数据表见[平台管理端技术设计](./平台管理端技术设计.md)。

### 5.3 用户资料

用户资料接口只返回允许公开的字段：用户 ID、用户名、昵称、邮箱、头像、账号状态和时间字段。密码哈希、Token、登录失败计数等安全字段永不进入响应 DTO。

## 6. 账本和成员权限

### 6.1 成员访问校验

建议提供统一的成员访问辅助方法：

```text
getActiveLedgerMember(userId, ledgerId)
requireLedgerRole(userId, ledgerId, allowedRoles)
```

所有账本资源 Service 必须复用这类校验，不能在每个模块中重新实现一套不一致的判断。

### 6.2 固定角色

| 能力 | `OWNER` | `EDITOR` | `VIEWER` |
| --- | --- | --- | --- |
| 查看账本资源 | 允许 | 允许 | 允许 |
| 新增/编辑账单 | 允许 | 允许 | 禁止 |
| 删除自己创建的账单 | 允许 | 允许 | 禁止 |
| 删除其他成员账单 | 允许 | 禁止 | 禁止 |
| 管理账本设置 | 允许 | 禁止 | 禁止 |
| 管理成员和邀请 | 允许 | 禁止 | 禁止 |
| 转移 Owner | 允许 | 禁止 | 禁止 |

角色权限必须在后端 Service 或 Guard 中检查。前端菜单和按钮只用于改善体验，不构成安全边界。

### 6.3 成员变更事务

以下操作必须在事务内完成：

- 接受邀请并创建成员关系；
- 修改成员角色；
- 移除成员；
- 成员主动退出；
- Owner 转移。

事务中必须保证账本至少保留一名 `OWNER`。个人账本的唯一 Owner 不能退出或被移除。

### 6.4 邀请和重新加入

- 邀请目标使用规范化邮箱，角色只能为 `EDITOR` 或 `VIEWER`，有效期固定为 72 小时。
- `LedgerInvitation` 只保存不可预测 Token 的 SHA-256 哈希值；原始 Token 只在创建成功响应中返回一次。
- 同一账本、同一邮箱同时只能存在一个 `PENDING` 邀请；接受邀请必须登录并匹配用户邮箱。
- `LEFT` 和 `REMOVED` 成员只能通过新的有效邀请重新加入，接受后复用原成员关系并恢复为 `ACTIVE`。
- 重新加入使用新邀请中的非 Owner 角色，不通过邀请恢复或授予 `OWNER`。
- 邀请创建、接受、拒绝、撤销、移除成员和重新加入都应记录审计信息。

## 7. 一期业务写入规则

### 7.1 账户和分类

- 账户、分类都必须带有 `ledgerId`。
- 创建、编辑和停用前先验证当前用户是账本成员，并验证资源确实属于该账本。
- 已被账单引用的账户和分类优先停用，不直接物理删除。
- 私人账户还要校验 `ownerId`；共享账本成员不能因为知道资源 ID 就访问其他人的私人账户。

### 7.2 账单

- 金额使用整数分，Service 层禁止浮点计算。
- 新增账单必须携带客户端幂等 ID，唯一性范围为账本。
- 修改账单必须携带 `version` 或约定的更新时间，版本不一致返回冲突。
- 删除账单默认写入 `deletedAt`，普通查询自动过滤软删除记录。
- 账单创建人、最后修改人和实际付款人分别保存，不能用一个字段替代三个业务概念。
- 账单涉及的账户、分类、付款人必须属于当前账本且处于允许使用的状态。

### 7.3 统计

统计只读取账本成员允许看到的数据，并统一过滤软删除账单。一期只统计收入和支出，不接收或处理转账类型。

## 8. 数据和基础设施边界

- PostgreSQL 是业务数据唯一主存储，Prisma 负责数据访问和事务。
- PostgreSQL 还保存可撤销的刷新会话；建议字段包括 `userId`、`tokenHash`、`deviceName`、`userAgent`、`lastUsedAt`、`expiresAt`、`revokedAt` 和 `replacedBySessionId`。
- Redis 只用于短期数据，例如登录限流、邀请过期缓存、幂等锁和同步锁，不保存账单主数据或作为刷新会话唯一来源。
- Prisma Migration 需要将邀请 Token 按哈希存储，并为同一账本/邮箱的未完成邀请增加重复约束或事务性校验。
- API 的统一响应、异常和请求日志放在 `common`，业务模块不重复实现。
- 平台管理员使用独立的 `AdminUser`、`AdminRole`、`AdminPermission`、`AdminRefreshSession` 和 `AdminAuditLog`，不能在普通 `User` 上增加 `isAdmin` 代替权限模型。
- 管理员高风险操作必须在同一事务中完成业务变更和审计写入；审计数据只追加，不记录密码、Cookie、Token 或部署密钥。
- Swagger/Scalar 描述由 DTO 和装饰器生成；生产环境不暴露调试接口。
- 当前一期不引入 MQTT、TCP、AI Agent 和设备日志等旧项目能力。

## 9. 错误处理

Service 使用 NestJS 标准异常表达业务失败：

- 未登录：认证失败；
- 已登录但没有账本成员关系：拒绝访问；
- 角色不足：权限不足；
- 管理员身份无效或 Token audience 错误：管理端认证失败；
- 管理员缺少权限码：管理端权限不足；
- 资源不存在或不属于当前账本：资源不可用；
- 参数不合法：请求参数错误；
- 版本冲突：并发修改冲突；
- 幂等请求重复：返回已存在的业务结果，不重复写入。

错误响应格式遵循 [接口约定](../api/接口约定.md)，Controller 不手工拼接另一套错误结构。

## 10. 测试设计

### 10.1 单元测试

- 认证 Service：密码校验、凭证签发、刷新失败和账号停用；
- 刷新会话 Service：Token 轮换、旧 Token 重放、单设备撤销、全部会话撤销和并发刷新；
- 用户 Service：敏感字段过滤、唯一性冲突和资料更新；
- 权限辅助：成员状态、角色等级和跨账本访问；
- 成员 Service：最后 Owner 保护、Owner 转移和成员变更；
- 邀请 Service：邮箱规范化、唯一未完成邀请、Token 过期/撤销、邮箱匹配和成员重新加入；
- 账单 Service：金额、幂等、版本冲突、软删除和资源归属。
- 管理员认证与权限：普通用户 Token 误用、audience 隔离、内置角色权限和管理员停用。
- 管理端高风险操作：操作原因、脱敏、并发冲突、业务与审计事务一致性。

### 10.2 接口契约测试

Controller 测试验证 DTO 传递、认证上下文、路径参数和主要异常映射。不能只断言 Service 被调用，还要验证关键参数没有被改写或丢失。

### 10.3 数据库集成测试

事务、唯一约束、级联关系和 Prisma Migration 需要隔离数据库测试。测试环境必须使用独立数据库或临时容器，不连接本地开发数据。

## 11. 实施顺序

1. 先实现 `common` 的认证上下文、统一异常和响应约定；
2. 实现 `auth` 和 `user`，补注册、登录、刷新、资料和密码测试；
3. 实现 `ledger` 和 `ledger-member`，补成员权限和 Owner 保护测试；
4. 实现 `account` 和 `category`，补账本归属测试；
5. 最后实现 `transaction` 和首页统计，补幂等、并发和软删除测试。
6. 实现基础 `statistics` 查询模块，补充账本隔离、软删除和私人账户可见性测试。
7. 在普通用户认证稳定后实现 `admin-auth`、`admin-permission` 和 `admin-audit`，再实现管理端用户、账本和高风险账单能力。

每一步都以对应接口文档和测试通过为完成条件，不跨越未确认的业务规则直接编码。

## 12. 取舍与风险

- 第一期使用固定角色，牺牲部分灵活性换取权限语义简单、可测试和易解释。
- Token 使用 Cookie，降低前端存储泄露风险，但要求前后端部署时正确处理同源、Secure 和 SameSite 配置。
- 一期不做复杂实时协同，降低并发合并成本；共享账本先通过刷新和同步状态保证数据可见。
- 账户余额是否实时落库需要在账户和账单技术方案中单独决定，不能在本模块中隐含假设。
- 管理端独立身份域增加模型和权限维护成本，但避免普通用户身份、账本成员角色和平台管理权限混用；本项目选择保留该边界。
