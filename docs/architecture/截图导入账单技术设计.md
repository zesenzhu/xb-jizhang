# 截图导入账单技术设计

> **本期不实施。** 三期范围已收敛为邀请、备注候选、键盘和日期时间四项；图片附件移出范围，图片 OCR 明确不在三期引入。本文是“截图导入账单”的后续专项设计，用于记录能力边界、OCR 选型和接口草案，重新立项前不能作为迁移或接口实现依据。

## 1. 结论先行

“截图导入”指用户选择一张支付截图，系统识别其中的金额、时间、商家和收支方向，回填成一张待确认的账单草稿。它不是纯前端能力，也不是纯后端能力：

| 环节 | 归属 | 结论 |
| --- | --- | --- |
| 选图/拍照/粘贴、压缩、方向校正、裁剪预览 | 前端 | 只有浏览器能拿到用户选择的文件 |
| 图片校验、限流、调用识别服务、模板解析、结构化归一 | 后端 | 模型、密钥和成本必须留在服务端 |
| 金额/时间/分类回填与用户确认 | 前端 | 识别必然有错，金额与时间必须人工确认 |
| 账单落库 | 后端 | 复用现有 `POST /api/ledgers/:ledgerId/transactions` 与 `clientRequestId` 幂等 |

核心判断：**识别不能放前端。** `tesseract.js` 一类 WASM 方案的中文识别准确率、十几到几十 MB 的模型体积、移动端数秒到十几秒的耗时，以及无法集中更新模型和限流，都不适合作为记账主入口的支撑能力。前端方案只能在“固定模板 + 用户逐字段校正”时勉强可用，实质退化为手动记账。

第二条判断：**不要默认自建 OCR 服务。** 当前生产服务器为 2C2G，按《账单图片附件与对象存储设计》的估算已接近内存上限，再跑 PaddleOCR（单实例通常需要数百 MB 到 1 GB 级内存并占用 CPU 做推理）会显著提高 OOM 风险。本期若实施，应优先走云 OCR 或多模态模型 API，把模型放在服务端之外。

第三条判断：**只返回草稿，绝不自动入账。** 金额或时间识别错误直接污染财务数据，必须由用户确认一次。

## 2. 现状核对（基线 `22496cc`）

| 项 | 现状 | 对本文的影响 |
| --- | --- | --- |
| 图片上传能力 | 无上传接口、无对象存储接入；三期不实施附件 | 截图导入需要自带一条临时上传通道 |
| 上传依赖 | `multer` 由 `@nestjs/platform-express` 间接提供（2.4.0），未安装 `@types/multer` | 可用 `FileInterceptor`，但需补类型依赖 |
| 记账入口 | 记账抽屉快捷条中“图片”为禁用占位 | 天然的入口位置，不需要新增导航 |
| 备注候选 | 已实现 `NoteSuggestionBar` 与服务端候选接口 | 导入草稿可直接复用备注交互 |
| 金额与时间契约 | `amountCents` 整数分；`occurredAt` 要求带时区 ISO 8601；创建需 `clientRequestId` | 识别结果必须归一成同一契约 |
| 生产环境 | 阿里云 2C2G、20 GB 系统盘，已运行 Nginx/Next.js/NestJS/PostgreSQL/Redis | 不能在本机加 OCR 推理进程 |
| 对象存储 | 附件专项设计选定阿里云 OSS 私有 Bucket，尚未实施 | 截图默认不落存储，未来可复用同一条通道 |

## 3. 能力边界

### 3.1 前端负责

- 入口：记账抽屉快捷条“图片”。
- 采集：`<input type="file" accept="image/*">` 相册选择；桌面端支持拖拽与粘贴。
- 预处理：等比压缩到长边约 1600 px、JPEG 质量约 0.8、按 EXIF 方向摆正，控制上传体积与识别耗时。
- 交互：上传进度、可取消、识别中的骨架、失败重试、草稿回填、字段高亮与逐项确认。
- 提交：用户确认后调用既有创建接口，携带 `clientRequestId`。

### 3.2 后端负责

- `multipart/form-data` 接收，校验类型、大小与真实内容魔数。
- 按用户限流与配额，防止刷识别费用。
- 调用识别适配器（云 OCR / 多模态模型 / 未来自建服务），统一超时与重试边界。
- 模板解析：识别来源应用（微信、支付宝、银行），抽取金额、时间、商家、收支方向、支付方式。
- 结构化归一：金额转整数分、时间转带时区 ISO 8601、方向映射 `EXPENSE/INCOME`、给出分类建议与置信度。
- 返回草稿，不写账单；原图默认不持久化。

### 3.3 明确不做

- 不做自动入账，不做“识别即保存”。
- 不支持聊天长截图中多条流水批量拆分（歧义与错行风险不可控）。
- 不做离线识别（必须联网）。
- 不做图片内容审核以外的 AI 理解（如情绪、场景描述）。
- 不在本期接入对象存储长期保存截图。

## 4. 端到端流程

```text
用户点“图片”
  → 前端选图/粘贴
  → 前端压缩 + 摆正
  → POST /api/transactions/imports （multipart，单张）
  → 后端校验（类型/大小/魔数/限流）
  → 识别适配器 → 模板解析 → 结构化归一
  → 返回 { draft, confidence, warnings }（不落库）
  → 前端回填记账抽屉（金额/时间/商家/收支/分类/账户）
  → 用户确认或修改
  → POST /api/ledgers/:ledgerId/transactions （既有接口，clientRequestId 幂等）
  → 成功入账
```

失败降级：识别失败或整体置信度过低时，前端保留已选图片和用户已填字段，提示“未能识别，请手动填写”，不阻断记账。

## 5. 识别方案对比

评估维度按本项目实际情况加权：2C2G 服务器、个人使用量、隐私、成本、可维护性。

### 5.1 候选方案

| 方案 | 说明 |
| --- | --- |
| A. 前端 WASM OCR | `tesseract.js` 等在浏览器内识别，服务端零成本 |
| B. 自建 PaddleOCR | Docker 部署 PaddleOCR HTTP 服务，内网调用 |
| C. 云 OCR API | 阿里云/腾讯云/百度等文字识别，按次计费 |
| D. 多模态大模型 API | 直接把截图交给视觉模型，输出结构化字段 |

### 5.2 对比

| 维度 | A 前端 WASM | B 自建 PaddleOCR | C 云 OCR | D 多模态模型 |
| --- | --- | --- | --- | --- |
| 中文识别准确率 | 低到中，版面复杂时明显下降 | 中到高 | 高 | 高（对版式变化更鲁棒） |
| 结构化能力 | 无，需自己写规则 | 无，需自己写规则 | 有限（部分厂商提供票据/卡证模板） | 可直接输出字段 |
| 服务器开销 | 0 | 高：数百 MB 到 1 GB 内存 + CPU，2C2G 不可行 | 极低 | 极低 |
| 单次成本 | 0 | 0（电费与机器折旧除外） | 按次计费，个人量级很低 | 按 token 计费，单次高于云 OCR |
| 延迟 | 移动端数秒到十几秒 | 0.3–2 秒（视图片与机器） | 0.2–1.5 秒（含网络） | 1–5 秒 |
| 隐私 | 图片不出设备 | 图片不出服务器 | 图片上传第三方 | 图片上传第三方 |
| 密钥管理 | 无 | 无 | 需服务端保管 AK/SK | 需服务端保管 API Key |
| 可演进性 | 差：模型随包体发布，缓存难更新 | 中：换模型需重建镜像 | 好：换厂商改适配器 | 好：换模型改适配器 |
| 失败模式 | 卡顿、内存溢出、识别乱码 | 内存不足、容器重启 | 限流、欠费、区域故障 | 超时、格式拒绝、结果不稳定 |
| 运维负担 | 低 | 高 | 低 | 低 |
| 本期可行性 | 不推荐 | 不可行（2C2G） | **推荐起步** | 备选/增强 |

### 5.3 推荐路径

1. **起步：云 OCR（C）+ 模板规则。** 微信、支付宝支付详情截图版式稳定，先用 OCR 拿到文本行，再用“关键词 + 位置 + 正则”抽取金额、时间、商家、方向。成本可控，服务器零新增负载。
2. **增强：多模态模型（D）作为兜底。** 当模板规则置信度低时，再调用一次多模态模型解析；或直接用它处理非标准截图（银行、外卖、账单邮件截图）。
3. **不做：前端 WASM（A）。** 准确率与体验不达标，会让用户对功能失去信任。
4. **延后：自建 PaddleOCR（B）。** 仅在以下条件同时成立时再评估：服务器升级到 4C8G 以上并有余量、有明确的离线/隐私硬要求、OCR 调用量足以覆盖运维成本。

无论选 C 还是 D，都必须包在 `ScreenshotRecognizer` 适配器接口后面，方法签名只暴露“图片字节 + 提示 → 结构化结果”，使厂商可替换。

具体厂商与计费以官网为准，本文不锁定供应商；选型时至少核对：中文支付截图的实测准确率、免费额度、QPS 限制、图片大小上限、是否留存图片、以及是否要求实名。

## 6. 接口草案

### 6.1 解析接口

```text
POST /api/transactions/imports
Content-Type: multipart/form-data
认证：登录用户（不要求账本成员，因为解析是草稿级操作）
```

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `file` | 文件 | 必填，JPEG/PNG/WebP，≤ 5 MB（压缩后） |
| `ledgerId` | string | 可选，用于分类建议与默认账户，必须是当前用户活跃成员账本 |

响应（成功 `200`，不落库）：

```json
{
  "success": true,
  "code": 0,
  "message": "操作成功",
  "data": {
    "draft": {
      "type": "EXPENSE",
      "amountCents": 4560,
      "occurredAt": "2026-11-08T11:52:00+08:00",
      "title": "瑞幸咖啡",
      "note": null,
      "categoryId": "category-uuid",
      "accountId": null,
      "confidence": 0.86
    },
    "source": "WECHAT_PAY",
    "warnings": ["AMOUNT_LOW_CONFIDENCE"]
  }
}
```

约束：

- `draft` 是建议值，服务端不校验其与账本的真实一致性；真正写入仍走账单创建接口的完整校验。
- `occurredAt` 必须带时区偏移；无法识别时间时返回 `null`，由前端填当前时间。
- `amountCents` 必须是整数分；识别出“12.345”这类非法金额时取两位小数并给出 `AMOUNT_ROUNDED` 警告，或直接判为低置信度不预填。
- `categoryId` 只能来自 `ledgerId` 对应账本的启用分类；不匹配时返回 `null`。
- 不返回原图地址，不返回 OCR 全文（避免把整张截图的文字外泄到前端日志）。

### 6.2 错误码

| HTTP | code | 场景 |
| --- | --- | --- |
| `400` | `40061` | 文件缺失、格式不支持、内容与声明类型不符 |
| `400` | `40062` | 识别结果无法构成草稿（整体置信度过低） |
| `413` | `41301` | 文件超过大小上限 |
| `429` | `42961` | 识别接口触发限流 |
| `503` | `50361` | 识别服务不可用或超时 |

错误文案必须区分“图片无法识别”和“服务暂时不可用”，前者引导手动填写，后者引导重试。

### 6.3 幂等与去重

- 解析接口本身不需要幂等键：同一张图重复解析只是重复消耗一次识别，不产生业务数据。
- 建议前端对同一张图（内容 SHA-256）在一次会话内复用解析结果，避免用户重复点击。
- 真正需要防重的是“同一张截图被导入两次”。建议在创建账单时携带 `importedFromHash`（可选扩展字段）或在前端做近似判断（金额+时间+商家），命中时提示“疑似已记过”，但不阻断用户。
- 账单创建仍以 `clientRequestId` 为唯一幂等依据，不因导入功能改变。

## 7. 结构化规则

| 字段 | 规则 |
| --- | --- |
| 金额 | 优先取“¥/￥”或“金额”标签后的数字；转整数分；拒绝负数与 0 |
| 时间 | 支持 `今天 11:52`、`2026-11-08 11:52`、`11月8日 11:52`；无年份时按当前年推断，推断结果晚于当前时间则回退一年 |
| 时区 | 统一按账本时区解释并输出带偏移的时间；无账本上下文时按 `Asia/Shanghai` |
| 收支方向 | “付款/支付/消费/转账给”归 `EXPENSE`；“收款/退款/红包收入”归 `INCOME`；无法判断时默认为 `EXPENSE` 并给出警告 |
| 标题 | 优先商家名；取不到时留空，不用整行 OCR 文本填充 |
| 分类 | 基于商家/关键词的映射表 + 用户历史（同商家最近使用的分类），属于建议值 |
| 支付方式 | 识别“微信/支付宝/银行卡”用于选择账户建议，但不自动绑定账户，避免账户余额被误判 |

金额和时间是“高置信度才预填”的字段；标题、分类、账户是“低置信度也可预填但必须显式标注为建议”的字段。

## 8. 数据模型影响

推荐：**本期不新增持久化表。**

- 解析是无状态操作，草稿只存在于响应中。
- 若需要审计与排查（例如统计识别失败率），增加可选的 `TransactionImportLog`（`userId`、`source`、`status`、`confidence`、`createdAt`，不含图片与 OCR 全文），保留期 30 天，定时清理。
- 若未来要“保留截图作为附件”，复用附件专项设计的 `TransactionAttachment` 与 OSS 通道，不新建第二套存储。

图片字节处理：

- 默认在内存流式处理，单请求上限 5 MB，处理完即释放，不落盘。
- 需要调试留样时，只能写入受控临时目录并设 TTL，且必须脱敏并限管理员访问；默认关闭。

## 9. 安全与隐私

- 只接受 JPEG/PNG/WebP，服务端校验魔数而不只看扩展名与 `Content-Type`。
- 拒绝 SVG、HTML、PDF 等可能触发脚本或解析器漏洞的输入。
- 限制像素总量（例如 ≤ 4000 万像素），防止解压炸弹。
- 按用户限流（建议 3 次/分钟、50 次/天起步），超限返回 `42961`；同时记录用量以便发现滥用。
- 不把图片写入应用日志、错误上报或 APM；不记录 OCR 全文。
- 交给第三方识别服务前，需在隐私说明中告知“截图会被上传用于识别”；若用户不接受，可只用模板规则或手动填写。
- OCR 结果视为不可信输入：不参与 SQL 拼接、不直接作为文件名、不直接渲染为 HTML。
- 第三方返回的错误信息不得原样透传给前端。

## 10. 前端交互与平台限制

- 入口：记账抽屉快捷条“图片”（当前为禁用占位），点击后打开系统选择器；桌面端支持拖拽与 `Ctrl+V` 粘贴。
- 状态：`idle → selecting → uploading（可取消）→ recognizing → drafted → failed`；每个状态都有可执行的下一步。
- 回填后字段旁标注“来自截图”，用户修改任一字段即移除标注；未识别字段保持空并聚焦提示。
- 不覆盖用户已经手动填写的字段：若用户先输了金额，导入结果只在金额为空时回填，冲突时提示让用户选择。
- PWA 限制：iOS Safari/PWA 不支持 Web Share Target，只能从相册选择；Android Chrome 可通过 `share_target` 支持“分享到记账”，属于增强项，需在 `manifest.webmanifest` 增加配置并单独验证。
- 离线：不可用。离线状态下点击入口直接提示“需要联网识别”，不进入上传流程。

## 11. 成本与配额

- 云 OCR 通常按次计费，个人记账场景月用量多在几十到几百次，绝对成本很低；具体单价、免费额度与 QPS 限制以厂商官网为准。
- 多模态模型按 token 计费，单张截图成本高于云 OCR，适合作为兜底而非默认路径。
- 需要设置两道闸门：单用户日配额、全局日配额。任一触发都返回明确提示，而不是让账单失败在超时上。

## 12. 分期建议

| 阶段 | 范围 | 门槛 |
| --- | --- | --- |
| P0 | 相册选图 → 云 OCR → 微信/支付宝模板解析 → 草稿确认入账 | 识别准确率在自备样本上达到可接受水平（金额字段 ≥ 95%） |
| P1 | 多模态兜底、疑似重复提示、Android 分享入口 | P0 稳定运行且有真实失败样本 |
| P2 | 银行/外卖等更多模板、批量导入 | 有明确用户诉求 |

若三期尚未收尾，本能力应作为四期候选立项，不插入当前实施计划。

## 13. 测试策略

- 适配器层：用固定样本图片与录制好的 OCR 响应做契约测试，不在 CI 调用真实第三方。
- 解析规则：纯函数测试覆盖金额、时间（含跨年推断）、方向、商家抽取、非法输入。
- 接口层：文件类型、魔数、大小、像素上限、限流、超时与错误码映射。
- 前端：状态机（取消上传、识别失败、字段冲突）与压缩函数纯函数测试。
- 端到端：一张真实截图从选图到入账的人工验收，另加一次第三方不可用的降级验收。
- 安全：伪装扩展名、超大像素、SVG/HTML 上传均须被拒绝。

## 14. 未决问题

1. OCR 供应商未定（云 OCR 或多模态模型），需先用真实截图样本做准确率对比再决定。
2. 是否允许用户保留原截图作为账单附件：当前建议默认不保存；若需要，需等附件专项落地后复用。
3. 单张图片上限（当前建议 5 MB）与前端压缩参数需在真机验证清晰度是否足够识别。
4. 是否需要“识别失败自动转手动填写”的埋点统计，用于评估功能价值。
5. 若未来服务器升级，是否重启自建 PaddleOCR 评估，取决于隐私要求与调用量。
6. 该能力属于四期还是独立小版本，需要与三期收尾节奏一起排期。
