# 小宝记账前端应用架构

## 1. 文档定位

本文档是前端路由、Layout、认证边界、数据管理、组件组织和 PWA 基础能力的总设计文档。它回答“Next.js 前端如何组织和协作”，不替代具体页面的 UI 细则、API 字段契约和后端权限实现。

本文档适用于同一个 Next.js 应用中的普通用户端和平台管理端。两端共用工程、构建和基础 UI 能力，但使用独立的路由域、认证上下文、请求客户端、Layout 和业务组件。

## 2. 现状与问题

当前前端基础页面集中在根路由，`AppShell` 同时承载普通记账和管理端演示组件，Zustand 只保存当前账本和网络状态，API 层也没有区分两类身份的刷新会话。继续沿用这种结构会产生以下问题：

- 普通用户和管理员的登录入口、路由守卫和 Cookie 边界不清晰；
- 顶层 `/ledgers` 不能表达账本属于当前用户域，也不利于区分管理端账本治理页面；
- 普通端移动导航和管理端桌面导航会互相污染；
- 服务端数据、客户端界面状态、离线数据和认证状态混在一个 Store 中；
- 页面刷新、深链接、切换用户和切换账本时容易出现状态残留或数据串用。

## 3. 总体原则

1. 一个 Next.js 应用，两个明确的前端身份域：普通用户端和平台管理端。
2. 普通用户端所有业务页面位于 `/user/**`；平台管理端所有页面位于 `/admin/**`。
3. 普通用户登录和管理员登录分开，前端请求客户端、认证状态和刷新队列分开。
4. 账本是普通用户域下的资源，不使用顶层 `/ledgers`；账本页面使用 `/user/ledger/[ledgerId]/**`。
5. URL 是当前页面资源的可恢复入口，Zustand 只保存缓存、偏好和交互状态，不能成为唯一事实来源。
6. 后端返回的服务端数据使用查询缓存或 IndexedDB 管理，不把完整账单列表长期堆进 Zustand。
7. 前端权限只用于导航和交互优化，后端 Guard、成员角色和管理员权限码才是最终安全边界。
8. PWA 只缓存静态页面壳和明确允许的公开资源，不能无条件缓存账单、管理员数据或审计日志。

## 4. 路由域设计

### 4.1 普通用户端

普通用户端使用 `/user` 作为基础路由：

```text
/user/login                              普通用户登录
/user/register                           普通用户注册
/user                                     登录后的首页概览
/user/ledger                              当前用户的账本列表和切换入口
/user/ledger/[ledgerId]                   指定账本首页
/user/ledger/[ledgerId]/transactions      指定账本账单列表
/user/ledger/[ledgerId]/transactions/new  指定账本快速记账
/user/ledger/[ledgerId]/accounts          指定账本账户管理
/user/ledger/[ledgerId]/categories        指定账本分类管理
/user/ledger/[ledgerId]/statistics        指定账本统计分析
/user/ledger/[ledgerId]/members           指定账本成员和邀请
/user/settings                            当前用户个人设置
```

这里不使用顶层 `/ledgers`。`ledger` 保留为业务资源名称，但始终挂在 `/user` 下，表达“用户正在访问自己有权限的账本资源”。如果后续需要账本分享链接，也必须经过登录和后端成员校验，不能因为 URL 可访问就绕过权限。

### 4.2 平台管理端

平台管理端使用 `/admin` 作为基础路由：

```text
/admin/login                              管理员登录
/admin                                    管理端首页
/admin/users                              普通用户管理
/admin/users/[userId]                     普通用户详情
/admin/ledgers                            账本治理
/admin/ledgers/[ledgerId]                 账本详情和运营摘要
/admin/audit-logs                         管理员审计日志
/admin/admin-users                        管理员账号和角色
/admin/system-settings                    受控系统配置
```

管理端的 `/admin/ledgers` 是平台治理资源，与普通用户端的 `/user/ledger/[ledgerId]` 不是同一页面和权限上下文。管理员页面不能复用普通用户的账本切换器，也不能把 `LedgerMember` 角色当作管理员权限。

### 4.3 公共路由和根路径

```text
/                                        根据会话状态进入用户登录或用户首页
/error                                  全局错误兜底
/not-found                             全局 404 兜底
```

根路径默认只面向普通用户端：未登录进入 `/user/login`，已登录进入 `/user`。管理员必须明确访问 `/admin/login`，不能通过根路径猜测或自动进入管理端。

### 4.4 App Router 物理目录

路由组只用于组织 Layout，不改变浏览器 URL：

```text
frontend/src/app/
├── layout.tsx                         根 Layout
├── page.tsx                           根路径跳转
├── error.tsx                          全局错误边界
├── not-found.tsx                      全局 404
├── user/
│   ├── layout.tsx                     普通用户域基础 Layout
│   ├── login/page.tsx
│   ├── register/page.tsx
│   ├── (workspace)/                   用户工作区路由组，不增加 URL 层级
│   │   ├── layout.tsx                 用户工作区 Layout
│   │   ├── page.tsx
│   │   ├── ledger/page.tsx
│   │   ├── ledger/[ledgerId]/...
│   │   └── settings/page.tsx
│   └── loading.tsx
└── admin/
    ├── layout.tsx                     管理端基础 Layout
    ├── login/page.tsx
    ├── (console)/                     管理工作台路由组，不增加 URL 层级
    │   ├── layout.tsx                 管理端工作台 Layout
    │   ├── page.tsx
    │   ├── users/...
    │   ├── ledgers/...
    │   └── audit-logs/...
    ├── loading.tsx
    └── error.tsx
```

登录页不挂载工作区导航；工作区 Layout 只包裹完成身份初始化后的业务页面。

## 5. Layout 与 Provider 分层

### 5.1 根 Layout

根 Layout 只负责全局基础设施：

- `html`、中文语言、Metadata 和 PWA Manifest；
- 全局 CSS、字体和基础主题；
- Service Worker 注册；
- 全局错误、Toast 和无障碍基础设施；
- 不包含普通用户 Sidebar、底部导航或管理端菜单。

根 Layout 不读取普通用户或管理员的业务权限，避免服务端渲染时把两个身份域混在一起。

### 5.2 普通用户端 Layout

普通用户工作区包含：

- `UserAuthBoundary`：初始化普通用户会话，处理 401 和退出；
- `UserWorkspaceProvider`：读取当前用户可访问账本并恢复当前账本；
- `UserDesktopSidebar`：桌面端导航和账本切换；
- `UserMobileHeader`：当前账本、同步状态和用户入口；
- `UserMobileBottomNav`：移动端首页、账单、统计和账本入口；
- `QuickTransactionEntry`：全局快速记账入口；
- `SyncStatusBar`：离线、同步中、失败和冲突提示。

普通用户端采用移动优先布局。宽屏时扩展为 Sidebar + 内容区，窄屏时使用顶部栏 + 底部导航，不在移动端强行展示管理端密集表格。

### 5.3 管理端 Layout

管理端工作台包含：

- `AdminAuthBoundary`：初始化管理员会话和权限摘要；
- `AdminSidebar`：按权限码过滤菜单；
- `AdminHeader`：管理员资料、退出和当前环境提示；
- `AdminBreadcrumb`：显示后台资源层级；
- `AdminContent`：页面内容和统一加载/错误状态；
- `HighRiskActionBoundary`：高风险操作的原因、确认和结果反馈。

管理端采用桌面优先布局。窄屏时 Sidebar 改为 Drawer，表格改为横向滚动或卡片列表，但不使用普通端底部导航。

### 5.4 认证 Provider 边界

两端必须分别维护：

```text
UserAuthProvider
  ├── userAuthStore
  └── userApiClient / userRefreshQueue

AdminAuthProvider
  ├── adminAuthStore
  └── adminApiClient / adminRefreshQueue
```

两套 Provider 不共享 Token、刷新锁、登录状态和注销动作。公共 Provider 只能承载不会区分身份域的能力，例如 Toast、网络状态和主题。

## 6. 数据管理分层

### 6.1 服务端数据

服务端数据包括用户资料、账本、成员、账户、分类、账单、统计、管理员用户和审计日志。推荐使用 TanStack Query 作为查询缓存层，负责：

- 请求去重和缓存；
- 加载、空数据、错误和重新验证状态；
- 分页与服务端筛选；
- 写入成功后的相关查询失效；
- 普通用户切换账本时按 `ledgerId` 隔离缓存；
- 管理端按资源和权限域隔离缓存。

如果暂不引入 TanStack Query，也必须按相同职责建立 API Hook 和缓存边界，不能把完整服务端列表直接堆进一个全局 Zustand Store。

### 6.2 Zustand 客户端状态

建议拆成以下 Store：

| Store | 保存内容 | 是否持久化 |
| --- | --- | --- |
| `userAuthStore` | 当前用户摘要、初始化状态、登录状态 | 只保存非敏感摘要或不持久化 |
| `adminAuthStore` | 当前管理员摘要、权限码、初始化状态 | 默认不持久化敏感信息 |
| `workspaceStore` | 当前 `ledgerId`、最近账本 ID、当前月份 | 可持久化 ID 和偏好 |
| `uiStore` | Sidebar、Drawer、主题、弹窗和筛选 UI 状态 | 按需持久化 |
| `offlineStore` | 网络状态、待同步数量、同步状态和错误摘要 | 可持久化状态摘要 |

Access Token、Refresh Token、密码、完整账单列表、管理员审计数据不能进入 Zustand 或 localStorage。

### 6.3 IndexedDB

IndexedDB 负责离线和有限的本地数据：

- 最近访问账本的只读快照；
- 最近账单缓存；
- 离线新增账单 Outbox；
- `clientRequestId`、账本 ID、重试次数、同步状态和冲突信息。

本地数据必须按用户和账本隔离：

```text
user:{userId}:ledger:{ledgerId}:transactions
user:{userId}:ledger:{ledgerId}:outbox
```

退出登录、切换账号或检测到用户身份变化时，不得继续展示上一用户的账本和账单缓存。

## 7. API 请求与认证

建议目录：

```text
frontend/src/lib/api/
├── client.ts                         公共 Axios 配置和错误转换
├── user-client.ts                    普通用户 Cookie 请求客户端
├── admin-client.ts                   管理员 Cookie 请求客户端
├── user-refresh-queue.ts             普通用户 401 刷新队列
├── admin-refresh-queue.ts            管理员 401 刷新队列
├── user-api.ts                       普通用户领域 API
└── admin-api.ts                      管理端领域 API
```

普通用户端和管理端分别使用：

```text
普通用户：access_token / refresh_token
管理端：  admin_access_token / admin_refresh_token
```

客户端统一要求：

- `withCredentials: true`；
- 优先通过同源 `/api` 访问后端；
- 401 时同一身份域只允许一个刷新请求，其余请求进入队列；
- 刷新接口本身不重试，刷新失败只清理对应身份域；
- 错误响应转成稳定的前端错误类型和用户可读文案；
- 不把 Token 复制到 Authorization Header、Zustand 或 localStorage；
- 修改请求遵循服务端 CSRF 和来源校验约定。

前端类型放在 `frontend/src/types/`，不直接把 Prisma Model 暴露为页面类型。

## 8. 权限与路由守卫

路由守卫分为三层：

1. Next.js `proxy.ts`：根据路径和 Cookie 是否存在进行快速跳转，只负责体验，不构成安全边界。
2. `UserAuthBoundary` / `AdminAuthBoundary`：进入 Layout 后调用当前身份接口，处理会话初始化、刷新失败和登录跳转。
3. NestJS Guard 和 Service：最终校验身份、账本成员角色、管理员权限码和资源归属。

普通用户端按当前账本的 `memberRole` 控制按钮和导航：`OWNER`、`EDITOR`、`VIEWER`。管理端按权限码控制菜单和操作，例如 `admin:user:read`、`admin:user:status` 和 `admin:audit:read`。页面不能只判断角色名称，也不能把隐藏按钮当作授权。

## 9. PWA 与离线边界

Service Worker 只缓存静态资源、图标、字体和必要的页面壳。默认不缓存：

- 登录和刷新响应；
- 普通用户账单 API；
- 管理端用户、账本和审计 API；
- 包含个人资料或敏感财务数据的响应。

第一阶段离线范围：

1. 打开已缓存的普通用户账本页面；
2. 离线新增收入和支出；
3. 将请求写入 IndexedDB Outbox；
4. 网络恢复后按顺序提交；
5. 使用 `clientRequestId` 防止重复创建；
6. 明确展示待同步、成功、失败和冲突。

第一阶段不支持离线编辑和删除，避免在权限变更、软删除和版本冲突尚未稳定时产生不可解释的数据合并。

## 10. 前端目录边界

```text
frontend/src/
├── app/
│   ├── user/                         普通用户路由和 Layout
│   └── admin/                        管理端路由和 Layout
├── components/
│   ├── ui/                           通用基础组件
│   ├── common/                       两端都可复用且不含业务权限的组件
│   ├── user/                         普通用户业务组件
│   ├── admin/                        管理端业务组件
│   └── mobile/                       普通端移动交互组件
├── hooks/
├── lib/
│   ├── api/                          两套请求客户端和领域 API
│   ├── auth/                         身份边界和会话初始化
│   ├── offline/                      IndexedDB 和同步队列
│   └── routing/                      路由常量和跳转策略
├── store/                            Zustand Store
└── types/                            前端 DTO、状态和错误类型
```

`FoundationDashboard` 不作为长期业务页面；迁移时拆分为普通用户首页、管理端首页和各自的组件预览。普通端的金额键盘、同步提示不能进入管理端；管理端的脱敏字段、高风险确认和表格筛选不能进入普通端。

## 11. 测试设计

- 路由策略：未登录访问 `/user/**` 或 `/admin/**` 时跳转到对应登录页；已登录用户访问管理端不被当作管理员；管理员访问普通用户端不复用管理员身份。
- Store：用户/管理员身份隔离、当前账本切换、用户切换后的状态清理、Sidebar 和网络状态。
- API 客户端：两套 Cookie 请求、401 单次刷新、并发请求排队、刷新失败清理对应状态和错误转换。
- 组件：普通端移动导航、管理端 Drawer、空数据、加载、错误、无权限和离线状态。
- 数据管理：账本 ID 缓存隔离、IndexedDB Outbox、重复 `clientRequestId`、同步失败重试和冲突保留。
- E2E：后续覆盖用户登录、进入账本、新增账单、管理员登录和权限不足跳转；不使用脆弱的 CSS 选择器断言。

## 12. 实施范围与顺序

1. 路由骨架：建立 `/user/**` 和 `/admin/**`，拆分根页面和两套 Layout。
2. 认证请求层：建立两套 Axios Client、当前身份初始化和独立刷新队列。
3. Store：拆分用户认证、管理员认证、工作区、界面和离线状态 Store。
4. 数据层：引入服务端查询缓存；建立前端 DTO、错误类型和账本范围缓存键。
5. PWA：整理 Service Worker 缓存边界、IndexedDB 存储和 Outbox 状态。
6. 页面迁移：把现有基础演示拆入普通首页、管理首页和两端专属组件目录。

每一步都必须配套类型检查、契约测试或组件测试；跨路由认证和主流程稳定后再增加 E2E。

## 13. 取舍与风险

- 单 Next.js 应用降低部署和共享依赖成本，但要求两端目录、Provider、API Client 和组件边界持续隔离。
- `/user/ledger/[ledgerId]` 比顶层 `/ledgers` 多一层路径，但能明确用户域和账本上下文，刷新和深链接更可靠。
- TanStack Query 增加一个服务端状态依赖，但能避免 Zustand 承担缓存失效、分页和并发请求管理，推荐采用。
- 两套认证刷新队列会增加基础代码，但能避免管理员会话和普通用户会话互相注销或刷新污染。
- PWA 离线只支持新增，牺牲部分离线编辑能力换取同步语义可控；离线编辑应在版本冲突方案稳定后单独评审。

## 14. 未决问题

1. 管理端是否在第一期同时发布页面，还是只先保留路由和 Layout 骨架。
2. 是否现在引入 TanStack Query，或先使用自建的 API Hook 过渡；不论选哪种，服务端数据都不能由 Zustand 长期承载。
3. 普通用户是否需要密码找回页面；当前用户需求暂未纳入密码找回。
