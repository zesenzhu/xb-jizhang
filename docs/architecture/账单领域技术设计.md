# 小宝记账账单领域技术设计

## 1. 设计目标

在现有 NestJS、Prisma、PostgreSQL 和账本成员权限基础上，增加账户、分类和账单能力。设计优先保证账本隔离、金额一致性、重复请求安全和多人并发编辑可解释。

第一期模块边界为：

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| `account` | 账户查询、创建、编辑、停用、共享/私人可见性和余额读取 | 账单筛选和统计聚合 |
| `category` | 收入/支出分类查询、创建、编辑、排序、停用 | 金额计算和账户余额 |
| `transaction` | 收入/支出写入、查询、详情、编辑、软删除和审计 | 复杂报表和离线队列 |
| `statistics` | 月度收支、结余、分类排行和账户汇总 | 修改账单 |

所有模块依赖现有的 `LedgerMember(status=ACTIVE)` 访问校验，不在各模块中重新实现角色判断。

## 2. Prisma 模型调整

现有 `Account`、`Category`、`Transaction` 和 `TransactionAuditLog` 模型可以作为基础，但进入实现前需要补齐以下约束：

- 增加受控的 `AccountType`，API 不接受任意账户类型字符串；
- 保留 `AccountVisibility`，`PRIVATE` 必须有 `ownerId`，`SHARED` 的 `ownerId` 为空；
- 为账户名称、分类名称和停用查询增加符合 API 筛选的索引；
- `Category` 继续使用 `[ledgerId, type, name]` 唯一约束；
- `Transaction` 继续使用 `[ledgerId, clientRequestId]` 幂等唯一约束；
- `Transaction.version` 用于乐观并发控制，更新成功后递增；
- `Transaction.deletedAt` 用于软删除，所有默认查询显式过滤；
- 账户余额字段继续使用整数分，禁止 `Decimal` 和浮点金额。

如果账户类型约束需要迁移，先生成 Prisma Migration，再实现 Service，不能只在 DTO 中校验而让数据库接受任意值。

## 3. 权限模型

### 3.1 资源读取

```text
getActiveLedgerMember(userId, ledgerId)
  -> 账本不存在或成员不是 ACTIVE：资源不可用
  -> 读取 SHARED 账户/分类
  -> PRIVATE 账户追加 ownerId = userId
```

账单查询允许所有活跃成员读取，但账单关联的私人账户字段必须经过当前用户可见性校验，不能通过详情接口泄露其他成员私人账户信息。

### 3.2 资源写入

- 账户：`OWNER` 管理共享账户，`OWNER/EDITOR` 管理自己创建的私人账户。
- 分类：仅 `OWNER` 管理。
- 账单：`OWNER/EDITOR` 创建和编辑，`OWNER` 可删除全部账单，`EDITOR` 只能删除自己创建的账单。
- `VIEWER` 所有写入均在 Service 层拒绝。

Controller 只负责 DTO 和认证上下文传递，不能以请求体中的 `userId`、`ownerId` 或 `operatorId` 作为授权依据。

## 4. 账单写入事务

### 4.1 创建

```text
校验活跃成员和角色
  ↓
校验金额、类型、账户、分类、付款人和时间
  ↓
按 ledgerId + clientRequestId 查询幂等记录
  ↓
事务内创建 Transaction
  ↓
事务内更新 Account.currentBalanceCents
  ↓
事务内写入 TransactionAuditLog
  ↓
提交并返回账单详情
```

幂等命中时直接返回原账单，不更新余额和审计记录。并发创建依靠数据库唯一约束兜底，Service 将唯一冲突转换为已存在的幂等结果或明确冲突。

### 4.2 编辑

编辑使用 `WHERE id = ? AND ledgerId = ? AND version = ? AND deletedAt IS NULL` 的条件更新。事务内按旧值和新值计算余额差异：

- 支出金额或账户变化：恢复旧账户影响，再应用新账户扣减；
- 收入金额或账户变化：恢复旧账户影响，再应用新账户增加；
- 类型变化：先撤销旧类型，再应用新类型；
- 更新 `updatedById` 和 `version = version + 1`；
- 追加 before/after 审计数据。

条件更新影响行数为 `0` 时区分资源不可用和版本冲突，统一返回不泄露敏感信息的冲突错误。

### 4.3 软删除

删除必须在一个事务中完成：条件更新 `deletedAt`、递增版本、恢复账户余额、写入审计记录。重复删除不再次恢复余额。

## 5. 账户余额一致性

第一期采用“账单写入事务同步余额”的方案：

- 创建、编辑和删除账单与余额变化同事务提交；
- 不允许 Controller 直接更新余额；
- 账户详情返回已落库的 `currentBalanceCents`；
- 后续增加后台校准任务，按未删除账单重算并报告差异，不自动覆盖人工修正；
- 统计金额以账单聚合为准，不能仅依赖账户当前余额。

优点是查询快速且适合首页展示；代价是账单写入事务更复杂，需要覆盖跨账户编辑、重复请求和异常回滚。

## 6. 统一查询约束

- 所有查询必须带 `ledgerId`，不能只按资源 ID 查询。
- 账单默认过滤 `deletedAt IS NULL`。
- 账户默认过滤 `isActive = true`，管理查询通过明确参数查看停用账户。
- 分类默认过滤 `isActive = true`，按 `type`、`sortOrder`、名称排序。
- 账单列表采用服务端分页，不能一次性加载整本账本。
- 详情查询需要回读完整业务结果，不能仅返回写入请求中的数据。

## 7. 错误和审计

建议错误码：

| 错误码 | 含义 |
| --- | --- |
| `40021` | 金额、时间或账单字段不合法 |
| `40321` | 当前角色不能执行账户、分类或账单操作 |
| `40421` | 资源不存在或不属于当前账本 |
| `40921` | 分类/账户唯一冲突或版本冲突 |
| `40922` | 幂等请求已存在 |

账单创建、编辑和删除记录 `CREATE`、`UPDATE`、`DELETE` 审计动作；审计 before/after 只保存必要字段，不写入 Token、密码和完整私人数据。

一期只支持 `EXPENSE` 和 `INCOME`。数据库当前保留 `TRANSFER` 枚举及转账关联列作为结构遗留，但不纳入一期 DTO、Service、统计和接口契约；后续若重新启用，必须单独完成需求评审和迁移设计。

## 8. 测试策略

### Service 单元测试

- 活跃成员和三种角色权限；
- 账本、账户、分类、付款人交叉归属；
- 私人账户可见性；
- 金额、类型和停用状态校验；
- 创建幂等、编辑版本冲突和重复删除；
- 余额变化、事务回滚和审计数据；
- 账单详情回读和软删除过滤。

### Controller 契约测试

- 方法、路径参数和 DTO 传递；
- 当前用户来自认证上下文；
- 分页、筛选和主要异常映射；
- 不接收或信任客户端操作者 ID。

### 集成验证

使用独立开发数据库验证 Migration、唯一约束、事务回滚和并发冲突，不连接生产数据。
