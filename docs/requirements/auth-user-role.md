# 用户与账本成员角色需求

## 1. 文档范围

本文档定义小宝记账第一阶段的用户账户、登录鉴权、个人资料和账本成员角色需求。它解决“谁可以进入系统”和“用户在某个账本中可以做什么”两个问题。

本文档不定义系统级管理员角色，也不设计可配置的权限矩阵。`OWNER`、`EDITOR`、`VIEWER` 是账本成员角色，不是全局用户角色。

## 2. 背景与目标

### 2.1 背景

小宝记账从第一阶段就支持多人共享账本。用户需要拥有自己的个人账本，也需要在共享账本中安全地协作记账。所有账本资源必须以成员关系为权限边界，不能仅凭用户 ID 或客户端传入的 `ledgerId` 放行。

### 2.2 目标

- 用户可以注册、登录、退出和保持登录状态。
- 用户可以查看和维护自己的基础资料。
- 新用户注册后自动获得一个个人账本和 Owner 成员关系。
- 账本成员可以根据角色查看或操作账本数据。
- 被移除或主动退出的成员不能继续访问账本。
- 角色变更、成员移除和 Owner 转移有明确的权限限制和审计边界。

### 2.3 非目标

- 第一阶段不做系统级 `ADMIN / USER` 角色。
- 不做自定义权限矩阵和动态权限码。
- 不做第三方登录、手机短信登录和邮箱验证。
- 不做密码找回和账号注销，作为后续独立需求。
- 不在本文档定义邀请链接的完整生命周期，邀请功能单独维护需求文档。

## 3. 用户角色

### 3.1 未登录用户

可以访问登录和注册入口，不能访问任何用户资料、账本、成员或账单数据。

### 3.2 已登录用户

可以查看和修改自己的资料，并根据 `LedgerMember` 关系访问所属账本。用户在不同账本中可以拥有不同的成员角色。

### 3.3 账本成员角色

| 角色 | 定位 | 核心能力 |
| --- | --- | --- |
| `OWNER` | 账本负责人 | 管理账本、成员和全部账本数据 |
| `EDITOR` | 记账成员 | 查看、新增和编辑账单 |
| `VIEWER` | 只读成员 | 查看账单、账户和统计 |

## 4. 核心流程

### 4.1 注册并创建个人账本

1. 用户提交唯一用户名和密码，可以补充昵称、邮箱。
2. 服务端校验账号唯一性和密码规则。
3. 服务端在同一个数据库事务中创建用户、个人账本和 `OWNER` 成员关系。
4. 注册成功后签发登录凭证，用户可以直接进入个人账本。

如果创建账本或成员关系失败，用户创建也必须回滚，不能留下没有账本的半成品用户。

### 4.2 登录与会话保持

用户使用用户名和密码登录。成功后服务端通过 HttpOnly Cookie 保存访问凭证和刷新凭证；前端不能依赖 localStorage 保存 Token。

访问凭证失效时，客户端可以使用刷新凭证静默续期。刷新失败后清理会话并回到登录流程。

### 4.3 查看和修改个人资料

用户可以查看自己的用户 ID、用户名、昵称、邮箱、头像和账号状态。用户名是登录标识，第一阶段不允许修改；昵称、邮箱和头像可以独立修改。

邮箱第一阶段为可选字段，但填写后必须保持唯一。邮箱验证不在本阶段实现，不能把未验证邮箱当作安全凭证。

### 4.4 管理账本成员角色

- 所有活跃成员可以查看当前账本成员列表，但只能看到业务需要的公开资料。
- 只有 `OWNER` 可以修改成员角色、移除成员和转移 Owner 身份。
- `EDITOR` 和 `VIEWER` 不能管理成员，也不能通过修改请求体伪造角色。
- 被移除或主动退出的成员立即失去该账本的访问权限。
- 账本始终至少保留一名 `OWNER`。
- Owner 转移成功后，原 Owner 默认降为 `EDITOR`，新成员成为 `OWNER`；该操作必须在一个事务中完成。
- 个人账本的唯一 Owner 不能直接退出或被移除，个人账本的归档或删除另行设计。

## 5. 权限矩阵

| 操作 | `OWNER` | `EDITOR` | `VIEWER` |
| --- | --- | --- | --- |
| 查看账本和成员 | 允许 | 允许 | 允许 |
| 查看账单、账户和统计 | 允许 | 允许 | 允许 |
| 新增账单 | 允许 | 允许 | 禁止 |
| 编辑账单 | 允许 | 允许 | 禁止 |
| 删除账单 | 允许 | 禁止 | 禁止 |
| 管理账本设置 | 允许 | 禁止 | 禁止 |
| 邀请成员 | 允许 | 禁止 | 禁止 |
| 修改成员角色 | 允许 | 禁止 | 禁止 |
| 移除成员 | 允许 | 禁止 | 禁止 |
| 转移 Owner | 允许 | 禁止 | 禁止 |
| 修改自己的资料 | 允许 | 允许 | 允许 |

以上权限必须由后端统一判断，前端隐藏按钮不能替代服务端授权。

## 6. 业务规则

1. 用户名全局唯一，不能为空；用户名和密码的长度、字符范围由接口校验规则明确声明。
2. 注册创建用户、个人账本和 Owner 成员关系必须使用同一个事务。
3. 所有账本相关查询和写入必须同时校验当前用户、目标 `ledgerId` 和活跃成员状态。
4. `LEFT` 或 `REMOVED` 状态的成员不能访问账本资源；重新加入需要经过明确的邀请流程。
5. 角色更新只能使用固定枚举值 `OWNER`、`EDITOR`、`VIEWER`。
6. 任何成员移除、角色变更或 Owner 转移都不能造成账本没有 Owner。
7. 成员列表不能返回密码哈希、刷新凭证、内部安全字段等敏感信息。
8. 认证接口需要限制登录失败频率；具体 Redis 限流策略在后端技术文档中定义。
9. 登录、刷新、退出和权限变更的错误结果不能泄露其他用户或非成员账本的敏感信息。
10. 用户自己的资料修改不改变其在任何账本中的成员角色。

## 7. 接口范围初稿

以下路径是接口设计初稿，详细 DTO、响应结构和错误码在 API 文档评审后确定：

### 认证与用户

- `POST /api/auth/register`
- `POST /api/auth/login`
- `POST /api/auth/refresh`
- `POST /api/auth/logout`
- `GET /api/users/me`
- `PATCH /api/users/me`
- `PATCH /api/users/me/password`

### 账本成员

- `GET /api/ledgers/:ledgerId/members`
- `PATCH /api/ledgers/:ledgerId/members/:memberId/role`
- `DELETE /api/ledgers/:ledgerId/members/:memberId`
- `POST /api/ledgers/:ledgerId/members/leave`
- `POST /api/ledgers/:ledgerId/ownership-transfer`

接口实现必须复用统一认证上下文和成员权限校验，不接受客户端直接传入的操作者 ID 作为可信身份。

## 8. 验收标准

### 注册和认证

- 给定未注册用户名和合法密码，当用户提交注册，则创建用户、个人账本和 Owner 成员关系，并建立登录状态。
- 给定已存在用户名，当用户提交注册，则返回明确的重复账号错误，且不创建账本或成员脏数据。
- 给定正确凭证，当用户登录，则可以访问自己的用户信息和账本列表。
- 给定错误凭证，当用户登录，则返回认证失败，且不泄露账号是否存在的敏感信息。
- 给定过期访问凭证和有效刷新凭证，当客户端刷新会话，则获得新的访问凭证。
- 给定无效刷新凭证，当客户端刷新会话，则会话失效并要求重新登录。

### 用户资料

- 给定已登录用户，当用户读取当前资料，则响应不包含密码哈希和 Token。
- 给定已登录用户，当用户修改昵称、邮箱或头像，则只更新允许字段，不改变成员角色。
- 给定已登录用户，当用户提交已被其他用户占用的邮箱，则修改失败并保留原资料。

### 成员角色

- 给定 Owner 查看成员列表，则可以看到当前活跃成员的必要公开资料和角色。
- 给定 Editor 或 Viewer，当其修改角色、移除成员或转移 Owner，则服务端拒绝操作。
- 给定 Owner 将成员从 Editor 修改为 Viewer，则修改成功且后续账单写操作立即受限。
- 给定最后一名 Owner 尝试退出、被移除或降级，则服务端拒绝操作。
- 给定成员已被移除或主动退出，当其继续请求账本数据，则服务端拒绝访问。
- 给定 Owner 转移 Owner 身份，则新 Owner 和原 Owner 的角色在同一操作中完成变更。

## 9. 测试要求

- 用户注册 Service：覆盖成功创建、用户名重复、事务失败回滚。
- 登录 Service：覆盖密码正确、密码错误、账号停用和刷新凭证失效。
- 用户资料 Service：覆盖敏感字段过滤、邮箱重复和非法字段。
- 成员权限 Service：覆盖三种角色、跨账本访问、成员状态、最后 Owner 保护和 Owner 转移。
- Controller：覆盖 DTO 参数传递、认证上下文传递和主要异常映射。
- 数据库集成测试：在实现事务和唯一约束时增加隔离数据库测试，不使用本地开发数据库。

## 10. 数据和文档影响

当前 Prisma Schema 已具备 `User`、`Ledger` 和 `LedgerMember` 基础模型，不需要引入系统级 `Role` 表。后续接口实现需要补充认证模块、用户模块、成员权限校验和必要的 Token 会话字段。

本需求确认后，需要继续维护：

- `docs/api/auth-user.md`
- `docs/api/ledger-member.md`
- `docs/architecture/backend.md`
- `docs/architecture/testing.md`
- `docs/ui/screens/ledger-members.md`

## 11. 未决问题

1. 后续是否允许用户使用邮箱作为登录标识，当前 MVP 只使用用户名登录。
2. 头像第一阶段使用外部 URL 还是接入本地上传，需要在 UI 和部署方案确定后决定。
3. 成员邀请使用邮箱、用户名还是通用邀请链接，需要在共享账本需求中单独确认。
