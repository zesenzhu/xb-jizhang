# 小宝记账一期用户需求

## 1. 文档定位

本文档把《需求基础》中的长期产品设想收敛为第一期可开发、可验收的用户需求。它定义一期交付什么、不交付什么，以及用户完成核心任务时必须得到的结果。

本文档是一期范围的主入口；用户注册、登录和成员角色的细节以《用户与成员角色需求》为准，长期能力和后续阶段仍以《需求基础》为准。

## 2. 一期目标

第一期完成一个可以真实使用的多人共享记账 PWA，使用户能够：

- 注册并安全登录；
- 自动拥有个人账本；
- 创建共享账本并邀请其他用户；
- 按成员角色协作；
- 快速记录收入和支出；
- 查看账单、账户余额和月度收支概览；
- 在网络不稳定时暂存账单，恢复网络后继续同步。

一期的核心衡量标准是：用户能够快速、准确地记下一笔账，并且不同账本和不同角色之间的数据不会混淆或越权。

## 3. 用户与使用场景

### 3.1 目标用户

- 个人用户：管理自己的日常收入、支出和账户。
- 家庭或伴侣：共同维护一个共享账本。
- 小型共同生活群体：多人记录公共支出，并查看共同账本的收支情况。

### 3.2 一期核心场景

1. 用户首次打开应用，注册账号并进入自动创建的个人账本。
2. 用户创建现金、微信、支付宝或银行卡等账户。
3. 用户选择支出类型、金额、分类和账户，快速保存一笔账。
4. 用户创建共享账本，通过邀请让其他成员加入。
5. Owner、Editor、Viewer 按角色完成各自允许的查看或记账操作。
6. 用户按月份查看收入、支出、结余和最近账单。
7. 用户离线时暂存一笔账，网络恢复后同步并避免重复创建。

## 4. 一期范围

### 4.1 P0 必须完成

| 功能域 | 一期要求 |
| --- | --- |
| 用户与认证 | 注册、登录、退出、刷新会话、当前用户资料、修改密码 |
| 个人账本 | 注册后自动创建、查看、切换和基础资料维护 |
| 共享账本 | 创建共享账本、查看自己加入的账本、切换当前账本 |
| 成员协作 | 邀请、接受邀请、成员列表、角色管理、移除成员、主动退出 |
| 角色权限 | 固定使用 `OWNER`、`EDITOR`、`VIEWER`，后端统一校验 |
| 账户管理 | 新增、编辑、停用现金、微信、支付宝、银行卡等账户 |
| 分类管理 | 收入和支出分类的查看、新增、编辑、停用 |
| 快速记账 | 支出和收入的新增、编辑、软删除 |
| 账单列表 | 按账本、月份、类型、分类、账户和成员查看与筛选 |
| 首页概览 | 月度收入、支出、结余、账户余额和最近账单 |
| 基础离线 | 离线暂存新增收入/支出，恢复网络后同步并展示结果 |
| 质量保障 | 核心权限、幂等、并发和跨账本隔离有自动化测试 |

### 4.2 P1 重要增强

- 标签和按标签筛选；
- 分类预算和月度预算；
- 更细的统计图表和按成员统计；
- 账单导入、导出和备份；
- 离线同步冲突的可视化处理。

### 4.3 一期明确不做

- 平台管理端前端页面和后台管理接口不作为本期用户业务交付；平台管理端作为独立权限域纳入总体架构，后台身份、权限模型、会话和审计边界按《平台管理端需求》预留；
- 第三方登录、短信登录、邮箱验证和密码找回；
- AA 分摊、复杂结算和多人实时协同编辑；
- 多币种换算、投资资产和负债管理；
- 自动同步银行、微信或支付宝流水；
- 附件、票据 OCR 和复杂报销流程。

### 4.4 平台管理端边界

本期先交付普通用户和多人共享账本能力，但后端设计必须保留平台管理端的独立身份边界。平台管理员使用独立的 `AdminUser`、管理端 Cookie、Token audience、Refresh Session、Guard 和权限码体系，不给普通 `User` 增加简单的 `isAdmin` 字段，也不把平台管理员混入 `LedgerMember` 角色。

普通用户前端使用 `/user/login`、`/user/register` 和 `/user/**` 路由，账本页面使用 `/user/ledger/[ledgerId]/**`；管理端前端后续使用 `/admin/login` 和 `/admin/**` 路由。本期不实现管理端业务页面。后台接口、Prisma 模型和审计设计以《平台管理端技术设计》和《管理端接口约定》为准。

## 5. 用户流程

### 5.1 首次使用

1. 用户进入应用，选择注册或登录。
2. 注册成功后，系统创建个人账本并将用户设为 `OWNER`。
3. 用户进入首页，看到空账本引导、快速记账入口和账户创建入口。
4. 用户创建至少一个账户和必要分类后，可以开始记录账单。

### 5.2 快速记账

1. 用户从首页或账单列表点击“记一笔”。
2. 用户选择收入或支出，输入金额，选择分类和账户。
3. 发生时间默认当前时间，用户可以修改；标题和备注为可选。
4. 用户提交后看到服务端确认结果，回到当前页面并刷新月度汇总。
5. 重复点击提交或网络重试不能生成重复账单。

### 5.3 共享账本

1. Owner 创建共享账本并设置账本名称。
2. Owner 发起邀请，设置被邀请人的目标身份或邀请方式。
3. 被邀请用户登录后查看并接受邀请。
4. 接受成功后加入账本，按照被授予的角色访问账本。
5. Owner 可以调整角色、移除成员或转移 Owner 身份。

### 5.4 离线记账

1. 用户在无网络状态下进入已缓存的账本和记账入口。
2. 用户填写收入或支出并保存，应用将记录标记为“待同步”。
3. 网络恢复后，应用按顺序提交待同步记录。
4. 服务端通过客户端幂等 ID 防止重复创建。
5. 同步成功、失败或发生冲突时，页面必须明确显示状态，不能伪造为已入账。

## 6. 一期业务规则

1. 所有账单、账户、分类和统计都属于账本，用户必须是该账本的活跃成员才能访问。
2. 个人账本和共享账本使用同一套账本模型；个人账本默认只有一个 `OWNER`。
3. `OWNER` 可以管理账本和成员；`EDITOR` 可以新增和编辑账单；`VIEWER` 只能查看。
4. 账单删除采用软删除，默认列表和统计不包含已删除数据。
5. 金额使用整数分保存和计算，界面展示为用户可读的金额格式。
6. 每笔新增账单必须携带客户端生成的唯一幂等 ID。
7. 编辑账单必须携带服务端返回的版本信息；版本冲突时保留服务端数据并提示用户处理。
8. 支出和收入必须选择有效的账本账户和分类；停用的账户或分类不能用于新增账单。
9. 成员被移除或主动退出后，不能继续读取原账本数据。
10. 权限检查在服务端完成，前端仅负责展示与交互限制。

## 7. 页面和交互要求

### 7.1 页面范围

- 登录页；
- 注册页；
- 首页概览；
- 账本列表和账本切换；
- 账单列表；
- 快速记账页或弹层；
- 账户管理；
- 分类管理；
- 成员和邀请管理；
- 个人设置。

### 7.2 必须覆盖的界面状态

- 首次加载和请求中；
- 无账本、无账户、无分类和无账单；
- 保存成功；
- 表单校验失败；
- 服务端请求失败；
- 无权限操作；
- 网络离线；
- 待同步、同步成功、同步失败和同步冲突。

### 7.3 移动端要求

- 首页打开后可以直接进入快速记账；
- 金额输入使用适合移动端的数字键盘；
- 关键操作在单手操作范围内完成；
- 错误信息不能只通过短暂 Toast 表示，表单错误需要保留到用户修正；
- 离线状态和同步状态不能依赖颜色单独表达。

## 8. 一期验收标准

### 8.1 账户和账本

- 给定新用户提交合法注册信息，当注册成功，则用户拥有一个个人账本并成为 Owner。
- 给定用户加入多个账本，当用户切换账本，则首页、账单、账户、分类和统计全部使用当前账本数据。
- 给定用户请求不属于自己的账本 ID，当用户访问账本资源，则服务端拒绝访问且不返回账本数据。

### 8.2 角色和协作

- 给定 Viewer，当其提交新增或编辑账单请求，则服务端拒绝写入。
- 给定 Editor，当其访问成员角色管理接口，则服务端拒绝操作。
- 给定 Owner 转移 Owner 身份，当操作成功，则新 Owner 获得管理权限，原 Owner 降为 Editor。
- 给定最后一名 Owner 尝试退出或被移除，当请求提交，则操作失败且账本仍保留原 Owner。

### 8.3 记账和统计

- 给定有效账户、分类和金额，当用户保存支出，则账单出现在当前账本列表和对应月份统计中。
- 给定金额为零、负数或格式非法，当用户提交账单，则显示字段错误且不发送有效创建请求。
- 给定相同客户端幂等 ID 的创建请求被重复提交，则服务端只保留一笔账单。
- 给定用户软删除一笔账单，当用户刷新列表和统计，则该账单不再计入默认结果。

### 8.4 离线和异常

- 给定设备离线，当用户保存合法账单，则记录进入待同步状态且用户填写内容不丢失。
- 给定网络恢复，当同步成功，则记录变为已同步并出现在账单列表中。
- 给定同步请求失败，则记录保留在队列中并显示可恢复错误，不伪造为已入账。
- 给定接口返回 401，当会话刷新失败，则清理登录状态并引导用户重新登录。

## 9. 测试要求

- 认证和用户资料：覆盖注册唯一性、会话刷新、敏感字段过滤和密码修改。
- 账本和角色：覆盖成员访问、三种角色越权、最后 Owner 保护和 Owner 转移。
- 账单：覆盖金额校验、账本隔离、账户/分类归属、软删除、幂等和并发冲突。
- 前端 Store 和离线队列：覆盖当前账本切换、网络状态、待同步状态和失败重试。
- 用户核心流程：后续使用 E2E 覆盖注册/登录、切换账本和新增账单主流程。

## 10. 影响文档和实现边界

本需求确认后，按以下顺序进入设计：

1. 维护 `用户与成员角色需求.md` 中的认证和角色细则。
2. 编写用户和账本成员 API 文档。
3. 编写后端认证、用户、账本和成员模块技术方案。
4. 编写首页、快速记账和成员管理 UI 文档。
5. 以验收标准拆分后端和前端实现计划，并为行为变更补充自动化测试。

平台管理端后台在普通用户认证稳定后单独实施；管理端前端页面不阻塞普通记账 MVP，但后台权限和审计模型不能使用临时的普通用户字段替代。

一期不要求一次性完成 P1 能力；P1 需求只有在 P0 主流程稳定后再进入开发。

## 11. 未决问题

1. 邀请目标采用邮箱、用户名还是通用邀请链接，影响成员邀请接口和 UI。
2. 一期离线范围是只支持新增收入/支出，还是允许离线编辑和删除，需要结合 IndexedDB 方案确认。
3. 首页月度统计是否需要在第一期支持自定义日期范围，当前默认只支持自然月。
