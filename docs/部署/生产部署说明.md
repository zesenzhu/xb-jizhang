# 小宝记账生产部署说明

## 1. 部署结论

小宝记账使用一个 Git 仓库、两个独立 Docker 镜像和一次 GitHub Actions 发布流程：

```text
提交或手动发布
  → 检测 backend/、frontend/ 变更
  → 只构建发生变化的镜像
  → 从 GitHub production Environment 生成生产配置
  → SSH 创建服务器目录
  → tar.gz + SCP 上传
  → 服务器校验并原子替换生产配置
  → 服务器 docker load
  → 仅重启变化的服务
  → 健康检查
```

前端和后端属于同一套环境，但分别运行在独立容器中。当前默认生产端口为前端 `8090`、后端 `8091`，只绑定服务器本机，由 Nginx 对外提供 HTTPS。

日常发布不需要登录服务器。完成一次性配置后，只需要关注 GitHub Actions 的执行结果；环境变量、部署目录、镜像上传、数据库迁移、健康检查和失败中止均由工作流完成。

## 2. 服务器目录

```text
/www/wwwroot/xiaobao-jizhang/
├── docker-compose.prod.yml
├── production.env       # GitHub Actions 自动同步，不提交 Git
├── release.env          # 部署脚本维护当前镜像版本
├── deploy-prod.sh
├── backup-prod.sh
└── backups/
```

旧项目 `xbnestjs` 继续使用自己的目录、Compose、容器、网络、数据库和 Redis，不与本项目共用。

## 3. 首次服务器准备

服务器需要提前安装并确认：

- Docker Engine 和 Docker Compose Plugin；
- Nginx；
- `curl`；
- GitHub Actions 使用的 SSH 用户具备目标目录读写权限和 Docker 执行权限；
- 域名 DNS 已指向服务器；
- HTTPS 证书已准备或由 Certbot/服务器面板托管。

工作流使用 `appleboy/scp-action@v0.1.7` 和 `appleboy/ssh-action@v1.0.3`，与参考项目已验证的发布链路保持一致。

工作流会在上传部署包前自动执行：

```bash
mkdir -p /www/wwwroot/xiaobao-jizhang/backups
```

服务器首次部署不需要手工创建 `production.env`。GitHub Actions 会生成 `production.env.new`，上传后由服务器校验并原子替换为 `production.env`。首次部署时必须同时构建前后端镜像，工作流会自动创建 `release.env`。

## 4. GitHub `production` Environment 配置

在仓库 `Settings → Environments` 创建名为 `production` 的 Environment。部署 Job 使用 `environment: production`，可以在 GitHub Actions 中查看发布状态，并按需设置人工审批。

### 4.1 Environment Secrets

以下字段放在 `Settings → Environments → production → Environment secrets`：

| 名称 | 用途 |
| --- | --- |
| `DB_PASSWORD` | PostgreSQL 密码 |
| `JWT_ACCESS_SECRET` | 普通用户 Access Token 密钥 |
| `JWT_ADMIN_ACCESS_SECRET` | 管理员 Access Token 密钥，必须与普通用户密钥不同 |
| `SERVER_HOST` | 服务器 IP 或域名 |
| `SERVER_USER` | SSH 部署用户 |
| `SERVER_SSH_KEY` | SSH 私钥 |
| `SERVER_PORT` | SSH 端口，可选，默认 `22` |

### 4.2 Environment Variables

以下字段放在 `Settings → Environments → production → Environment variables`：

| 名称 | 用途 | 默认值 |
| --- | --- | --- |
| `DB_USER` | PostgreSQL 用户 | `jizhang` |
| `DB_NAME` | PostgreSQL 数据库名 | `jizhang` |
| `CORS_ORIGINS` | 正式前端域名，例如 `https://jizhang.xiaobao.work` | `https://jizhang.xiaobao.work` |
| `ACCESS_TOKEN_TTL_SECONDS` | 普通用户 Access Token 有效期 | `900` |
| `REFRESH_SESSION_TTL_SECONDS` | 普通用户刷新会话有效期 | `2592000` |
| `ADMIN_ACCESS_TOKEN_TTL_SECONDS` | 管理员 Access Token 有效期 | `900` |
| `ADMIN_REFRESH_SESSION_TTL_SECONDS` | 管理员刷新会话有效期 | `2592000` |
| `BACKEND_PORT` | 宿主机后端端口 | `8091` |
| `FRONTEND_PORT` | 宿主机前端端口 | `8090` |
| `JIZHANG_DEPLOY_PATH` | 服务器部署目录 | `/www/wwwroot/xiaobao-jizhang` |

推荐生成密钥：

```bash
openssl rand -hex 32
```

分别生成并填写 `DB_PASSWORD`、`JWT_ACCESS_SECRET` 和 `JWT_ADMIN_ACCESS_SECRET`。不要把真实值写入 `.env.production.example`、代码、Issue、日志或普通 GitHub Variables。

工作流每次发布都会从这些 Secrets/Variables 生成生产配置；未配置 `CORS_ORIGINS` 时默认使用 `https://jizhang.xiaobao.work`，不把 `production.env` 写回仓库。

## 5. 变更检测规则

| 变更路径 | 后端镜像 | 前端镜像 | 数据库备份 | 数据库迁移 |
| --- | ---: | ---: | ---: | ---: |
| `backend/**` | 构建 | 不构建 | 执行 | 执行 |
| `frontend/**` | 不构建 | 构建 | 不执行 | 执行 |
| `docker-compose.prod.yml` | 不构建 | 不构建 | 不执行 | 执行 |
| `docker/nginx/**` | 不构建 | 不构建 | 不执行 | 执行 |
| `scripts/**`、Workflow | 不构建 | 不构建 | 不执行 | 执行 |
| `docs/**` | 不构建 | 不构建 | 不部署 | 不部署 |

数据库迁移在每次实际部署时都会执行，不受变更范围影响。`prisma migrate deploy` 对已应用的迁移是幂等的，跳过已完成的记录只产生一次查询。迁移不能挂在后端变更判断下：变更检测基线是单次提交的 diff，一次只修改 `scripts/` 或 `.github/` 的发布同样会拉取新镜像与新 Prisma schema，一旦跳过，线上数据库就会停留在旧结构，并让后续所有写接口返回 500。

数据库备份只在后端镜像变化时创建，且必须早于迁移执行；先改表结构再备份会让备份失去回滚价值。

手动执行 Workflow 时可以选择 `deploy_all=true`，强制构建前后端。API 破坏性变更也建议强制双端发布，或先发布兼容后端再发布前端。

## 6. 发布触发方式

默认推送 `v*` Tag 触发：

```bash
git tag v0.1.0
git push origin v0.1.0
```

也可以在 GitHub Actions 页面手动运行，并按需选择：

- `deploy_all`：强制重新构建并发布前后端；
- `sync_config`：只同步 GitHub `production` Environment 配置并重启服务，不重新构建镜像。

例如只修改了数据库密码、JWT Secret、域名或端口时，选择 `sync_config` 即可，不需要提交代码或重新构建镜像。

镜像使用 Git commit SHA 作为版本，例如：

```text
xiaobao-jizhang-backend:abcdef...
xiaobao-jizhang-frontend:abcdef...
```

`release.env` 保存当前前后端镜像版本，因此只改前端时后端版本保持不变，只改后端时前端版本保持不变。

## 7. 发布流程

每次实际部署都会按以下顺序执行：

```text
GitHub Environment Secrets/Variables
  → 生成 production.env.new
  → SSH 创建服务器目录
  → SCP 上传部署文件和生产配置
  → 服务器校验必填配置
  → 原子替换 production.env
  → 加载发生变化的镜像
  → 启动 PostgreSQL/Redis
  → 后端变化时备份数据库
  → 执行 prisma migrate deploy
  → 按变化重启后端/前端
  → 健康检查
```

前端变化时只加载并更新前端镜像；后端版本保持不变。后端变化时只加载并更新后端镜像；前端版本保持不变。配置变化时不构建镜像，但会重新应用前后端容器配置。

健康检查访问 `/api/health`，该接口会查询 Prisma 迁移记录表。数据库不可达或迁移未应用时返回 `503`，部署脚本据此中止，不会把「容器已启动但数据库仍是空库」的状态判定为发布成功。

如果生产配置缺少必填字段，部署会在替换旧配置前失败，不会使用不完整配置重启服务。GitHub Actions 同一时间只允许一个生产发布运行，避免两个发布互相覆盖 `release.env`。

## 8. Nginx 和 HTTPS

推荐使用同源域名：

```text
https://jizhang.example.com/       → 127.0.0.1:8090
https://jizhang.example.com/api/   → 127.0.0.1:8091/api/
```

前端构建参数固定使用：

```env
NEXT_PUBLIC_API_URL=/api
```

### 8.1 站点配置文件必须独立

生产服务器上的站点配置写在 `/www/server/panel/vhost/nginx/jizhang.<域名>.conf`，**不要追加到旧项目的 `xiaobao.work.conf` 末尾**。旧项目文件会被宝塔面板在修改域名、续证书或切换运行环境时整体重写，追加内容会静默丢失；同一端口出现重复 `server_name` 时，nginx 也会只保留其中一个并打印 `conflicting server name`，实际生效者取决于文件名排序。

本站点配置以 `docker/nginx/jizhang.conf.example` 为模板，替换域名与证书路径后落盘，然后执行 `nginx -t && nginx -s reload`。

### 8.2 域名与证书

| 项目 | 说明 |
| --- | --- |
| 证书文件 | `/etc/nginx/certs/<域名>.pem`（含完整链）与 `<域名>.key` |
| 必须包含的 SAN | 裸域与 `www` 变体，否则 `www` 访问会报证书名称不匹配 |
| 有效期 | 契约 CA 已缩短至 199 天以内，个人测试证书通常更短 |
| 续期检查 | 到期前 30 天重新申请并覆盖两个文件，再执行 `nginx -t && nginx -s reload` |

证书到期当天，全站 TLS 握手直接失败且没有任何降级入口。上线后必须把到期日写入日历或监控，不能只依赖证书颁发机构的邮件提醒。

### 8.3 Cookie 与 HTTPS 的强耦合

后端在 `NODE_ENV=production` 下会为会话 Cookie 加上 `Secure` 属性：

```text
Set-Cookie: access_token=...; HttpOnly; Secure; SameSite=Lax; Path=/
Set-Cookie: refresh_token=...; HttpOnly; Secure; SameSite=Lax; Path=/api/auth
```

`Secure` Cookie 只在 HTTPS 响应中被浏览器接受。因此：

- HTTP 下登录接口会返回成功但浏览器丢弃 Cookie，随后 `GET /api/users/me` 返回 `401`，表现为“登录后又跳回登录页”的死循环；
- 前端 API 基地址必须是相对路径 `/api`，由页面协议自动继承 HTTPS；写成 `http://` 会让 POST 被 `301` 降级为 GET，登录接口直接返回 `404 Cannot GET /api/auth/login`。

排查会话问题时按此顺序取证，不要凭现象猜测：

```bash
curl -sI https://<域名>/user/login | grep -i strict-transport-security   # HTTPS 是否纳入强制
curl -s https://<域名>/api/health                                        # 反代是否命中本项目后端
curl -s -D- -o /dev/null -X POST https://<域名>/api/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"x","password":"y"}' | grep -i set-cookie
```

第三步若没有回显 `Set-Cookie: ... Secure`，说明请求没有真正落在 HTTPS 上。

### 8.4 HSTS 必须分档下发

站点模板默认写入 `Strict-Transport-Security: max-age=300`。这个响应头会被浏览器持久记录，且**无法通过修改服务器配置撤销**，只能等待 `max-age` 到期。

分档推进顺序：

| 阶段 | 值 | 进入下一档的前置条件 |
| --- | --- | --- |
| 初始 | `max-age=300` | 证书、跳转、Cookie 全部正常 |
| 观察 | `max-age=86400` | 完整走过一次证书续期 |
| 稳定 | `max-age=31536000` | 续期流程已自动化或有明确负责人 |

禁止添加 `includeSubDomains` 与 `preload`：前者要求所有子域先具备有效证书，后者进入浏览器内置清单后几乎无法移除。

### 8.5 安全响应头的继承陷阱

nginx 的 `add_header` 继承规则是：某个 `location` 中只要出现任意一条 `add_header`，该 location 就**不再继承** server 级的全部 `add_header`。站点模板中 `/`、`/sw.js`、`/_next/static/` 都自带 `Cache-Control`，因此 HSTS 与安全头在这些 location 中重复声明。新增带 `add_header` 的 location 时，必须同步补齐同一组头，否则该路径会静默缺失 HSTS。

模板中的 `Content-Security-Policy-Report-Only` 只上报不拦截。确认违规日志为零后，再改为 `Content-Security-Policy` 正式生效。

## 9. 三期当前不新增对象存储；第四期目标方案

图片附件与对象存储已移出三期范围，因此当前生产部署**不新增 OSS/MinIO、不新增对象存储环境变量、不增加附件备份任务**。现有 PostgreSQL、Redis、NestJS、Next.js 和 Nginx 的部署方式保持不变。

当前 `ecs.e-c1m1.large`（2 vCPU/2 GiB、20 GB 系统盘）仍需注意资源余量：

- 不建议在同一台机器上再运行 MinIO；这会增加内存和磁盘压力。
- 第四期已确定生产使用阿里云 OSS 标准本地冗余私有 Bucket，本地开发和集成测试使用 MinIO；不在当前 2C2G ECS 上运行生产 MinIO。详细方案见[第四期账单图片附件与对象存储设计](../architecture/账单图片附件与对象存储设计.md)。
- 第四期采用预签名直传和短期签名读取：NestJS 只负责鉴权、签发地址、完成确认和元数据，不中转图片二进制。
- 阿里云当前试用额度按 20GB 存储、2GB 下行流量、20 万次请求、3 个月有效期规划；存储量、下行流量、请求数达到 80% 时告警，到期前确认续费或转按量付费。
- 生产 Bucket 保持私有并配置受限 CORS，只允许正式前端域名；AccessKey 或 RAM 凭据只注入后端环境变量，不能进入前端和仓库。
- 当前部署应限制 Node 堆、PostgreSQL 共享缓冲和 Docker 日志大小，避免系统盘和内存被占满。
- 第四期上线前，数据库和 OSS 必须纳入联合备份、恢复演练和附件对象对账；在演练完成前保持附件功能关闭。

## 10. 回滚## 10. 回滚

回滚前后端镜像版本时，修改服务器 `release.env` 中对应的镜像 Tag，然后执行：

```bash
docker compose \
  --env-file production.env \
  --env-file release.env \
  -f docker-compose.prod.yml \
  up -d --no-build backend frontend
```

数据库 Migration 不保证自动向下回滚。包含不可逆 Schema 变更的发布必须先备份，并准备向前兼容的修复 Migration。

## 11. 用户需要提前处理的事项

只需要一次性提供或处理：

1. 生产服务器 IP、SSH 用户、SSH 端口和部署私钥；
2. GitHub `production` Environment 的 Secrets 和 Variables；
3. 记账项目正式域名和 DNS 解析；
4. Nginx 安装、站点配置和 HTTPS 证书；
5. 首次部署后的管理员 Bootstrap 账号初始化；
6. 数据库备份目录的磁盘空间和备份保留策略；
7. 首次 staging 或生产发布窗口；
8. 证书到期日提醒（当前证书有效至 2027-01-31），以及到期前 30 天的续期操作人。

完成一次性配置后，日常发布、环境配置同步、镜像上传、容器更新和健康检查均由 GitHub Actions 自动执行。只有 Nginx、DNS、证书续期等服务器基础设施事项不属于本仓库发布流程。
